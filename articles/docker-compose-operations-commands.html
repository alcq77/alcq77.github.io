Docker 与 Docker Compose 常用运维命令

知知行笔记·约 62 分钟阅读
dockercomposecontainersoperationstroubleshooting

使用 Docker 和 Compose 查看容器状态、排查日志与网络问题，以及构建镜像、更新服务、备份数据和清理资源。

命令采用 Linux shell 与 Compose V2 的 docker compose 写法；旧的 docker-compose 是另一套命令，执行前先确认本机版本，并调整示例名称与地址。启停、更新和清理操作按需选择。

普通用户没有Docker操作权限时，使用管理员批准的sudo或已有rootless环境。镜像拉取、导出、加载和启动必须操作同一目标daemon；不要在rootless与 sudo docker、本机与远程context之间混用。示例中的版本、资源限制、目录和端口都需按实际部署核对。

要做什么 阅读位置
查看状态、日志和资源，定位容器退出 第1～6项
构建镜像，打包后上传到离线服务器并加载 第7项，尤其7.2～7.5
排查端口和网络、备份与恢复数据 第8、9项
用Compose部署、离线迁移、更新和回滚 第10～13项，离线部署看13.2
释放磁盘或快速定位故障 第14、15项，先查对象归属再清理

1. 环境、版本和目标主机

安装 Docker Engine 与 Compose 插件（Ubuntu / Debian）

仅用于官方当前支持的Ubuntu/Debian版本的新安装环境。先用 cat /etc/os-release、uname -m 确认发行版与架构；已有Docker、Podman、containerd或业务容器时，先核对兼容与迁移方案，不直接卸载替换。

准备软件源：

sudo apt-get update                         # 刷新批准的软件源索引
sudo apt-get install ca-certificates curl    # 安装证书和HTTPS下载工具
sudo install -m 0755 -d /etc/apt/keyrings     # 创建软件源公钥目录
. /etc/os-release                           # 读取当前发行版变量
# 下列步骤仅在ID为ubuntu或debian时使用
docker_os="$ID"                             # 仅选择已确认支持的ubuntu或debian
curl -fL "https://download.docker.com/linux/$docker_os/gpg" -o /tmp/docker.asc # 下载官方源公钥，失败停止
sudo install -m 0644 /tmp/docker.asc /etc/apt/keyrings/docker.asc # 安装核对过指纹的公钥
# 生成匹配发行版及架构的源定义；tee覆盖该源文件，执行前确认不是其他管理员维护的配置。
printf 'deb [arch=%s signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/%s %s stable\n' \
  "$(dpkg --print-architecture)" "$docker_os" "${UBUNTU_CODENAME:-$VERSION_CODENAME}" \
  | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null
sudo apt-get update                         # 验证新源能够正常读取，失败不继续安装

示例：Ubuntu使用ubuntu仓库及本机发行代号，Debian使用debian仓库；不要把Ubuntu代号写进Debian源。下载失败时先停止，确认网络、证书与官方源可达，不跳过签名。

| sudo tee ... > /dev/null 中，| 将生成的源配置传给具有权限的 tee 写入文件；> /dev/null 只丢弃 tee 同时输出到终端的那份内容，不会取消文件写入。tee 默认覆盖目标文件。

安装并验证：

sudo apt-get install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin # 安装引擎、CLI和插件
sudo systemctl enable --now docker # 新安装环境启动并开启自启
sudo docker version                         # 验证Client及Server连接
sudo docker compose version                 # 验证Compose V2插件

示例：docker compose version能输出版本，表示V2插件可用；docker version还应能连接Server。安装包可能自动启动服务，需在批准的主机上操作。发行版支持范围及版本选择以 Ubuntu安装说明 和 Debian安装说明 为准。

安装 Docker Engine 与 Compose 插件（RHEL 9 / CentOS Stream 9示例）

仅对匹配且受支持的发行版使用官方源；Rocky/AlmaLinux等兼容发行版须按其维护策略核对，不默认认定官方同等支持。已有容器运行时先核对现状。

cat /etc/os-release                         # 确认当前系统，不套用到CentOS 7
sudo dnf install dnf-plugins-core            # 为示例中的DNF4安装源管理插件
# CentOS Stream 9：选这一条
sudo dnf config-manager --add-repo https://download.docker.com/linux/centos/docker-ce.repo # 添加CentOS对应源
# RHEL 9：改选这一条，不要两套源都加
# sudo dnf config-manager --add-repo https://download.docker.com/linux/rhel/docker-ce.repo
sudo dnf install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin # 安装引擎及插件
sudo systemctl enable --now docker          # 新安装环境启动并设置开机自启
sudo docker version                         # 确认Client和Server可用
sudo docker compose version                 # 确认Compose插件可用

示例：安装时核对包源与GPG指纹。DNF5的源管理语法与DNF4可能不同，按系统和官方版本说明选择；CentOS 7不适用此清单，也不应通过关闭GPG校验或换成Stream源来强行安装。

参考 CentOS安装说明 与 RHEL安装说明。

已有Docker，只缺 docker compose 或普通用户无权限

先确认Docker来源及官方软件源已经正确配置，再按系统仅安装插件：

# Ubuntu / Debian，已有匹配Docker官方源
sudo apt-get update                         # 更新现有批准源的包索引
sudo apt-get install docker-compose-plugin  # 仅补装匹配的Compose插件
# RHEL系，已有匹配Docker官方源时改选下面这一条
# sudo dnf install docker-compose-plugin
sudo docker compose version                 # 安装后核对插件版本

示例：系统仓库安装的 docker.io 可能搭配发行版自己的Compose包，先查本机包来源，不混装官方与发行版整套运行时。无需为了使用Compose另装旧的 docker-compose Python工具。

sudo docker ps             # 已获授权时单条sudo
sudo docker compose version # 同一管理身份下核对插件是否可用

示例：普通用户无Docker socket权限可使用获准的sudo或已部署的rootless模式。加入docker组相当于授予很高的主机权限，需要管理员明确授权，不把socket改成777。详见 Docker非root使用说明。

CentOS 7：维护已有Docker，先确认引擎与Compose版本

CentOS 7已结束维护，Docker当前CentOS安装说明面向受支持的Stream版本，不能套用到7。下面用于盘点已有运行环境；新部署先迁移到受维护系统，再按上面的对应步骤安装。

cat /etc/centos-release         # 确认系统版本
uname -r                       # 记录实际运行内核，不代表全部功能均可用
rpm -q docker-ce docker-ce-cli containerd.io docker-compose-plugin # 查询已安装官方RPM，其他来源可能查不到
command -v docker docker-compose # 找到已有程序，二进制安装不一定在RPM记录中
sudo docker version            # 分别检查Client与Server，连接失败不等于没有安装
sudo docker info               # 检查存储驱动、Docker根目录及cgroup信息
sudo docker compose version    # 有V2插件时查看版本；缺少插件时报错，继续查现状
docker-compose version         # 仅有旧独立程序时查询它的版本
yum --showduplicates list docker-ce docker-compose-plugin # 查询已有批准源的候选，不执行升级

示例：只有Compose V1时常用命令入口为 docker-compose ps、docker-compose logs --tail=100，本文V2特有选项不能直接照搬。V1已停止维护；迁移前备份compose文件及数据，核对项目名、容器名称、网络与依赖语义，在测试环境验证，不直接替换可执行文件重建线上容器。

没有适用插件或候选包时，保留原运行时，安排升级迁移；不能混装Stream RPM、关闭签名或下载最新版插件来碰运气。旧引擎不支持 docker context 等命令时先查 docker --help，用实际支持的命令查询当前目标，不因排查而升级整套引擎。cgroup v1限制与计数见性能排查。

docker version             # 客户端和服务端版本
docker info                # 存储驱动、日志驱动、根目录等
docker compose version     # Compose 插件版本
docker context ls          # 可用连接目标
docker context show        # 当前目标
docker system df           # 镜像、容器、卷、缓存占用
docker system df -v        # 详细占用

示例：docker version 只有 Client、Server 连接失败时，检查 daemon、socket 权限和当前 context。远程 context 的操作作用于远端，执行删除前尤其需要核对。

systemctl status docker --no-pager -l          # 系统安装的 Docker 服务状态
sudo journalctl -u docker -b -n 100 --no-pager # 本次开机 daemon 日志
docker --help                               # CLI 帮助
docker run --help                           # 当前版本支持的启动选项

示例：rootless Docker 的服务可能属于用户级 systemd，需使用对应用户的 systemctl --user。不要因命令权限不足就把 Docker socket 改成所有人可写；Docker 控制权限本身具有很高的主机权限。

2. 容器列表、筛选和状态

docker ps                                      # 正在运行的容器
docker ps -a                                   # 包含已退出容器
docker ps --filter name=demo-web                # 名称匹配
docker ps -a --filter status=exited             # 退出容器
docker ps --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}' # 按名称、状态和端口显示摘要
docker inspect demo-web                        # 完整配置和状态
docker inspect -f '{{json .State}}' demo-web     # 状态、退出码、健康检查

示例：Up 表示主进程存活；配置了健康检查才会有 healthy/unhealthy。Exited (137) 可能涉及 SIGKILL，但不能仅凭退出码断言 OOM，还要核对 OOMKilled 和主机日志。inspect 可能包含环境变量中的凭证，分享前脱敏。

3. 创建并运行容器

# 新建演示容器：回环8080映射容器80，限制资源并配置日志轮转；先确认名称和端口未占用。
docker run -d --name demo-web \
  --restart unless-stopped \
  -p 127.0.0.1:8080:80 \
  --memory 256m --cpus 1 \
  --log-driver json-file \
  --log-opt max-size=10m --log-opt max-file=3 \
  nginx:1.28

示例：创建名为 demo-web 的 Nginx，主机回环8080映射到容器80，最多1个CPU配额和256MB内存，控制台日志按文件滚动。镜像标签需使用已批准且可用的版本，精确复现可固定 digest。这里的资源值仅为演示。

-p 8080:80 通常向全部主机地址发布，开放范围与只绑定127.0.0.1不同；还要核对 Docker 的转发规则和实际外部可达性。不要仅凭主机防火墙界面认定端口被拦截。

docker start demo-web          # 启动已创建的容器
docker stop -t 30 demo-web     # 优雅停止，超时后可能强制结束
docker restart -t 30 demo-web  # 重启，会中断连接
docker update --restart unless-stopped demo-web # 修改重启策略

示例：start 复用原容器配置，不会采用新的镜像或新的端口参数；要修改这些配置，需要重建容器。上述为备选操作，不要一起执行。

创建前用 docker ps -a --filter name=demo-web确认名称是否已被旧容器占用，用 sudo ss -lntp 'sport = :8080'核对监听。名称冲突时先查旧容器用途，不直接强删；端口占用时核对归属或选择其他获准端口。启动后执行下面的只读检查：

docker ps -a --filter name=demo-web          # 查看容器是否存活、有无持续重启
docker logs --tail 50 demo-web               # 核对入口进程和配置错误
docker port demo-web                        # 查看实际发布地址及端口
curl -I --connect-timeout 3 --max-time 5 http://127.0.0.1:8080/ # 从主机验证新连接

示例：看到 127.0.0.1:8080映射且请求返回预期网页响应，才继续验证实际业务。创建失败时先查错误，不反复运行同一个run；已经创建但退出的容器仍占用名称。

4. 日志、事件和退出原因

docker logs --tail 100 --timestamps demo-web       # 最近100行及时间
docker logs --since 30m --tail 300 demo-web        # 最近30分钟
docker logs -f --tail 100 demo-web                # 实时跟踪
docker inspect -f '{{.State.ExitCode}} {{.State.OOMKilled}} {{.State.Error}}' demo-web # 退出码、OOM标记及引擎错误
docker events --since 30m --filter container=demo-web # 事件流

示例：日志中查应用异常，inspect 中查退出码和 OOM 标记，events 中查 die、restart 等事件。事件不是永久审计记录，也不能单独证明是谁操作了容器。logs -f、events 按 Ctrl+C 退出查看，不会停止容器。

先查 docker ps -a → inspect状态 → 最近日志 → 同时段daemon/内核日志。例如 OOMKilled=true需要继续核对容器限制和主机内存；退出码1应先读应用报错，不能用增大内存统一处理。镜像主进程正常结束也会退出容器，-d不会把已结束的程序自动变成常驻服务。

docker logs 主要查看标准输出与错误，能否读取取决于日志驱动及相关配置；应用写在容器文件系统里的日志要另查。不要手工截断 Docker 内部日志文件，优先配置日志轮转。

5. 进入容器、执行命令与复制文件

docker exec -it demo-web sh                  # 进入已有容器
docker exec demo-web nginx -t                # 容器内执行一次配置校验
docker exec -u 0 -it demo-web sh             # 确有需要时使用容器内 root
docker cp demo-web:/etc/nginx/nginx.conf ./nginx.conf # 复制到本机
docker cp ./nginx.conf demo-web:/tmp/nginx.conf       # 复制到容器临时位置

示例：精简镜像不一定有 bash、curl、ps，可先尝试 sh；distroless 镜像可能连 shell 也没有。复制到 /tmp 不会自动应用配置；修改前需核对挂载与原配置。

exec只适用于正在运行的容器，已退出时先查看logs与inspect，不为了进入shell反复启动异常服务。需要重定向或管道时，应明确让容器内shell解释，例如 docker exec demo-web sh -c 'nginx -t 2>&1'；没有shell的镜像不能使用这一写法。

exec 创建的交互 shell 中执行 exit 通常只退出该 shell。不要与 attach 混淆：attach 连接主进程的输入输出，Ctrl+C 可能给主进程发送信号；默认脱离快捷键为 Ctrl+P 再 Ctrl+Q。

容器内临时修改可能在重建时消失；长期配置写进镜像、挂载文件或 Compose 清单。

6. CPU、内存和磁盘排查

docker stats --no-stream                          # 一次性资源快照
docker stats demo-web                             # 实时资源
docker top demo-web                               # 容器进程
docker inspect -f '{{.HostConfig.Memory}} {{.HostConfig.NanoCpus}}' demo-web # 内存字节上限及CPU核数×10^9
docker ps -s                                      # 可写层大小
docker diff demo-web                              # 可写层变更
docker system df -v                               # Docker 存储占用

示例：容器内存接近限制时结合 OOMKilled 排查。ps -s 的可写层不包括全部挂载卷和日志占用，磁盘满时还需查主机文件系统、卷、日志和构建缓存。

docker info --format '{{.DockerRootDir}}'     # 找到本daemon数据目录，远程context返回的是远端路径
df -h                                      # 在对应daemon主机查看文件系统空间
df -i                                      # 检查inode是否耗尽，避免只看剩余GB
docker inspect -f '{{.HostConfig.LogConfig.Type}} {{.LogPath}}' demo-web # 查日志驱动与引擎记录的日志路径

示例：Memory=268435456为256MiB，NanoCpus=1000000000为1个CPU配额；字段为0时通常没有通过对应字段设置限制，还需核对其他配额和父cgroup。docker stats的内存展示可能扣除部分缓存，不能简单等同进程RSS；CPU高需结合容器进程和应用采样。实时stats按Ctrl+C退出。不要直接删除 /var/lib/docker、修改引擎内部元数据或截断活动日志来腾空间。

7. 镜像拉取、查看、构建和推送

7.1 在线拉取、构建与仓库发布

docker image ls                                   # 本地镜像
docker pull nginx:1.28                            # 拉取指定标签
docker image inspect nginx:1.28                   # digest、架构等
docker history nginx:1.28                         # 镜像层历史
docker build --pull -t demo-api:1.0.0 .            # 当前目录 Dockerfile 构建
docker tag demo-api:1.0.0 registry.example.com/team/demo-api:1.0.0 # 给同一镜像增加仓库标签，不复制业务数据
docker login registry.example.com                 # 按提示认证
docker push registry.example.com/team/demo-api:1.0.0 # 上传镜像，需已认证且有推送权限
docker logout registry.example.com                # 退出仓库登录

示例：构建后给同一镜像加仓库标签再推送。推送前确认仓库和权限；不要把密码放进 -p 参数或 Dockerfile。构建上下文中的凭证应通过 .dockerignore 排除，构建秘密使用专门的 secret 挂载。

构建示例以当前目录有正确Dockerfile及业务文件为前提。--pull会尝试更新基础镜像，Dockerfile中的安装命令也可能联网；“目标服务器离线运行”不等于“构建过程无需网络”。需要可复现发布时，用批准的固定版本或digest，并保留源码提交、Dockerfile、构建参数和镜像ID。

7.2 离线部署前，分清要打包的内容和平台

完整顺序：目标机确认运行环境与平台 → 联网机拉取或构建目标镜像 → 导出镜像包及校验清单 → 传输 → 目标机校验 → load → 核对镜像 → 按原运行参数创建容器 → 验证或回退。

内容 docker image save会包含吗 还需要准备什么
已选镜像的层及镜像配置、标签 包含 导出时明确写出需要的完整镜像名
当前容器可写层的临时修改 不包含 将必要修改纳入Dockerfile，重新构建
命名卷、bind mount中的数据 不包含 按第9项单独备份、传输和恢复
Compose清单、运行参数、外置配置 不包含 保存清单、环境来源、挂载文件和目录结构
数据库、证书私钥、外部服务 不包含 使用对应备份及安全交付方式，核对目标依赖可达
Docker Engine、Compose插件 不包含 目标机预先安装兼容的运行环境

先在目标服务器检查，普通用户需要相应Docker及SSH权限：

uname -m                                   # 查看目标机CPU架构
docker version                             # 确认Server可连接及引擎版本
docker info --format '{{.OSType}}/{{.Architecture}}' # 核对目标daemon的系统和架构
docker compose version                     # 使用Compose部署时确认插件版本
df -h                                      # 检查接收目录及Docker数据盘的可用空间
docker info --format '{{.DockerRootDir}}'    # 找到镜像实际加载到哪个数据盘

示例：Linux x86_64通常对应 linux/amd64，aarch64通常对应 linux/arm64。Docker Desktop需确认使用Linux容器模式，不能拿Windows容器镜像交给Linux引擎。包大小不是最终占用，加载、解压和新旧版本并存都需要空间。

联网机与目标机架构不同时，拉取目标平台，例如 docker pull --platform linux/amd64 nginx:1.28。自有应用可在已配置目标平台构建能力的Buildx上执行 docker buildx build --platform linux/amd64 --load -t demo-api:1.0.0 .，再检查本地镜像。--load用于把单平台结果装入本地镜像存储，构建缓存里有结果不等于 docker image save能找到；跨平台构建还可能需要模拟器或原生构建节点。Buildx构建说明

下面采用较通用的save/load方式，不依赖较新API才有的 save/load --platform。save只导出本地已有内容，不会自动替你下载其他平台；多平台镜像存储和旧引擎之间也需先做兼容性验证。

7.3 联网机导出镜像、生成校验和并上传

以下演示把Nginx镜像交付给 linux/amd64目标机。nginx:1.28为示例标签，实际应替换为本次批准的具体镜像；为每轮交付建独立空目录，不覆盖上轮回退包。

mkdir ./offline-demo && cd ./offline-demo    # 在当前可写目录创建本轮工作目录；已存在则先停止核对
docker pull --platform linux/amd64 nginx:1.28 # 联网机拉取目标平台镜像，失败不继续打包
docker image inspect --format '{{.Id}} {{.Os}}/{{.Architecture}}' nginx:1.28 # 确认镜像ID及平台
docker image inspect --format '{{.Id}} {{.Os}}/{{.Architecture}}' nginx:1.28 > image-info.txt # 记录交付镜像身份
docker image save -o nginx-1.28.tar nginx:1.28 # 把已确认的镜像及标签写成tar文件
ls -lh nginx-1.28.tar                       # 确认文件存在且有合理大小
sha256sum nginx-1.28.tar image-info.txt > SHA256SUMS # 生成本轮文件校验清单
sha256sum -c SHA256SUMS                     # 联网机先检查自己的交付文件

示例校验输出为 nginx-1.28.tar: OK和 image-info.txt: OK；镜像信息形如 sha256:... linux/amd64。>会创建或覆盖右侧文件；导出使用 -o直接写包，不把终端输出当成镜像文件。包内容和来源仍需可信，SHA256只检查文件是否一致。

需要压缩时，可在确认tar导出成功后使用 gzip -c nginx-1.28.tar > nginx-1.28.tar.gz将压缩结果写入新文件并保留原tar；随后应对实际传输的 .tar.gz重新生成清单，上传和加载也改为该文件。目标机 docker image load -i nginx-1.28.tar.gz可读取gzip压缩包。不要只改扩展名冒充压缩，也不要校验tar却上传另一个未经校验的文件。save与load说明。

在联网机执行传输，地址、用户和SSH端口按实际授权替换。先确认目标SSH主机指纹，不关闭主机身份校验：

ssh -p 22 ops@192.0.2.20 'mkdir -p ~/offline-demo' # 在目标登录用户家目录准备接收目录
scp -P 22 nginx-1.28.tar image-info.txt SHA256SUMS ops@192.0.2.20:~/offline-demo/ # 上传镜像、身份记录与校验清单
ssh -p 22 ops@192.0.2.20                    # 登录目标机，下面的加载命令改在这里执行

ssh -p为小写p，scp -P为大写P。每轮使用独立接收目录，目录已有文件时先核对版本；传输完成不代表校验通过。目标目录无权限时先用用户自己的接收目录，再由获准管理员放到部署位置，不把目录改成777。

缺少scp、校验或压缩工具，以及Windows上传方式 
command -v ssh scp sha256sum tar gzip        # 查询当前机器是否具备传输、校验和归档工具

在能访问批准软件源的机器上，按系统安装缺失包：

# Ubuntu / Debian：只安装缺少的工具。
sudo apt-get update                         # 更新批准源索引
sudo apt-get install openssh-client coreutils tar gzip # scp/ssh、SHA256与归档工具

# 使用dnf的RHEL系；已有CentOS 7改用其批准仓库和yum，不套用Stream包。
sudo dnf install openssh-clients coreutils tar gzip # 安装本机匹配的工具包
# sudo yum install openssh-clients coreutils tar gzip # CentOS 7有匹配候选时才选择执行

离线目标机缺软件包时，需事先准备匹配发行版、架构及依赖的离线安装介质，镜像tar不会提供这些宿主机工具。

Windows已启用OpenSSH客户端时，可以在PowerShell进入交付文件目录后执行同样的 scp -P 22 ...上传。也可使用MobaXterm的SFTP面板上传上述三个文件到同一目录；仍然在Linux目标机执行 sha256sum -c SHA256SUMS。不要通过终端复制粘贴tar二进制内容。Windows上需核对Docker目标为Linux平台；本文的Bash数组和shell语法不能原样贴进PowerShell。

7.4 目标服务器校验、加载和离线启动

以下在目标服务器执行；先确认接收文件已齐全，且本机Docker环境符合7.2的检查结果：

cd ~/offline-demo                           # 进入本轮实际接收目录
sha256sum -c SHA256SUMS                      # 必须所有文件均为OK，失败先重传，不继续load
cat image-info.txt                          # 查看预期镜像ID及平台，不执行此文件内容
docker image load -i nginx-1.28.tar          # 把镜像加载进当前daemon，不会自动启动或更新容器
docker image inspect --format '{{.Id}} {{.Os}}/{{.Architecture}}' nginx:1.28 # 与交付身份记录逐项对比
docker image ls nginx:1.28                   # 确认完整名称和标签都存在

load通常输出 Loaded image: nginx:1.28。检查安装后镜像的ID、OS和架构与 image-info.txt一致。镜像ID、仓库manifest digest、tar文件SHA256是不同概念，不能把三者当作同一串哈希；离线包加载后也不保证保留所有远端仓库digest元数据。

加载相同标签可能将该标签指向另一份镜像，但不会更新已运行的容器。已有服务升级先按第13项保存旧容器配置、镜像ID和回退版本，不能因为load成功就认为业务已经切换。

下面仅在没有同名演示容器、回环8080端口空闲时运行；若第3项已启动过同名容器，改用其他明确名称及端口或按原部署方式更新：

docker ps -a --filter name=demo-web          # 核对名称占用和旧容器用途
sudo ss -lntp 'sport = :8080'                # 核对主机端口，存在其他监听先处理冲突
# 只用本地已加载镜像创建演示容器，不访问镜像仓库；新连接仅绑定主机回环地址。
docker run -d --name demo-web --pull=never \
  --restart unless-stopped \
  -p 127.0.0.1:8080:80 \
  --log-driver json-file --log-opt max-size=10m --log-opt max-file=3 \
  nginx:1.28
docker ps -a --filter name=demo-web          # 查看是否运行或异常退出
docker logs --tail 100 demo-web              # 查看启动错误
curl -I --connect-timeout 3 --max-time 5 http://127.0.0.1:8080/ # 验证目标机本地HTTP响应

--pull=never使镜像缺失时直接报错，避免离线环境等待拉取；它不禁止容器中的应用联网，数据库、DNS、许可证和启动脚本下载等运行依赖仍要事先准备。命令支持情况先查本机 docker run --help；旧版本不支持时应使用已验证的兼容流程，不能忽略参数后假定不会联网。

示例：端口映射正确、日志无配置错误、本机返回预期Nginx页面后，再查实际代理、域名和业务路径。其他机器不能直接访问目标机的127.0.0.1；需要对外服务时按批准的监听地址及访问规则发布，不为排障随意改为全网开放。

7.5 多个镜像、离线构建和容器导出的区别

多个已在本地核验的镜像可合并保存，例如 docker image save -o stack-images.tar demo-api:1.0.0 redis:7.4；目标机执行 docker image load -i stack-images.tar，再逐个检查名称和平台。Compose应按实际生效清单列出全部镜像，完整流程见13.2，不能只打包主应用却漏掉数据库、缓存或工具服务。

save/load用于迁移镜像；export/import主要处理容器文件系统，不会自动保留完整镜像历史、原运行配置和挂载卷数据，不能作为同等替代。也不要用 docker commit替代可复现构建，挂载卷不会因此自动打入镜像。

真正的离线构建还要准备Dockerfile引用的基础镜像、构建前端、语言依赖、系统包、BuildKit能力与构建上下文；目标机已有业务运行镜像，并不代表重新build就无需联网。只有离线运行需求时，优先在具备构建条件的机器完成构建，再save/load交付。

8. 网络、DNS 与端口

docker network ls                                     # 网络列表
docker network inspect demo-net                       # 网段、成员
docker port demo-web                                  # 主机发布端口
docker inspect -f '{{json .NetworkSettings.Networks}}' demo-web # 查看容器实际加入的网络和地址
docker exec demo-web cat /etc/resolv.conf              # 容器 DNS 配置
curl -I --connect-timeout 3 --max-time 5 http://127.0.0.1:8080/ # 从宿主机检查发布端口

示例：同一自定义网络中的服务通常用容器名或服务名通信；容器内的 localhost 指容器自身。容器服务需监听可被其他容器访问的地址，不应只绑定容器内127.0.0.1。

docker network create demo-net             # 新建用户网络
docker network connect demo-net demo-web   # 把容器加入网络，会改变连通范围
docker network disconnect demo-net demo-web # 从网络移除，会影响连接

示例：只在确认拓扑后执行连接操作。排查顺序是容器进程 → 容器监听 → 网络成员 → DNS → 主机端口 → 外部规则 → 应用认证；不要通过反复重启代替定位。

现象 下一步怎么查 如何判断
本机发布端口也不通 docker port、容器日志、主机监听与转发规则 先区分没发布、进程没启动、应用监听错地址
本机能访问，外部不通 发布地址、路由、防火墙、云安全组和前置代理 绑定127.0.0.1时本来就仅限本机，不直接放开全部来源
服务名无法解析 两端是否在同一用户网络、实际Compose服务名 默认bridge不等同自定义网络的服务发现能力
解析正常却连接拒绝 目标应用端口、监听地址、启动就绪与日志 容器间使用容器端口，通常不是宿主机映射端口
外部DNS或HTTPS失败 容器resolv.conf、出口、代理及证书链 不以写死公网DNS、关闭TLS验证作为通用修复

容器没有curl或诊断工具时，优先使用应用自检、主机已有工具或获准的调试镜像；离线环境先按第7项准备调试镜像，不在生产容器临时联网安装一堆软件。EXPOSE 80只是镜像元数据，不能代替 -p发布端口。

9. 挂载卷与持久化

docker volume ls                                 # 命名卷列表
docker volume inspect demo-data                  # 卷属性
docker inspect -f '{{json .Mounts}}' demo-web      # 实际挂载来源、目标、读写模式
docker volume create demo-data                   # 创建命名卷

示例：命名卷用于持久数据；bind mount 使用明确的宿主机路径。卷挂载到原有非空目录时会遮盖镜像里的相应内容，不能看到文件不一定等于数据已删除。

只读挂载的启动示例：

# 将已经存在的主机静态目录只读挂载；使用独立名称和空闲回环端口。
docker run -d --name demo-static \
  -p 127.0.0.1:8081:80 \
  --mount type=bind,src=/opt/demo/html,dst=/usr/share/nginx/html,readonly \
  nginx:1.28

示例：主机 /opt/demo/html 必须存在。容器可以读取但不能通过该挂载写入静态文件。数据库挂载还应核对 UID/GID、SELinux 标签和备份策略，不能直接用全目录 chmod 777 解决。

卷备份示例

以下用于普通文件卷，先停止或排空所有写入者，确认业务允许一致性备份。命令在Docker daemon所在主机执行；远程context不会替你把CLI本地目录上传到远端。离线环境先按第7项加载同平台的辅助镜像。

docker volume inspect demo-data             # 确认备份的是实际业务卷，查不到先停止，不让run自动建空卷
BACKUP_DIR=$(mktemp -d "$PWD/volume-backup.XXXXXXXX") # 创建唯一的本轮备份目录，失败不继续
printf '%s\n' "$BACKUP_DIR"                 # 记录备份位置，恢复时使用同一目录
docker image inspect alpine:3.22            # 确认辅助镜像已准备，离线机器不能临时拉取
# 启动临时辅助容器：源卷只读挂载，归档写到宿主机本轮备份目录。
docker run --rm --pull=never \
  --mount type=volume,src=demo-data,dst=/data,readonly \
  --mount type=bind,src="$BACKUP_DIR",dst=/backup \
  alpine:3.22 tar -czf /backup/demo-data.tgz -C /data .
gzip -t "$BACKUP_DIR/demo-data.tgz"          # 完整检查gzip数据流，失败不把该归档视为有效备份
tar -tzf "$BACKUP_DIR/demo-data.tgz" | head # 预览归档路径，默认最多显示10行
sha256sum "$BACKUP_DIR/demo-data.tgz"        # 记录备份文件哈希，传输后再次对比

示例：辅助容器退出后归档仍在主机备份目录。在线准备机缺少辅助镜像时先执行 docker pull alpine:3.22并核对平台；缺少宿主机tar/gzip/SHA256工具见7.3的折叠说明。数据库运行中直接打包数据目录通常不能保证一致性，应优先使用数据库备份工具或受支持的快照流程。

tar -tzf ... | head 中的 | 把归档文件列表交给 head，默认只显示前10行；这只用于快速查看，不等于已经完整校验或恢复验证了整个备份。

恢复前先验证备份，使用新的空卷演练，不覆盖已有生产数据：

RESTORE_VOLUME="demo-data-restore-$(date +%Y%m%d-%H%M%S)" # 选新的恢复卷名，确认同名卷不存在
docker volume create "$RESTORE_VOLUME"     # 创建独立空卷；原业务卷不覆盖
# 只读挂载归档并解压到新卷，辅助镜像须已在本地准备。
docker run --rm --pull=never \
  --mount type=volume,src="$RESTORE_VOLUME",dst=/data \
  --mount type=bind,src="$BACKUP_DIR",dst=/backup,readonly \
  alpine:3.22 tar -xzf /backup/demo-data.tgz -C /data
docker volume inspect "$RESTORE_VOLUME"    # 确认恢复目标和实际卷属性

示例：恢复后用隔离的兼容应用验证文件数量、关键内容、UID/GID和业务读写，确认无误才安排切换；不能仅凭tar退出码认定业务恢复成功。新终端先把 BACKUP_DIR重新设为实际备份目录。文件系统ACL、扩展属性等额外要求还需匹配工具和备份格式；数据库逻辑备份按数据库自己的恢复流程验证。

10. Compose 的文件与项目范围

docker compose ls                                 # Compose 项目列表
docker compose -p demo -f /opt/demo/compose.yaml config -q # 校验
docker compose -p demo -f /opt/demo/compose.yaml config --services # 服务名
docker compose -p demo -f /opt/demo/compose.yaml config --images   # 镜像

示例：使用固定 -p demo 与 -f /opt/demo/compose.yaml，避免在不同目录意外操作另一套项目。完整 config 会展开环境变量，可能显示敏感值，分享时不要直接贴出原始结果。

下面的 Compose 命令均假设已进入 /opt/demo，使用该目录的 compose.yaml 和固定项目名 demo；跨目录、自动化或有多个清单时保留完整的 -p/-f/--env-file参数，每轮操作保持一致。

最小示例文件：

services:
  web:
    image: nginx:1.28
    ports:
      - "127.0.0.1:8080:80"
    restart: unless-stopped
    volumes:
      - ./html:/usr/share/nginx/html:ro
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"

各字段：image为要运行的镜像名；ports为主机回环8080到容器80；restart为容器重启策略；volumes把清单目录下的html只读挂载；logging限制新容器的控制台日志文件大小与份数。

首次新建演示项目时，在已获准且可写的项目目录保存上述清单为 compose.yaml，再准备网页。已有站点不覆盖现有index：

cd /opt/demo                               # 进入管理员准备且允许访问的项目目录
mkdir -p html                              # 准备bind mount源目录，避免误挂空目录
printf '%s\n' '<!doctype html><meta charset="utf-8"><h1>demo ready</h1>' > html/index.html # 仅新建演示站点写入验证页面
docker compose -p demo -f compose.yaml config -q # 校验清单语法、变量和结构
docker compose -p demo -f compose.yaml config --images # 记录实际引用的镜像名

示例：该清单不需要旧式顶层 version字段。web是服务名，不要求容器名也叫web；不要凭猜测名字操作容器，使用 docker compose -p demo ps查询。语法检查不会验证所有主机文件权限、外部服务就绪或业务正确性。

11. Compose 启动、停止与重建

docker compose -p demo config -q           # 先校验
docker compose -p demo up -d               # 创建/按配置重建并后台运行
docker compose -p demo ps -a               # 查看项目内容器
docker compose -p demo start web           # 启动已存在的服务容器
docker compose -p demo stop -t 30 web       # 停止，保留容器
docker compose -p demo restart web         # 重启原容器
docker compose -p demo up -d --no-deps web  # 只更新目标服务，不连带启动依赖

示例：修改环境变量、端口或镜像后，使用 up -d 应用变化；restart 不会重新读取这些变更来重建容器。--no-deps 只在依赖已经满足时使用。

首次启动建议按 config -q → 准备镜像和挂载文件 → up -d → ps -a → logs → 主机入口 → 实际业务执行。命令返回容器ID或状态为running不等于业务就绪；镜像有健康检查时结合healthy，否则用实际接口检查。前台 docker compose up按Ctrl+C可能停止这一组服务，后台启动使用 -d；logs -f退出仅停止看日志。

docker compose -p demo up -d --force-recreate web # 强制重建，会替换容器
docker compose -p demo down                      # 删除项目容器和非外部网络

示例：down 会中断整个项目。默认不删除命名卷，但容器可写层会丢失，匿名卷再次启动时也未必自动复用；重要数据应明确挂载。不要为查看状态执行 down。

12. Compose 日志、执行和资源

docker compose -p demo logs --tail 100 --timestamps web # 最近日志
docker compose -p demo logs -f --since 10m web           # 实时日志
docker compose -p demo exec web sh                      # 进入运行容器
docker compose -p demo exec -T web nginx -t              # 无TTY执行，适合脚本
docker compose -p demo top                              # 进程
docker compose -p demo port web 80                       # 查询映射
docker compose -p demo run --rm --no-deps web nginx -t   # 一次性新容器

示例：exec 在原容器执行；run 创建一次性容器，默认不发布服务端口，仍可能访问该服务声明的卷和网络，执行写操作前应核对影响。资源检查可取 ps -q 返回的容器ID再用 docker stats。

docker compose -p demo ps -q web             # 查询实际运行的web容器ID，不假设其名称
docker stats --no-stream 容器ID              # 将上一条查询的真实ID代入，查看一次资源快照
curl -I --connect-timeout 3 --max-time 5 http://127.0.0.1:8080/ # 核对示例主机端口的响应

ps -q可能返回多个副本或没有结果；没有运行容器时先用 ps -a查退出状态，不直接把空命令替换传给stats，因为无容器参数的stats会展示全部运行容器。

13. Compose 更新、回滚和环境

13.1 在线更新和配置来源

docker compose -p demo pull web             # 仅拉取，不更新运行容器
docker compose -p demo up -d --no-deps web   # 按新镜像重建目标服务
docker compose -p demo logs --tail 100 web   # 核对启动日志
docker compose -p demo ps                   # 查看状态

示例：更新前保留原清单、镜像 digest 和数据备份。失败时把清单改回原镜像再 up -d --no-deps web；镜像回滚不会回滚数据库和挂载配置。

docker compose -p demo build --pull web                 # 本地构建
docker compose -p demo up -d --build web                # 构建并应用
docker compose -p demo --env-file .env.prod config -q    # 指定变量来源
docker compose -p demo -f compose.yaml -f compose.prod.yaml config -q # 合并校验
docker compose -p demo --profile tools config --services # 配置指定 profile

示例：多文件顺序会影响最终配置，后文件按 Compose 合并规则覆盖或补充；相对路径通常基于第一个清单的位置。.env 常用于清单插值，不代表所有变量自动进入容器；容器环境需通过 environment 或 env_file 等声明。

--env-file显式指定清单插值来源，但已有shell变量仍可能覆盖同名值。需要验证最终镜像名时查看 config --images，配置中关键变量可用 ${APP_IMAGE:?请设置APP_IMAGE}要求非空。完整config和inspect可能展开密码，保存在受控目录并限制权限，不放进公开文档或普通发布日志。

13.2 Compose整套离线打包、传输与启动

本节以第10项的最小静态站点为完整例子：compose.yaml引用 nginx:1.28，挂载同目录的 html/。两端Docker平台必须匹配，目标机已安装兼容的Engine和Compose，端口与项目名已确认。所有镜像都在准备机先拉取或构建，目标机不build、不pull。

准备机：先核对实际清单。 以下假设准备机上的 /opt/demo就是本轮部署内容，不从正在变化的目录中途打包：

cd /opt/demo                               # 进入本轮完整项目目录
docker compose -p demo -f compose.yaml config -q # 先验证清单和变量
docker compose -p demo -f compose.yaml config --services # 确认本轮服务范围
docker compose -p demo -f compose.yaml config --images # 确认所有最终镜像名及标签
docker compose -p demo -f compose.yaml pull  # 联网准备机拉取本例镜像，失败先处理

真实项目若包含 build:，先在有构建条件的机器构建并为每个服务设置明确 image:；不要指望目标机补构建。多文件、profile和环境文件必须在列镜像、拉取、校验和启动时保持一致。准备机架构不同于目标机时，按7.2给每项服务明确匹配的 platform并取得对应镜像；不能只改平台字段却没有对应镜像。

准备机：制作交付包。 本例没有额外环境文件或密钥；下面只复制明确需要的清单与网页，不整目录打包源码、日志和凭据：

BUNDLE_DIR=$(mktemp -d "$PWD/offline-release.XXXXXXXX") # 为本轮创建唯一交付目录
cp -p compose.yaml "$BUNDLE_DIR/compose.yaml" # 复制已校验的部署清单
cp -a html "$BUNDLE_DIR/html"               # 复制本例静态文件，保留清单中的相对目录
docker compose -p demo -f compose.yaml config --images > "$BUNDLE_DIR/images.txt" # 输出本轮镜像清单
sort -u -o "$BUNDLE_DIR/images.txt" "$BUNDLE_DIR/images.txt" # 去重，保留完整镜像名
mapfile -t OFFLINE_IMAGES < "$BUNDLE_DIR/images.txt" # Bash按行读入数组，不进行空格拆分
test "${#OFFLINE_IMAGES[@]}" -gt 0           # 必须至少有一个镜像，失败先检查清单和profile
docker image inspect --format '{{.Id}} {{.Os}}/{{.Architecture}} {{json .RepoTags}}' "${OFFLINE_IMAGES[@]}" # 全部镜像必须存在且平台正确
docker image save -o "$BUNDLE_DIR/images.tar" "${OFFLINE_IMAGES[@]}" # 合并保存本轮全部已核验镜像
docker image inspect --format '{{.Id}} {{.Os}}/{{.Architecture}} {{json .RepoTags}}' "${OFFLINE_IMAGES[@]}" > "$BUNDLE_DIR/image-info.txt" # 保存身份记录
cd "$BUNDLE_DIR"                           # 清单使用相对文件名，便于目标机原样校验
find compose.yaml html images.txt image-info.txt images.tar -type f -exec sha256sum {} + > SHA256SUMS # 校验清单和网页也纳入交付校验
sha256sum -c SHA256SUMS                     # 发送前确认每一项均为OK
printf '%s\n' "$BUNDLE_DIR"                 # 记录本轮交付目录绝对路径

mapfile和数组语法用于Bash，不能直接贴进PowerShell或sh。"${OFFLINE_IMAGES[@]}"逐项传递镜像名；不是只把images.txt本身当成镜像。任一检查、复制或save失败时停在该步骤，不生成看似完整的交付包。

清单中的其他bind mount、配置、secret文件要单独确认内容、权限和交付路径；符号链接的目标不会被 cp -a自动带上。命名卷数据不在本包内，按第9项迁移；外部网络、外部卷和依赖服务需在目标预先准备。包含环境文件时按同一参数验证，秘密通过受控方式交付，不把展开后的完整config随意打包或公开。

准备机：传输整个交付目录。 记录本轮目录名，例如 offline-release.A1b2C3d4，不要与之前的单镜像 offline-demo目录混淆：

ssh -p 22 ops@192.0.2.20 'mkdir -p ~/releases' # 在目标用户家目录准备交付父目录
scp -P 22 -r "$BUNDLE_DIR" ops@192.0.2.20:~/releases/ # 递归上传本轮目录，保留内部相对结构

目标机：先校验、加载，再启动。 下例将目录名替换为实际上传结果，不把演示目录名当作固定值：

cd ~/releases/offline-release.A1b2C3d4        # 进入本轮实际接收目录，后续保持同一终端
sha256sum -c SHA256SUMS                      # 所有文件均为OK才继续
docker compose -p demo -f compose.yaml config -q # 在目标版本Compose上再次校验
docker compose -p demo -f compose.yaml config --images # 与images.txt逐项核对名称、标签和平台配置
docker image load -i images.tar             # 加载所有交付镜像，不会自动重建现有容器
mapfile -t OFFLINE_IMAGES < images.txt       # 读取交付镜像名
test "${#OFFLINE_IMAGES[@]}" -gt 0           # 空清单或读取失败时停止
docker image inspect --format '{{.Id}} {{.Os}}/{{.Architecture}} {{json .RepoTags}}' "${OFFLINE_IMAGES[@]}" # 与image-info.txt对比
docker compose -p demo -f compose.yaml up --help # 先确认当前版本支持--pull和--no-build
docker compose -p demo -f compose.yaml up -d --pull never --no-build # 只用本地镜像创建或更新本轮项目
docker compose -p demo -f compose.yaml ps -a # 核对全部服务是否运行，有无异常退出
docker compose -p demo -f compose.yaml logs --tail 100 # 查看本轮启动日志
curl -fsS --connect-timeout 3 --max-time 5 http://127.0.0.1:8080/ # 本例应能读到demo ready网页

示例成功表现：校验项全部OK，镜像身份与平台匹配，web运行，HTTP正文包含本例 demo ready；真实业务继续验收登录、接口与依赖。--pull never禁止拉取镜像，--no-build禁止构建；它们不会禁止应用本身联网。旧Compose不支持相关选项时，不直接去掉参数冒充离线部署，应先确认其受控兼容方案。Compose up选项

此处用交付目录直接运行适合新建演示站点；已有项目切换前必须保存运行版本，确认项目名仍是同一套，且清单全部配置完整。相对bind mount会随着发布目录改变指向；数据库和持久目录应使用明确稳定的宿主机路径、受控命名卷或外部卷，不放进每轮临时交付目录。默认命名卷还与项目名有关，不能随意换 -p造成业务连到空卷。

13.3 更新前留好回退版本，失败后按原参数恢复

以同一 /opt/demo/compose.yaml维护的web服务为例，其他服务不变。以下是维护窗口内的操作流程，不是整机零停机发布：

cd /opt/demo                               # 进入本次维护的原项目目录
DEPLOY_BACKUP=$(mktemp -d "$PWD/deploy-backup.XXXXXXXX") # 为本轮配置和镜像记录建独立目录
cp -p compose.yaml "$DEPLOY_BACKUP/compose.yaml" # 备份本轮修改前清单
docker compose -p demo -f compose.yaml config -q # 确认原清单有效
docker compose -p demo -f compose.yaml ps -q web # 查询当前web容器ID，多个副本时逐个记录

把刚刚查到的真实容器ID填入下面变量。这里应从运行容器的 .Image取得镜像ID，而不是只检查可能已被pull/load改变的标签：

RUNNING_WEB_ID='实际容器ID'                 # 替换为本轮确认的单个web容器ID
OLD_WEB_IMAGE=$(docker inspect -f '{{.Image}}' "$RUNNING_WEB_ID") # 读取当前容器真正使用的镜像ID
docker image inspect "$OLD_WEB_IMAGE"      # 确认该旧镜像仍存在，失败先停止更新
ROLLBACK_IMAGE="local/demo-web:rollback-$(date +%Y%m%d-%H%M%S)" # 给旧镜像准备独立保留标签
docker image tag "$OLD_WEB_IMAGE" "$ROLLBACK_IMAGE" # 固定回退引用，避免原标签被新load覆盖
printf '%s\n' "$ROLLBACK_IMAGE" > "$DEPLOY_BACKUP/rollback-image.txt" # 保存回退镜像名
docker image save -o "$DEPLOY_BACKUP/rollback-image.tar" "$ROLLBACK_IMAGE" # 需要磁盘或跨机恢复时保留旧镜像包

同时备份实际环境文件、挂载配置和需要恢复的数据，权限与秘密范围按部署约定处理。回退标签只能避免失去原标签，不能防止 image prune -a删除未被容器引用的旧镜像，所以观察期内保留归档，不执行无差别清理。

随后编辑原位置的清单，将web改为已批准的新镜像，在线环境先pull；离线环境按13.2校验并load本轮镜像后执行：

docker compose -p demo -f compose.yaml config -q # 修改后先检查语法和变量
docker compose -p demo -f compose.yaml up -d --no-deps --pull never --no-build web # 只更新已确认依赖正常的web
docker compose -p demo -f compose.yaml ps -a web # 确认当前状态
docker compose -p demo -f compose.yaml logs --tail 100 web # 核对新启动日志
curl -fsS --connect-timeout 3 --max-time 5 http://127.0.0.1:8080/ # 检查真实业务响应，路径按实际配置

回退时先保存失败日志，再恢复原清单路径及本轮备份中的环境/挂载配置。不要直接用备份子目录的compose.yaml启动，否则相对挂载路径可能变了。下面假设本次只改了该清单：

printf '%s\n' "$DEPLOY_BACKUP"              # 新终端先将变量恢复为本轮真实备份目录
cp -p "$DEPLOY_BACKUP/compose.yaml" ./compose.yaml # 在原位置恢复原清单，避免改变相对路径基准
cat "$DEPLOY_BACKUP/rollback-image.txt"     # 读取旧版本的固定回退标签

将原清单中web的 image设为记录的回退标签；旧镜像不在本地时，先从本轮 rollback-image.tar执行load，再验证：

docker compose -p demo -f compose.yaml config -q # 校验恢复后的清单
docker compose -p demo -f compose.yaml up -d --no-deps --pull never --no-build web # 按回退引用重建web
docker compose -p demo -f compose.yaml logs --tail 100 web # 检查恢复日志
curl -fsS --connect-timeout 3 --max-time 5 http://127.0.0.1:8080/ # 重做原版本业务验收

这会替换服务容器，可能中断请求；不先down整个项目，不使用 down -v回滚。数据库迁移、数据写入和外部副作用不会因换回镜像自动恢复，需预先确认兼容性、对应备份及业务回退方案。

13.4 依赖、健康检查与开机自启

services:
  cache:
    image: redis:7.4
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 3s
      retries: 5
  app:
    image: registry.example.com/team/demo-api:1.0.0
    depends_on:
      cache:
        condition: service_healthy

示例：此 Redis 示例仅供未启用认证的受控演示环境，app 镜像为占位地址。service_healthy 在启动阶段等待健康检查；运行后依赖失效仍需应用重连。普通短写 depends_on 只表达启动顺序。单独的 unhealthy 不会自动触发 Docker 重启策略。

Docker daemon 开机启动与容器重启策略是两层配置；Compose 自身不是常驻守护进程，配置 restart 后由 Docker 负责对应容器的重启行为。

14. 清理命令：逐项确认范围

先用 docker system df -v 确认占用与对象归属。以下命令有删除作用，单独按需执行：

docker rm demo-old                  # 删除已停止的指定容器，可写层丢失
docker image rm demo-api:old         # 删除指定镜像标签/镜像
docker image prune                  # 清理悬空镜像
docker builder prune                # 清理构建缓存，后续构建可能变慢
docker container prune              # 删除所有已停止容器
docker network prune                # 清理未被容器使用的网络

示例：退出容器可能保留重要日志或未挂载的数据，先检查再删除；不默认加 -f 跳过确认。image prune -a 会扩大到未被容器引用的镜像，可能删掉本地回滚镜像。

以下范围更大，不作为常规巡检命令：

docker system prune            # 综合清理停止容器、未用网络、悬空镜像和构建缓存
docker volume rm demo-unused   # 删除指定未使用卷，其数据会丢失
docker compose -p demo down -v  # 删除项目容器与关联非外部卷，会丢失卷数据

示例：停用项目后卷也许暂时没有容器引用，但仍是需要保留的数据库。不要把“未使用”等同“无价值”；卷清理必须先核对备份和数据归属。

推荐顺序：system df -v找大对象 → inspect确认所属项目和挂载 → 保存日志、回退镜像或数据备份 → 删除具体对象 → 再查磁盘。先用带名称或ID的定点删除；只有明确允许全局范围时再考虑prune，过滤条件也不能替代归属核对。

例如清理单个已停止的演示容器前：

docker inspect demo-old                     # 查状态、挂载和项目标签，先确认不是待恢复业务
docker logs --tail 100 demo-old              # 保存需要的故障证据，日志驱动不支持时查对应日志源
docker rm demo-old                          # 确认可丢弃可写层后删除这个停止容器，不加-v
docker system df -v                         # 对比镜像、容器、卷和缓存占用
df -h                                      # 在daemon主机复查文件系统实际可用空间

示例：删除一个容器不一定释放镜像共享层或挂载卷空间；仍有进程持有已删除文件时，文件系统空间也可能暂不回收。不要看到释放量较小就立即扩大到 system prune -a --volumes。

docker ps -a                               # 看整体运行、退出和重启状态
