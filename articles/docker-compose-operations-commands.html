Docker 与 Docker Compose 常用运维命令

知知行笔记·2026-11-03·约 26 分钟阅读
dockercomposecontainersoperationstroubleshooting

使用 Docker 和 Compose 查看容器状态、排查日志与网络问题，以及构建镜像、更新服务、备份数据和清理资源。

命令采用 Linux shell 与 Compose V2 的 docker compose 写法；旧的 docker-compose 是另一套命令，执行前先确认本机版本，并调整示例名称与地址。启停、更新和清理操作按需选择。

1. 环境、版本和目标主机

安装 Docker Engine 与 Compose 插件（Ubuntu / Debian）

仅用于官方当前支持的Ubuntu/Debian版本的新安装环境。先用 cat /etc/os-release、uname -m 确认发行版与架构；已有Docker、Podman、containerd或业务容器时，先核对兼容与迁移方案，不直接卸载替换。

准备软件源：

sudo apt-get update
sudo apt-get install ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
. /etc/os-release
# 下列步骤仅在ID为ubuntu或debian时使用
docker_os="$ID"
curl -fL "https://download.docker.com/linux/$docker_os/gpg" -o /tmp/docker.asc
sudo install -m 0644 /tmp/docker.asc /etc/apt/keyrings/docker.asc
printf 'deb [arch=%s signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/%s %s stable\n' \
  "$(dpkg --print-architecture)" "$docker_os" "${UBUNTU_CODENAME:-$VERSION_CODENAME}" \
  | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null
sudo apt-get update

示例：Ubuntu使用ubuntu仓库及本机发行代号，Debian使用debian仓库；不要把Ubuntu代号写进Debian源。下载失败时先停止，确认网络、证书与官方源可达，不跳过签名。

| sudo tee ... > /dev/null 中，| 将生成的源配置传给具有权限的 tee 写入文件；> /dev/null 只丢弃 tee 同时输出到终端的那份内容，不会取消文件写入。tee 默认覆盖目标文件。

安装并验证：

sudo apt-get install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo systemctl enable --now docker # 新安装环境启动并开启自启
sudo docker version
sudo docker compose version

示例：docker compose version能输出版本，表示V2插件可用；docker version还应能连接Server。安装包可能自动启动服务，需在批准的主机上操作。发行版支持范围及版本选择以 Ubuntu安装说明 和 Debian安装说明 为准。

安装 Docker Engine 与 Compose 插件（RHEL 9 / CentOS Stream 9示例）

仅对匹配且受支持的发行版使用官方源；Rocky/AlmaLinux等兼容发行版须按其维护策略核对，不默认认定官方同等支持。已有容器运行时先核对现状。

cat /etc/os-release
sudo dnf install dnf-plugins-core
# CentOS Stream 9：选这一条
sudo dnf config-manager --add-repo https://download.docker.com/linux/centos/docker-ce.repo
# RHEL 9：改选这一条，不要两套源都加
# sudo dnf config-manager --add-repo https://download.docker.com/linux/rhel/docker-ce.repo
sudo dnf install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo systemctl enable --now docker
sudo docker version
sudo docker compose version

示例：安装时核对包源与GPG指纹。DNF5的源管理语法与DNF4可能不同，按系统和官方版本说明选择；CentOS 7不适用此清单，也不应通过关闭GPG校验或换成Stream源来强行安装。

参考 CentOS安装说明 与 RHEL安装说明。

已有Docker，只缺 docker compose 或普通用户无权限

先确认Docker来源及官方软件源已经正确配置，再按系统仅安装插件：

# Ubuntu / Debian，已有匹配Docker官方源
sudo apt-get update
sudo apt-get install docker-compose-plugin
# RHEL系，已有匹配Docker官方源时改选下面这一条
# sudo dnf install docker-compose-plugin
sudo docker compose version

示例：系统仓库安装的 docker.io 可能搭配发行版自己的Compose包，先查本机包来源，不混装官方与发行版整套运行时。无需为了使用Compose另装旧的 docker-compose Python工具。

sudo docker ps             # 已获授权时单条sudo
sudo docker compose version

示例：普通用户无Docker socket权限可使用获准的sudo或已部署的rootless模式。加入docker组相当于授予很高的主机权限，需要管理员明确授权，不把socket改成777。详见 Docker非root使用说明。

docker version             # 客户端和服务端版本
docker info                # 存储驱动、日志驱动、根目录等
docker compose version     # Compose 插件版本
docker context ls          # 可用连接目标
docker context show        # 当前目标
docker system df           # 镜像、容器、卷、缓存占用
docker system df -v        # 详细占用

示例：docker version 只有 Client、Server 连接失败时，检查 daemon、socket 权限和当前 context。远程 context 的操作作用于远端，执行删除前尤其需要核对。

systemctl status docker --no-pager -l          # 系统安装的 Docker 服务状态
sudo journalctl -u docker -b -n 100 --no-pager # 本次开机 daemon 日志
docker --help                               # CLI 帮助
docker run --help                           # 当前版本支持的启动选项

示例：rootless Docker 的服务可能属于用户级 systemd，需使用对应用户的 systemctl --user。不要因命令权限不足就把 Docker socket 改成所有人可写；Docker 控制权限本身具有很高的主机权限。

2. 容器列表、筛选和状态

docker ps                                      # 正在运行的容器
docker ps -a                                   # 包含已退出容器
docker ps --filter name=demo-web                # 名称匹配
docker ps -a --filter status=exited             # 退出容器
docker ps --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'
docker inspect demo-web                        # 完整配置和状态
docker inspect -f '{{json .State}}' demo-web     # 状态、退出码、健康检查

示例：Up 表示主进程存活；配置了健康检查才会有 healthy/unhealthy。Exited (137) 可能涉及 SIGKILL，但不能仅凭退出码断言 OOM，还要核对 OOMKilled 和主机日志。inspect 可能包含环境变量中的凭证，分享前脱敏。

3. 创建并运行容器

docker run -d --name demo-web \
  --restart unless-stopped \
  -p 127.0.0.1:8080:80 \
  --memory 256m --cpus 1 \
  --log-driver json-file \
  --log-opt max-size=10m --log-opt max-file=3 \
  nginx:1.28

示例：创建名为 demo-web 的 Nginx，主机回环8080映射到容器80，最多1个CPU配额和256MB内存，控制台日志按文件滚动。镜像标签需使用已批准且可用的版本，精确复现可固定 digest。这里的资源值仅为演示。

-p 8080:80 通常向全部主机地址发布，开放范围与只绑定127.0.0.1不同；还要核对 Docker 的转发规则和实际外部可达性。不要仅凭主机防火墙界面认定端口被拦截。

docker start demo-web          # 启动已创建的容器
docker stop -t 30 demo-web     # 优雅停止，超时后可能强制结束
docker restart -t 30 demo-web  # 重启，会中断连接
docker update --restart unless-stopped demo-web # 修改重启策略

示例：start 复用原容器配置，不会采用新的镜像或新的端口参数；要修改这些配置，需要重建容器。上述为备选操作，不要一起执行。

4. 日志、事件和退出原因

docker logs --tail 100 --timestamps demo-web       # 最近100行及时间
docker logs --since 30m --tail 300 demo-web        # 最近30分钟
docker logs -f --tail 100 demo-web                # 实时跟踪
docker inspect -f '{{.State.ExitCode}} {{.State.OOMKilled}} {{.State.Error}}' demo-web
docker events --since 30m --filter container=demo-web # 事件流

示例：日志中查应用异常，inspect 中查退出码和 OOM 标记，events 中查 die、restart 等事件。事件不是永久审计记录，也不能单独证明是谁操作了容器。logs -f、events 按 Ctrl+C 退出查看，不会停止容器。

docker logs 主要查看标准输出与错误，能否读取取决于日志驱动及相关配置；应用写在容器文件系统里的日志要另查。不要手工截断 Docker 内部日志文件，优先配置日志轮转。

5. 进入容器、执行命令与复制文件

docker exec -it demo-web sh                  # 进入已有容器
docker exec demo-web nginx -t                # 容器内执行一次配置校验
docker exec -u 0 -it demo-web sh             # 确有需要时使用容器内 root
docker cp demo-web:/etc/nginx/nginx.conf ./nginx.conf # 复制到本机
docker cp ./nginx.conf demo-web:/tmp/nginx.conf       # 复制到容器临时位置

示例：精简镜像不一定有 bash、curl、ps，可先尝试 sh；distroless 镜像可能连 shell 也没有。复制到 /tmp 不会自动应用配置；修改前需核对挂载与原配置。

exec 创建的交互 shell 中执行 exit 通常只退出该 shell。不要与 attach 混淆：attach 连接主进程的输入输出，Ctrl+C 可能给主进程发送信号；默认脱离快捷键为 Ctrl+P 再 Ctrl+Q。

容器内临时修改可能在重建时消失；长期配置写进镜像、挂载文件或 Compose 清单。

6. CPU、内存和磁盘排查

docker stats --no-stream                          # 一次性资源快照
docker stats demo-web                             # 实时资源
docker top demo-web                               # 容器进程
docker inspect -f '{{.HostConfig.Memory}} {{.HostConfig.NanoCpus}}' demo-web
docker ps -s                                      # 可写层大小
docker diff demo-web                              # 可写层变更
docker system df -v                               # Docker 存储占用

示例：容器内存接近限制时结合 OOMKilled 排查。ps -s 的可写层不包括全部挂载卷和日志占用，磁盘满时还需查主机文件系统、卷、日志和构建缓存。

7. 镜像拉取、查看、构建和推送

docker image ls                                   # 本地镜像
docker pull nginx:1.28                            # 拉取指定标签
docker image inspect nginx:1.28                   # digest、架构等
docker history nginx:1.28                         # 镜像层历史
docker build --pull -t demo-api:1.0.0 .            # 当前目录 Dockerfile 构建
docker tag demo-api:1.0.0 registry.example.com/team/demo-api:1.0.0
docker login registry.example.com                 # 按提示认证
docker push registry.example.com/team/demo-api:1.0.0
docker logout registry.example.com                # 退出仓库登录

示例：构建后给同一镜像加仓库标签再推送。推送前确认仓库和权限；不要把密码放进 -p 参数或 Dockerfile。构建上下文中的凭证应通过 .dockerignore 排除，构建秘密使用专门的 secret 挂载。

docker image save -o demo-api-1.0.0.tar demo-api:1.0.0 # 离线导出镜像
docker image load -i demo-api-1.0.0.tar                # 导入镜像
sha256sum demo-api-1.0.0.tar                          # 校验传输一致性

示例：在目标机器 load 后再创建容器。save/load 保存镜像，export/import 面向容器文件系统，后者不能等同完整镜像及卷数据备份。

8. 网络、DNS 与端口

docker network ls                                     # 网络列表
docker network inspect demo-net                       # 网段、成员
docker port demo-web                                  # 主机发布端口
docker inspect -f '{{json .NetworkSettings.Networks}}' demo-web
docker exec demo-web cat /etc/resolv.conf              # 容器 DNS 配置
curl -I --connect-timeout 3 --max-time 5 http://127.0.0.1:8080/

示例：同一自定义网络中的服务通常用容器名或服务名通信；容器内的 localhost 指容器自身。容器服务需监听可被其他容器访问的地址，不应只绑定容器内127.0.0.1。

docker network create demo-net             # 新建用户网络
docker network connect demo-net demo-web   # 把容器加入网络，会改变连通范围
docker network disconnect demo-net demo-web # 从网络移除，会影响连接

示例：只在确认拓扑后执行连接操作。排查顺序是容器进程 → 容器监听 → 网络成员 → DNS → 主机端口 → 外部规则 → 应用认证；不要通过反复重启代替定位。

9. 挂载卷与持久化

docker volume ls                                 # 命名卷列表
docker volume inspect demo-data                  # 卷属性
docker inspect -f '{{json .Mounts}}' demo-web      # 实际挂载来源、目标、读写模式
docker volume create demo-data                   # 创建命名卷

示例：命名卷用于持久数据；bind mount 使用明确的宿主机路径。卷挂载到原有非空目录时会遮盖镜像里的相应内容，不能看到文件不一定等于数据已删除。

只读挂载的启动示例：

docker run -d --name demo-static \
  -p 127.0.0.1:8081:80 \
  --mount type=bind,src=/opt/demo/html,dst=/usr/share/nginx/html,readonly \
  nginx:1.28

示例：主机 /opt/demo/html 必须存在。容器可以读取但不能通过该挂载写入静态文件。数据库挂载还应核对 UID/GID、SELinux 标签和备份策略，不能直接用全目录 chmod 777 解决。

卷备份示例

以下假设写入该卷的应用已经停止，./backup 已创建，且 demo-data 已由 volume inspect 确认存在：

docker run --rm \
  --mount type=volume,src=demo-data,dst=/data,readonly \
  --mount type=bind,src="$PWD/backup",dst=/backup \
  alpine:3.22 tar -czf /backup/demo-data.tgz -C /data .
tar -tzf ./backup/demo-data.tgz | head # 核对归档可读

示例：归档写到主机的 backup 目录。数据库运行中直接打包数据目录通常不能保证一致性，应优先使用数据库备份工具或受支持的快照流程。

tar -tzf ... | head 中的 | 把归档文件列表交给 head，默认只显示前10行；这只用于快速查看，不等于已经完整校验或恢复验证了整个备份。

恢复前先验证备份，使用新的空卷演练，不覆盖已有生产数据：

docker volume create demo-data-restore
docker run --rm \
  --mount type=volume,src=demo-data-restore,dst=/data \
  --mount type=bind,src="$PWD/backup",dst=/backup,readonly \
  alpine:3.22 tar -xzf /backup/demo-data.tgz -C /data

示例：恢复到 demo-data-restore，再用兼容的应用版本验证权限、数据和业务；原卷保持保留。

10. Compose 的文件与项目范围

docker compose ls                                 # Compose 项目列表
docker compose -p demo -f /opt/demo/compose.yaml config -q # 校验
docker compose -p demo -f /opt/demo/compose.yaml config --services # 服务名
docker compose -p demo -f /opt/demo/compose.yaml config --images   # 镜像

示例：使用固定 -p demo 与 -f /opt/demo/compose.yaml，避免在不同目录意外操作另一套项目。完整 config 会展开环境变量，可能显示敏感值，分享时不要直接贴出原始结果。

下面的 Compose 命令均假设已进入 /opt/demo，使用该目录的 compose.yaml 和固定项目名 demo。

最小示例文件：

services:
  web:
    image: nginx:1.28
    ports:
      - "127.0.0.1:8080:80"
    restart: unless-stopped
    volumes:
      - ./html:/usr/share/nginx/html:ro
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"

示例：先准备 html/index.html。该清单不需要旧式顶层 version 字段。web 是服务名，不要求容器名也叫 web。

11. Compose 启动、停止与重建

docker compose -p demo config -q           # 先校验
docker compose -p demo up -d               # 创建/按配置重建并后台运行
docker compose -p demo ps -a               # 查看项目内容器
docker compose -p demo start web           # 启动已存在的服务容器
docker compose -p demo stop -t 30 web       # 停止，保留容器
docker compose -p demo restart web         # 重启原容器
docker compose -p demo up -d --no-deps web  # 只更新目标服务，不连带启动依赖

示例：修改环境变量、端口或镜像后，使用 up -d 应用变化；restart 不会重新读取这些变更来重建容器。--no-deps 只在依赖已经满足时使用。

docker compose -p demo up -d --force-recreate web # 强制重建，会替换容器
docker compose -p demo down                      # 删除项目容器和非外部网络

示例：down 会中断整个项目。默认不删除命名卷，但容器可写层会丢失，匿名卷再次启动时也未必自动复用；重要数据应明确挂载。不要为查看状态执行 down。

12. Compose 日志、执行和资源

docker compose -p demo logs --tail 100 --timestamps web # 最近日志
docker compose -p demo logs -f --since 10m web           # 实时日志
docker compose -p demo exec web sh                      # 进入运行容器
docker compose -p demo exec -T web nginx -t              # 无TTY执行，适合脚本
docker compose -p demo top                              # 进程
docker compose -p demo port web 80                       # 查询映射
docker compose -p demo run --rm --no-deps web nginx -t   # 一次性新容器

示例：exec 在原容器执行；run 创建一次性容器，默认不发布服务端口，仍可能访问该服务声明的卷和网络，执行写操作前应核对影响。资源检查可取 ps -q 返回的容器ID再用 docker stats。

13. Compose 更新、回滚和环境

docker compose -p demo pull web             # 仅拉取，不更新运行容器
docker compose -p demo up -d --no-deps web   # 按新镜像重建目标服务
docker compose -p demo logs --tail 100 web   # 核对启动日志
docker compose -p demo ps                   # 查看状态

示例：更新前保留原清单、镜像 digest 和数据备份。失败时把清单改回原镜像再 up -d --no-deps web；镜像回滚不会回滚数据库和挂载配置。

docker compose -p demo build --pull web                 # 本地构建
docker compose -p demo up -d --build web                # 构建并应用
docker compose -p demo --env-file .env.prod config -q    # 指定变量来源
docker compose -p demo -f compose.yaml -f compose.prod.yaml config -q # 合并校验
docker compose -p demo --profile tools config --services # 配置指定 profile

示例：多文件顺序会影响最终配置，后文件按 Compose 合并规则覆盖或补充；相对路径通常基于第一个清单的位置。.env 常用于清单插值，不代表所有变量自动进入容器；容器环境需通过 environment 或 env_file 等声明。

依赖与健康检查

services:
  cache:
    image: redis:7.4
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 3s
      retries: 5
  app:
    image: registry.example.com/team/demo-api:1.0.0
    depends_on:
      cache:
        condition: service_healthy

示例：此 Redis 示例仅供未启用认证的受控演示环境，app 镜像为占位地址。service_healthy 在启动阶段等待健康检查；运行后依赖失效仍需应用重连。普通短写 depends_on 只表达启动顺序。单独的 unhealthy 不会自动触发 Docker 重启策略。

Docker daemon 开机启动与容器重启策略是两层配置；Compose 自身不是常驻守护进程，配置 restart 后由 Docker 负责对应容器的重启行为。

14. 清理命令：逐项确认范围

先用 docker system df -v 确认占用与对象归属。以下命令有删除作用，单独按需执行：

docker rm demo-old                  # 删除已停止的指定容器，可写层丢失
docker image rm demo-api:old         # 删除指定镜像标签/镜像
docker image prune                  # 清理悬空镜像
docker builder prune                # 清理构建缓存，后续构建可能变慢
docker container prune              # 删除所有已停止容器
docker network prune                # 清理未被容器使用的网络

示例：退出容器可能保留重要日志或未挂载的数据，先检查再删除；不默认加 -f 跳过确认。image prune -a 会扩大到未被容器引用的镜像，可能删掉本地回滚镜像。

以下范围更大，不作为常规巡检命令：

docker system prune            # 综合清理停止容器、未用网络、悬空镜像和构建缓存
docker volume rm demo-unused   # 删除指定未使用卷，其数据会丢失
docker compose -p demo down -v  # 删除项目容器与关联非外部卷，会丢失卷数据

示例：停用项目后卷也许暂时没有容器引用，但仍是需要保留的数据库。不要把“未使用”等同“无价值”；卷清理必须先核对备份和数据归属。

15. 常见故障速查

现象 优先检查
Cannot connect to daemon daemon 状态、context、socket、rootless 模式
容器不断重启 inspect状态、退出码、logs、挂载权限、配置、依赖
OOMKilled 容器限制、主机内存、应用峰值、JVM/堆外内存
容器正常但访问不到 进程监听、发布端口、监听地址、主机规则、代理
容器内连 localhost 失败 localhost 指容器自己；核对目标服务和网络
修改清单不生效 是否只做了 restart；核对项目名与文件，用 up 重建
重建后数据没了 数据是否只在可写层或匿名卷、实际挂载路径是否变化
日志占满磁盘 日志驱动、轮转、应用文件日志、卷和缓存分别查
pull 失败 仓库认证、DNS、代理、镜像标签、架构、证书
exec 找不到 sh 精简镜像不带shell，采用镜像允许的调试方式

命令选项以本机 --help 为准，可查 Docker CLI 与 Compose CLI。另见 Kubernetes 常用运维命令。
