Kafka 部署、运维与故障排查

知知行笔记·约 37 分钟阅读
kafkamqkraftoperationstroubleshooting

从连接失败、消息积压、ISR 收缩、磁盘上涨等现象入手，按顺序检查并验证处理结果。命令以 Apache Kafka 4.0.2、Linux Bash、普通消费者组为例；这是一套固定版本示例。已有集群先确认版本与部署方式，再使用它对应的工具。4.x 使用 KRaft，旧 ZooKeeper 集群的修复和迁移不能直接套用。

生产消费代码见 Kafka 消息生产、消费与可靠性实践，需要追到内部实现时看 Kafka 核心机制与源码排查。

1. 执行前先确认环境和权限

Kafka 工具可以在能访问集群的管理机上执行，磁盘、进程、日志命令则需要登录到对应 Broker 主机。以下变量在同一个 Bash 终端中设置，后续示例沿用它们。

export KAFKA_HOME=/opt/kafka                       # 改成实际 Kafka 安装目录
export BS='broker1.example.com:9092,broker2.example.com:9092' # 客户端入口，不能填 Controller 端口
export TOPIC=orders                               # 本次排查的主题
export GROUP=orders-worker                        # 本次排查的消费者组
cd "$KAFKA_HOME"                                  # 后面的 bin/ 从安装目录执行
bin/kafka-topics.sh --version                     # 查看这套命令行工具的版本
java -version                                    # 查看当前终端使用的 JDK

示例：服务运行在 /srv/kafka，管理机却使用 /opt/kafka 中另一版本的脚本，应先核对差异。命令行工具的版本不等于远端 Broker 的版本，后者还要查部署镜像、安装清单或启动日志。

ADMIN=()                                         # 无认证的隔离实验集群使用空参数
# 已有安全集群改用下面两行；文件由管理员提供，不能用空文件绕过认证
# export CLIENT_CONFIG="$HOME/.config/kafka/admin.properties"
# ADMIN=(--command-config "$CLIENT_CONFIG")       # 管理命令追加认证、TLS 参数

示例："${ADMIN[@]}" 是 Bash 数组展开，空数组不增加参数；安全集群会展开为两个独立参数。生产者用 --producer.config，消费者用 --consumer.config，不能把管理命令的 --command-config 原样放过去。

id                                               # 查看当前用户和所属组
sudo -l                                          # 查看获准执行的管理操作
systemctl status kafka --no-pager -l              # 查看 systemd 服务状态，服务名按实际替换
sudo systemctl cat kafka                         # 核对启动用户、程序路径和配置文件

示例：查询 Kafka 的授权由 Kafka ACL 决定，Linux 上使用 root 不会自动获得 Topic 权限。查看进程用服务所属用户；读取其他用户日志、端口归属或操作 systemd 时才按需使用 sudo。没有 sudo 授权时请管理员执行对应步骤，不改成 chmod -R 777。

展开：安装排查工具和 JDK

按系统选择一组。包安装在被检查的主机；管理机只需 JDK、Kafka 工具及必要的网络工具。

cat /etc/os-release                              # 确认发行版，避免混用软件源
# Ubuntu / Debian：安装 JDK 和诊断工具
sudo apt-get update                              # 更新软件索引
sudo apt-get install default-jdk curl ca-certificates tar procps iproute2 sysstat lsof openssl
# RHEL / Rocky / AlmaLinux：使用系统已有 dnf 仓库
# sudo dnf install java-17-openjdk-devel curl ca-certificates tar procps-ng iproute sysstat lsof openssl
java -version                                    # Kafka 4.0 的 Broker 和工具需要 Java 17+
command -v iostat pidstat jcmd lsof                # 确认工具已进入 PATH

示例：iostat、pidstat 由 sysstat 提供，jcmd 由 JDK 提供。容器精简镜像不一定包含它们，优先在宿主机或已有诊断环境操作，不临时修改运行中的业务镜像。

CentOS 7只从现有批准仓库安装基础工具，JDK另行核对，不能假设基础仓库提供Java 17：

sudo yum install curl ca-certificates tar procps-ng iproute sysstat lsof openssl # 安装网络、进程与磁盘诊断工具
uname -m                                        # 核对CPU架构，不能混用x64与ARM构建
ldd --version                                   # 查看glibc版本，与所选JDK发行包要求对照
yum --showduplicates list java-17-openjdk-devel  # 查询候选；无包时不添加其他发行版的源
java -version                                   # 查看当前JDK；Java 8/11不能运行本文4.0 Broker示例

示例：原Kafka运行在Java 8/11时，先确认原Kafka版本，维护时沿用它匹配的工具；不要为运行本文示例原地升级生产JDK或Kafka。本文实验的Broker和命令行工具至少需要Java 17，优先在受维护的管理机或实验机上准备。

确实需要在CentOS 7使用JDK 17时，先按JDK供应方的支持平台、架构和glibc要求选发行包，完成来源及校验和核对。可参考JDK归档安装方法，安装方法本身不代表任意构建都支持CentOS 7。若已将审核过的JDK解压到 /opt/jdk-17，仅在当前终端指定它：

export JAVA_HOME=/opt/jdk-17                     # 改为已验证兼容的JDK目录，不修改整机默认Java
export PATH="$JAVA_HOME/bin:$PATH"              # 当前终端优先使用这一套JDK
java -version                                   # 验证实际运行版本，不能出现GLIBC缺失等错误
javac -version                                  # 编译示例时确认包含编译器
jcmd -l                                         # 用获准身份列出可见JVM，附加工具应匹配目标JDK

示例：出现 GLIBC_2.xx not found时不要替换系统glibc，改选供应方确认兼容的构建或换到受维护系统。当前终端的 JAVA_HOME不会自动改变systemd服务，服务环境以其unit配置为准。旧sysstat字段按本机表头阅读；cgroup v1检查见Linux内核排查。

2. 新建一个可以验证收发的实验环境

展开：下载二进制包，启动单节点 KRaft

在新建的实验目录执行。单节点只用于学习、验证命令，不提供副本容错。这里绑定回环地址，远程客户端无法连接。

mkdir -p "$HOME/kafka-lab"                         # 新建实验工作目录
cd "$HOME/kafka-lab"                              # 后续下载均保存在这里
curl -fLO https://archive.apache.org/dist/kafka/4.0.2/kafka_2.13-4.0.2.tgz # 下载固定版本
curl -fLO https://archive.apache.org/dist/kafka/4.0.2/kafka_2.13-4.0.2.tgz.sha512 # 下载校验值
EXPECTED_SHA512="$(sed '1s/^[^:]*: //' kafka_2.13-4.0.2.tgz.sha512 | tr -d '[:space:]' | tr 'A-F' 'a-f')" # 转换Apache分组换行的校验值
printf '%s  %s\n' "$EXPECTED_SHA512" kafka_2.13-4.0.2.tgz | sha512sum -c - # 必须看到OK，失败则停止
tar -xzf kafka_2.13-4.0.2.tgz                      # 解压到当前目录
export KAFKA_HOME="$PWD/kafka_2.13-4.0.2"          # 保存安装位置
export BS=127.0.0.1:9092                          # 当前实验集群入口
export TOPIC=orders                              # 实验主题
export GROUP=orders-worker                       # 实验消费者组
ADMIN=()                                         # 实验环境未开启认证
cd "$KAFKA_HOME"                                  # 进入安装目录
mkdir -p "$HOME/kafka-lab/data"                   # 使用持久目录，避免 /tmp 被清理
cat > config/lab.properties <<EOF
# 单进程同时承担 Broker、Controller，只用于本机实验
process.roles=broker,controller
node.id=1
controller.quorum.bootstrap.servers=127.0.0.1:9093
listeners=PLAINTEXT://127.0.0.1:9092,CONTROLLER://127.0.0.1:9093
advertised.listeners=PLAINTEXT://127.0.0.1:9092
inter.broker.listener.name=PLAINTEXT
controller.listener.names=CONTROLLER
listener.security.protocol.map=CONTROLLER:PLAINTEXT,PLAINTEXT:PLAINTEXT
log.dirs=$HOME/kafka-lab/data
offsets.topic.replication.factor=1
transaction.state.log.replication.factor=1
transaction.state.log.min.isr=1
EOF
CLUSTER_ID="$(bin/kafka-storage.sh random-uuid)"    # 仅初始化新实验集群时生成一次
bin/kafka-storage.sh format --standalone -t "$CLUSTER_ID" -c config/lab.properties # 初始化全新空目录
bin/kafka-server-start.sh config/lab.properties    # 前台启动，保留这个终端

示例：日志显示启动完成后，新开终端重新设置 KAFKA_HOME、BS、TOPIC、GROUP 和 ADMIN，再运行下一节。普通重启只执行最后一行；已有数据目录不重新生成集群 ID，也不再次格式化。前台服务按 Ctrl+C 会停止 Broker。

下载、初始化和运行方式可对照 Apache Kafka Quick Start。

多节点部署要先明确什么

正式环境把 Controller 与 Broker 的角色、故障域和安全通道规划好，再初始化。常见规划是 3 个专用 Controller 和至少 3 个 Broker；3 个 Controller 需要至少 2 个正常才能形成多数派。增加 Broker 不等于增加 Controller。

项目 配置和检查重点
节点身份 全集群 node.id 唯一；重启保留原 ID 和原数据
集群身份 所有节点使用同一个 cluster ID；每个目录保留正确的 meta.properties
角色 process.roles=controller 或 broker；实验的合并模式不等于生产隔离
Quorum 区分静态 controller.quorum.voters 和动态 quorum；按所用方式初始化和变更成员
地址 Broker 的广播地址对实际客户端可达；Controller 地址对节点可达
存储 数据、元数据目录持久化，服务用户有权限，监测空间和 inode
内部主题 在首次创建前规划 offsets、transaction 内部主题副本数；修改默认值不会自动增加已有主题副本
业务主题 例如副本数 3、min.insync.replicas=2，与生产者 acks=all 配合
安全 按已有 PKI/身份体系配置 TLS、SASL、ACL；不把明文实验端口暴露到公网

静态和动态 quorum 的初始化参数不同，尤其不能给已有集群的每个 Controller 分别运行 --standalone。新增节点和变更成员应按 KRaft 部署与成员管理执行。

验证一次完整收发

先确认第 1 节变量，在实验集群执行：

bin/kafka-topics.sh --bootstrap-server "$BS" "${ADMIN[@]}" --create --topic "$TOPIC" --partitions 3 --replication-factor 1 # 新建实验主题
bin/kafka-topics.sh --bootstrap-server "$BS" "${ADMIN[@]}" --describe --topic "$TOPIC" # 查看分区和 Leader
printf 'order-1001:created\norder-1002:created\n' | bin/kafka-console-producer.sh --bootstrap-server "$BS" --topic "$TOPIC" --property parse.key=true --property key.separator=: --producer-property acks=all # 写两条带 key 的消息
bin/kafka-console-consumer.sh --bootstrap-server "$BS" --topic "$TOPIC" --from-beginning --max-messages 2 --timeout-ms 10000 --property print.key=true --property print.partition=true --property print.offset=true # 限量读取验证

示例：能读到两条订单事件才说明客户端到数据分区的收发路径通了。printf ... | ... 把左侧文字作为右侧标准输入；控制台退出不会删除消息。该验证命令没有使用业务消费者组，避免影响其分区分配与进度。安全集群为生产者、消费者分别补上对应的配置文件参数。

3. 故障先定位范围，再改配置

现象 建议执行顺序 先找的证据
完全连不上 进程 → 监听 → DNS/TCP → Kafka API → 广播地址 → TLS/认证 端口归属、连接错误、元数据中的节点地址
主题不可用 describe → 无 Leader 分区 → 副本主机 → quorum → Broker 日志 Leader、ISR、存储错误、选举与 fencing
发送变慢 客户端队列 → Broker 请求分段耗时 → ISR → 磁盘/GC/网络 是本地处理慢，还是等待副本慢
消费积压 分区 Lag 趋势 → 成员分配 → 业务耗时 → poll/rebalance → Broker 热点分区、慢 SQL、线程阻塞、频繁重平衡
磁盘持续上涨 目录占用 → 主题策略 → 日志段 → cleaner/删除延迟 → 副本迁移 delete/compact、分区数量、未完成迁移
提交位移失败 组状态和协调器 → 内部主题 Leader/ISR → 加载日志 → 客户端 ownership 是业务失败、组变更，还是协调器不可用

先保存事发时间、涉及主题/分区/组、错误码、最近变更和监控截图。重启会改变线程、连接与部分现场，先收集这些证据。

4. 服务突然不可用、连不上

在 Broker 主机执行：

date -Is                                         # 记录主机时间并与应用侧时间对齐
pgrep -af 'kafka.Kafka'                           # 查找 Broker JVM，避免仅按 java 判断
sudo ss -lntp 'sport = :9092'                     # 确认客户端端口和进程归属
systemctl status kafka --no-pager -l              # 查看服务状态与退出结果
sudo journalctl -u kafka --since '30 minutes ago' --no-pager # 查看退出、启动和错误日志
sudo journalctl -k --since '30 minutes ago' --no-pager | grep -Ei 'oom|out of memory|killed process|I/O error|read-only' # 检查内核杀进程及磁盘错误

示例：Killed process ... java 是内核 OOM 的证据；systemd 的 status=15/TERM 只说明终止信号，单凭它不能证明是谁停止的。追查人为操作还要结合已有 sudo、审计、SSH 和发布平台记录；未提前启用审计时，往往无法事后还原发送信号的人。

在出问题的客户端主机执行：

getent hosts broker1.example.com                  # 检查实际客户端使用的 DNS 解析
timeout 3 bash -c 'exec 3<>/dev/tcp/broker1.example.com/9092' # 只验证 TCP 建连，退出码0代表连通
bin/kafka-broker-api-versions.sh --bootstrap-server "$BS" "${ADMIN[@]}" # 验证 Kafka 协议并观察返回节点

示例：TCP 成功但 Kafka API 超时，继续检查协议、TLS、认证与广播地址。bootstrap.servers 只是入口，客户端获取元数据后会连接分区 Leader、协调器等其他 Broker。常见情况是入口可达，但 advertised.listeners 返回容器主机名、localhost 或另一网络的地址。

listeners 管本地绑定，advertised.listeners 管对客户端公布什么地址；广播地址不能写 0.0.0.0。多网络场景要分监听器配置，改完从每个实际客户端网络重新验证全部节点。

openssl s_client -connect broker1.example.com:9093 -servername broker1.example.com -verify_hostname broker1.example.com -CAfile /path/to/ca.pem -verify_return_error < /dev/null # 对已有TLS端口检查证书链和主机名

示例：证书 SAN 不包含广播主机名时，修证书或地址，不清空 ssl.endpoint.identification.algorithm 来跳过验证。TLS 握手通过仍不代表 SASL 登录和 ACL 授权通过。

CentOS 7的旧OpenSSL先用 openssl s_client -help 核对选项；若不支持 -verify_hostname，在具有相应能力的管理机执行这条检查。Kafka端口不是HTTP接口，不能改用curl的HTTPS响应来验收；仅删除主机名参数后握手成功，也不代表域名验证通过。最终还需用原Kafka客户端的TLS/SASL配置验证连接。

5. Leader 不可用、ISR 收缩

bin/kafka-topics.sh --bootstrap-server "$BS" "${ADMIN[@]}" --describe --topic "$TOPIC" # 查看每个分区 Leader、Replicas、Isr
bin/kafka-topics.sh --bootstrap-server "$BS" "${ADMIN[@]}" --describe --unavailable-partitions # 只列无可用 Leader 的分区
bin/kafka-topics.sh --bootstrap-server "$BS" "${ADMIN[@]}" --describe --under-replicated-partitions # 列出同步副本不足的分区
bin/kafka-metadata-quorum.sh --bootstrap-server "$BS" "${ADMIN[@]}" describe --status # KRaft：查看元数据多数派状态
bin/kafka-metadata-quorum.sh --bootstrap-server "$BS" "${ADMIN[@]}" describe --replication # KRaft：查看各元数据副本追赶情况

示例：Replicas: 1,2,3、Isr: 1,2 表示副本 3 未在同步集合中，不等于主题已丢失。若 min.insync.replicas=2，再失去一个同步副本时，acks=all 写入可能失败，这是保护可靠性的行为。

按输出中的 Broker ID 找到主机，检查磁盘、网络、GC、抓取线程错误与重启记录。如果只有个别分区异常，先查这些副本；大量主题同时无 Leader，再重点查 Broker 故障和 Controller quorum。Quorum 的 HighWatermark 与业务分区高水位是两套数据，不能相互替代。

处理顺序：恢复磁盘和节点连通 → 恢复正常副本抓取 → 等待 ISR 回来 → 再验证收发与错误率。不要把启用非 ISR 副本选举、降低 min ISR、删除元数据目录当成常规恢复动作；这些会改变数据保留或可靠性结果。

6. 消费积压：先看哪个分区、哪个成员慢

bin/kafka-consumer-groups.sh --bootstrap-server "$BS" "${ADMIN[@]}" --describe --group "$GROUP" # 查看各分区提交进度及 Lag
bin/kafka-consumer-groups.sh --bootstrap-server "$BS" "${ADMIN[@]}" --describe --group "$GROUP" --members --verbose # 查看成员及其分区分配
bin/kafka-consumer-groups.sh --bootstrap-server "$BS" "${ADMIN[@]}" --describe --group "$GROUP" --state # 查看状态、协调器与成员数

示例：只有分区 2 的 Lag 增长，且一直由同一个成员负责，优先查该分区 key 热点和对应业务处理；所有分区都增长，则核对输入速率、总消费能力、下游容量。至少间隔一段时间采样两次，单点 Lag 不能表示趋势。

字段/状态 怎么理解 下一步
CURRENT-OFFSET 已提交的下一条消费位置，不一定是进程最新处理位置 检查提交是否失败、是否过久才提交
LOG-END-OFFSET / LAG 工具显示的末端位置与提交位置差 位移空洞、事务和压实会影响计数，结合消息年龄
成员无分区 实例数可能超过可分配分区数，也可能订阅不同 加实例之前先看分配结果
Preparing/CompletingRebalance classic 组正在重平衡 查 poll 超时、成员启停、订阅变化
Empty 该组目前没有活跃成员，可能仍有位移 查应用是否正常运行、是否连错集群

积压恢复要估算时间：假设新增 5 万条/秒，持续处理能力 8 万条/秒，净追赶速度只有 3 万条/秒。900 万条积压约需 300 秒，前提是这些速率稳定且 Lag 可近似计数。还要确保最旧未消费消息不会在追赶过程中超过留存期。

处理优先级：修复下游瓶颈和失败重试风暴 → 降低单次 poll 处理时间或批量处理 → 在分区允许范围内扩消费者 → 再评估分区扩容。直接把位移调到最新会跳过业务数据，不是消除积压的通用方案。

7. 磁盘上涨、留存不生效

在 Broker 主机上，把 /var/lib/kafka 改成实际数据挂载点：

df -hT /var/lib/kafka                             # 检查文件系统空间与类型
df -i /var/lib/kafka                              # 检查 inode，空间未满也可能写不了文件
sudo du -xhd1 /var/lib/kafka                       # 统计同一文件系统下各分区目录占用
sudo lsof +L1                                    # 查已删除但仍被进程持有的文件
iostat -xz 1 5                                   # 连续观察磁盘等待、吞吐和队列
bin/kafka-log-dirs.sh --bootstrap-server "$BS" "${ADMIN[@]}" --describe --topic-list "$TOPIC" # 查每个副本大小和目录错误
bin/kafka-configs.sh --bootstrap-server "$BS" "${ADMIN[@]}" --entity-type topics --entity-name "$TOPIC" --describe --all # 查看主题实际配置和继承来源

示例：df 大而 du 小，先查已删除文件、挂载点和其他目录；du 的分区目录明显变大，则检查以下规则。

  • retention.bytes 是每个分区的留存阈值，整个集群还要乘上分区数量与副本数，并留出额外空间。
  • delete 按日志段回收，不是逐条消息到点立即删；段切分、检查周期、删除延迟和复制状态都会影响回收时点。
  • compact 保留每个 key 的最新状态，不表示按时间删除所有旧消息；compact,delete 同时有时间/大小保留约束。
  • null value 的 tombstone 参与压实删除；字符串 "null" 和空字符串不是 tombstone。
  • segment.bytes/segment.ms 太大时，小流量主题回收粒度可能很粗；频繁切小段又会增加文件与恢复开销。
  • 副本迁移中的 future 目录、cleaner 临时文件、内部主题，也会占空间；不要手工删除这些文件。

需要临时调整业务主题留存时，先保存旧配置、确认最慢消费者和补数据需求，再执行：

bin/kafka-configs.sh --bootstrap-server "$BS" "${ADMIN[@]}" --entity-type topics --entity-name "$TOPIC" --describe --all > topic-config.before.txt # 保存变更前配置供人工核对
bin/kafka-configs.sh --bootstrap-server "$BS" "${ADMIN[@]}" --entity-type topics --entity-name "$TOPIC" --alter --add-config retention.ms=259200000 # 示例：明确批准后改为3天，会使旧数据有资格被删
bin/kafka-configs.sh --bootstrap-server "$BS" "${ADMIN[@]}" --entity-type topics --entity-name "$TOPIC" --describe --all # 核对配置已生效

示例：回退必须恢复原来的值；原先没有主题级覆盖才用 --delete-config retention.ms 恢复继承。把留存改长无法找回已经删除的数据。参数含义见 主题配置。

8. 发送变慢、CPU 或 GC 异常

在 Broker 主机执行，先从进程列表确认 PID，不自动拿到多个 JVM 后直接操作：

pgrep -af 'kafka.Kafka'                           # 找到本次检查的 JVM
PID=12345                                        # 替换成已确认的 Broker PID
ps -p "$PID" -o pid,ppid,user,etime,%cpu,%mem,args # 确认进程身份和运行时间
pidstat -p "$PID" -u -r -d 1 5                    # 按进程看 CPU、内存缺页和 I/O
vmstat 1 5                                       # 看运行队列、swap、阻塞与CPU等待
iostat -xz 1 5                                   # 与磁盘负载同时对照
jcmd "$PID" Thread.print -l > kafka-threads.txt    # 服务用户执行，保存线程栈
jcmd "$PID" GC.heap_info                          # 服务用户执行，查看当前堆状态

示例：jcmd 需要同机、匹配权限，并通常使用相应 JDK；容器中还涉及 PID 命名空间。> kafka-threads.txt 把标准输出保存到文件，会覆盖同名文件。先用现有 GC 日志和监控，不为了一次观测在生产环境强制 Full GC 或直接抓超大 heap dump。

证据 优先排查 变更后的验证
RequestQueueTimeMs 高 I/O处理线程是否忙、CPU/磁盘是否已饱和 队列降低且请求延迟改善
LocalTimeMs 高 日志写入、压缩/转换、授权、锁竞争 具体慢步骤耗时下降
Produce RemoteTimeMs 高 Follower 磁盘、网络、抓取进度、ISR 副本追上且发送超时下降
ResponseQueue/SendTime 高 网络线程、出口带宽、客户端读响应 排队与重传下降
客户端 buffer 等待高 Broker慢、元数据不可达、生产速率超出能力 重试和排队消退、最终回调成功
大量 major fault、读I/O增大 页缓存不足、回放历史数据、其他进程争抢内存 热业务延迟恢复

吞吐和延迟先各自给目标，再逐项实验。保留可靠性要求，用批次、压缩和并行度改善效率；不通过关闭重试或把 acks 改成 0 来掩盖故障。堆要给页缓存、线程栈、直接内存和容器限制留余量，不把“固定 6GB 堆”当通用答案。

9. 扩分区、迁移副本与下线节点

扩分区只增加并行度，不会自动重分布历史数据。同一 key 的新消息可能切换分区，先评估顺序、去重、流处理关联以及下游容量。

bin/kafka-topics.sh --bootstrap-server "$BS" "${ADMIN[@]}" --describe --topic "$TOPIC" # 记录原分区数与副本分布
bin/kafka-topics.sh --bootstrap-server "$BS" "${ADMIN[@]}" --alter --topic "$TOPIC" --partitions 6 # 示例：由3增到6，不能原地缩回
bin/kafka-topics.sh --bootstrap-server "$BS" "${ADMIN[@]}" --describe --topic "$TOPIC" # 验证新分区都有 Leader 和 ISR

副本迁移适用于 Broker 扩容、磁盘失衡、调整副本数和下线。以至少 3 个 Broker 的集群为前提，目标 ID 必须真实存在，下面以 ID 1、2、3、4 为例：

cat > topics-to-move.json <<'EOF'
{"version":1,"topics":[{"topic":"orders"}]}
EOF
bin/kafka-reassign-partitions.sh --bootstrap-server "$BS" "${ADMIN[@]}" --topics-to-move-json-file topics-to-move.json --broker-list '2,3,4' --generate > reassignment-plan.txt # 只生成方案，包含当前和建议分配

示例：阅读输出，把“当前分配”保存为 reassignment-before.json，把审核后的“建议分配”保存为 reassignment-after.json，均只保留对应 JSON。不能直接把整份带说明文字的输出当 JSON。核对每个分区仍有足够副本、目标故障域与磁盘空间，再执行：

bin/kafka-reassign-partitions.sh --bootstrap-server "$BS" "${ADMIN[@]}" --reassignment-json-file reassignment-after.json --execute --throttle 10485760 # 示例：每秒10MiB迁移限速，按实际余量调整
bin/kafka-reassign-partitions.sh --bootstrap-server "$BS" "${ADMIN[@]}" --reassignment-json-file reassignment-after.json --verify # 检查完成情况；完成后按工具行为清除本次迁移限速
bin/kafka-log-dirs.sh --bootstrap-server "$BS" "${ADMIN[@]}" --describe --topic-list "$TOPIC" # 验证实际落盘位置、future副本及错误
bin/kafka-topics.sh --bootstrap-server "$BS" "${ADMIN[@]}" --describe --topic "$TOPIC" # 验证最终副本列表与 ISR

示例：加了 Broker 不会自动迁走旧数据；Broker 下线前要确认它承载的所有业务与内部主题副本已迁移，而不是只看 orders。回退使用之前保存的分配方案重新迁移，也需要时间和容量，并非瞬间撤销。迁移期间继续观察 Lag 和延迟，不能把限速设得低到副本永远追不上新增数据。

10. 动态配置、自启与滚动维护

先从实际生效配置判断来源：主题覆盖、单 Broker 动态配置、集群动态默认、静态文件及内置默认值可能不同。修改配置文件并不保证覆盖了动态值。

bin/kafka-configs.sh --bootstrap-server "$BS" "${ADMIN[@]}" --entity-type brokers --entity-default --describe # 查看集群动态默认
bin/kafka-configs.sh --bootstrap-server "$BS" "${ADMIN[@]}" --entity-type brokers --entity-name 1 --describe --all # 查看Broker 1的配置及来源

示例：是否能动态更新取决于本版本参数的 Update Mode，不能因为旧版本支持动态修改就认为 4.x 也支持。只读配置需要按计划滚动重启，见 Broker 配置说明。

展开：二进制部署的 systemd 服务模板

仅用于尚无服务托管的新实例。先准备专用 kafka 用户、真实 JDK 路径、配置、持久目录和权限，并完成新集群初始化；不与已有容器、脚本守护或 systemd 实例重复启动。将下面内容保存为 /etc/systemd/system/kafka.service，按实际路径调整。

[Unit]
Description=Apache Kafka
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=kafka
Group=kafka
WorkingDirectory=/opt/kafka
Environment="JAVA_HOME=/path/to/jdk-17"
Environment="KAFKA_HEAP_OPTS=-Xms1g -Xmx1g"
ExecStart=/opt/kafka/bin/kafka-server-start.sh /etc/kafka/server.properties
Restart=on-failure
RestartSec=10
TimeoutStopSec=180
LimitNOFILE=100000

[Install]
WantedBy=multi-user.target

示例：1GiB 堆和文件句柄数只是起始模板，应结合分区规模与限制调整。Type=simple 的启动命令不加 -daemon、nohup 或 &，让 systemd 跟踪实际进程。检查现有 log4j 配置中的日志目录是否允许 kafka 用户写入。

sudo systemd-analyze verify /etc/systemd/system/kafka.service # 校验单元文件
sudo systemctl daemon-reload                      # 重新载入服务定义
sudo systemctl enable --now kafka                 # 新实例启用自启并启动
systemctl status kafka --no-pager -l              # 查看启动结果
sudo journalctl -u kafka -n 100 --no-pager         # 检查日志与权限错误

滚动维护一次只操作一个节点：确认无不可用分区、ISR 和容量正常 → 保存配置 → 优雅停止 → 更新 → 启动 → 等待副本追上 → 验证收发和错误率 → 再进行下一个。Controller 还要保证多数派存活。

sudo systemctl stop kafka                         # 在已确认的目标节点优雅停止
sudo systemctl start kafka                        # 完成该节点维护后启动
sudo journalctl -u kafka -n 100 --no-pager         # 确认恢复过程无持续错误
bin/kafka-topics.sh --bootstrap-server "$BS" "${ADMIN[@]}" --describe --under-replicated-partitions # 等待该次维护带来的ISR不足消退

示例：重启不会重新 format 数据目录。版本升级还涉及客户端兼容性、metadata.version、事务/组协议等条件；先按目标版本升级文档完成预检和回退设计，不能把换二进制包等同于完整升级。

11. 安全和监控：分清问题在哪一层

报错 检查位置
SSLHandshakeException 信任链、有效期、SAN、监听协议、双向证书要求
SaslAuthenticationException SASL机制、用户、凭据文件、服务端认证配置
TopicAuthorizationException 实际 principal 对该 Topic 的操作权限
GroupAuthorizationException 该 principal 对目标 group.id 的权限
TransactionalIdAuthorizationException transactional.id 对应的授权

KRaft ACL 使用 org.apache.kafka.metadata.authorizer.StandardAuthorizer。不要直接复制旧版 ZooKeeper authorizer 配置。已有安全集群由管理员使用管理凭据执行最小授权：

bin/kafka-acls.sh --bootstrap-server "$BS" "${ADMIN[@]}" --list --topic "$TOPIC" # 查看目标主题ACL
bin/kafka-acls.sh --bootstrap-server "$BS" "${ADMIN[@]}" --list --group "$GROUP" # 查看消费者组ACL
bin/kafka-acls.sh --bootstrap-server "$BS" "${ADMIN[@]}" --add --allow-principal User:orders-reader --operation Read --operation Describe --topic "$TOPIC" # 示例：授予主题读取权限
bin/kafka-acls.sh --bootstrap-server "$BS" "${ADMIN[@]}" --add --allow-principal User:orders-reader --operation Read --group "$GROUP" # 示例：授予指定组读取权限

示例：orders-reader 必须是认证后实际得到的 principal 名称；TLS DN 映射可能改变它。权限变更后用这个用户验证，而非继续使用管理员。认证、加密、授权分别配置，不能用开放全部 ACL 或把业务用户设为 super user 来处理授权错误。参照 ACL 配置和 TLS 配置。

监控同时覆盖业务与基础设施：端到端处理延迟、错误/重试率、各分区 Lag 与消息年龄、ISR/离线分区、请求分段耗时、磁盘剩余时间、GC、网络重传、Controller quorum 健康。按版本和角色选择指标，详见 Kafka 监控指标。

已有 Prometheus/JMX Exporter/Grafana 体系优先复用。启用远程 JMX 时配置认证、TLS 和网络访问范围；不要把无认证 JMX 暴露出去。监控 Kafka 端收发成功还不够，应有独立的轻量端到端探测，验证业务链路实际可用。

12. 容量、压测和跨集群恢复

容量先用真实压缩后的流量测量：单副本写入速率 × 留存秒数 × 副本数，再加索引、内部主题、段回收波动、迁移空间和故障余量。热点分区单独估算；总容量够不代表最满那块盘够。网络还要计算副本同步、每个消费者组读取与跨集群复制。

只在专用测试主题和批准的窗口压测，下面前提是已创建 kafka-bench，且其留存与容量可控：

bin/kafka-producer-perf-test.sh --topic kafka-bench --num-records 100000 --record-size 1024 --throughput 1000 --producer-props bootstrap.servers="$BS" acks=all enable.idempotence=true compression.type=lz4 # 固定输入速率测试，约100MiB原始载荷

示例：安全集群另传 --producer.config "$CLIENT_CONFIG"。用符合生产可靠性要求的配置，记录 p95/p99、错误率、ISR、磁盘和 CPU；不要只用平均延迟或一次峰值承诺 SLA。

跨集群使用 MirrorMaker 2 等复制链路时，先定义要复制的主题、方向、命名规则和故障切换方案。目标分区数、授权、消费位移转换以及恢复顺序都要验证；不能把源集群 offset 原样当成目标 offset，也不要盲目复制内部位移主题覆盖目标状态。

复制不等于备份：误删和错误数据可能沿复制链路传播。保留独立恢复手段，并演练停止源写入、等待复制、转换消费位移、切换入口和验证业务去重的完整过程。双向复制还需防循环。实现细节参照 跨集群复制。
