容器运维

Kubernetes 常用运维命令

知知行笔记·约 26 分钟阅读
kuberneteskubectlk8soperationstroubleshooting

使用 kubectl 检查集群和应用状态、查看日志、发布与回滚服务，以及排查配置、存储、网络和节点问题。

操作前确认集群和命名空间，将示例中的 demo、demo-api、Pod、节点名、镜像及地址替换为实际值。读取 Secret、进入容器、修改配置、重启和删除资源需要对应 RBAC 权限。

1. 集群、上下文和命名空间

安装 kubectl：选择版本、下载、校验及普通用户安装

kubectl只是客户端，不会创建Kubernetes集群。先向管理员确认API Server版本，客户端版本一般应在服务端前后一个小版本内；不要在不知集群版本时直接下载最新版。

CentOS 7可以在已有兼容客户端上维护集群，但客户端可执行不代表这台机器适合安装新版Kubernetes节点。旧客户端、内核和运行时分别核对；本机工具不兼容时在受维护的管理机上使用匹配集群版本的kubectl，不临时替换生产节点组件。详见版本偏差规则。

下面演示Linux amd64下载流程，v1.35.0仅为固定版本示例，应改为与集群匹配、经批准的补丁版本；uname -m若为aarch64，下载架构改为arm64。

uname -m
mkdir -p "$HOME/downloads/kubectl"
cd "$HOME/downloads/kubectl"
kubectl_version='v1.35.0' # 按集群版本调整
kubectl_arch='amd64'     # 按实际架构调整
curl -fLO "https://dl.k8s.io/release/$kubectl_version/bin/linux/$kubectl_arch/kubectl"
curl -fLO "https://dl.k8s.io/release/$kubectl_version/bin/linux/$kubectl_arch/kubectl.sha256"
printf '%s  kubectl\n' "$(cat kubectl.sha256)" | sha256sum --check

示例：最后应显示 kubectl: OK。任一步下载失败或校验不符就停止，不安装该文件。

上面的 | 把 printf 生成的“校验值＋文件名”作为标准输入传给 sha256sum --check，不需要再创建一个校验清单文件。$(cat kubectl.sha256) 则是命令替换，先读取校验文件内容，再放到 printf 的参数中。

校验成功后，有管理员授权可安装到系统路径：

sudo install -o root -g root -m 0755 kubectl /usr/local/bin/kubectl
kubectl version --client

示例：没有sudo时可改为个人目录，不需要改变系统权限：

mkdir -p "$HOME/.local/bin"
install -m 0755 kubectl "$HOME/.local/bin/kubectl"
export PATH="$HOME/.local/bin:$PATH"
kubectl version --client

示例：export仅对当前shell及后代生效；长期使用将同样PATH配置放进自己所用shell的配置文件，避免重复追加。集群访问还需要管理员发放的个人kubeconfig，不能复制他人的cluster-admin凭据。

KUBECONFIG="$HOME/.kube/demo-config" kubectl config current-context
KUBECONFIG="$HOME/.kube/demo-config" kubectl -n demo auth can-i get pods

示例：这里假设管理员提供的配置已安全放在该路径。能输出客户端版本不代表已有集群访问权；本机sudo也不能解决Kubernetes RBAC的Forbidden。步骤见 kubectl官方安装说明。

kubectl version --client                 # 本机客户端版本
kubectl version                          # 客户端与服务端版本
kubectl config get-contexts              # 上下文列表
kubectl config current-context           # 当前集群上下文
kubectl cluster-info                     # 集群服务信息
kubectl get namespaces                   # 命名空间
kubectl api-resources                    # 实际可用资源类型
kubectl explain deployment.spec          # 资源字段说明

示例：current-context 返回测试集群名后，才在该集群排查。API资源以集群实际提供的为准，不假设每个集群都安装了 Ingress Controller、metrics-server 或自定义资源。

kubectl config use-context demo-cluster                  # 切换默认上下文
kubectl config set-context --current --namespace=demo    # 更改当前上下文默认命名空间
kubectl --context demo-cluster -n demo get pods          # 单次显式指定目标

示例：脚本或多集群运维优先显式使用 --context 与 -n，避免默认目标变化后误操作。kubeconfig 可能含凭证，不要直接公开或上传。

2. 全局巡检与资源列表

kubectl get nodes -o wide                   # 节点、版本与地址
kubectl get pods -A -o wide                 # 全集群 Pod
kubectl -n demo get deploy,sts,ds,job,cronjob # 常见工作负载
kubectl -n demo get svc,ingress              # 服务和入口
kubectl -n demo get pvc                      # 存储申请
kubectl -n demo get events --sort-by=.metadata.creationTimestamp # 最近事件顺序
kubectl -n demo get pods -w                  # 持续观察变化

示例：READY 1/2 表示两个容器中只有一个就绪；Running 不等于所有容器或业务都正常。get all 不包含全部资源，ConfigMap、Secret、PVC、Ingress 等需单独查询。-w 按 Ctrl+C 退出观察。

3. 定位应用与查看详情

kubectl -n demo get pods -l app=demo-api -o wide # 按实际标签定位
kubectl -n demo describe deployment demo-api   # 工作负载详情与事件
kubectl -n demo describe pod demo-api-abc-123   # 调度、镜像、探针、退出原因
kubectl -n demo get pod demo-api-abc-123 -o yaml # Pod最终配置
kubectl -n demo get pod demo-api-abc-123 -o jsonpath='{.metadata.ownerReferences}' # 控制器归属

示例：describe pod 底部 Events 中出现 FailedMount，先查卷和权限；出现 FailedScheduling，先查资源、污点、亲和性和PVC，而非直接删Pod。YAML可能含字面量环境变量等敏感配置，分享前脱敏。

4. 日志：当前、上次、多个容器

kubectl -n demo logs demo-api-abc-123 -c app --tail=100 --timestamps # 指定容器
kubectl -n demo logs demo-api-abc-123 -c app --since=30m             # 最近30分钟
kubectl -n demo logs demo-api-abc-123 -c app --previous             # 上次退出实例
kubectl -n demo logs -f demo-api-abc-123 -c app --tail=100           # 实时追踪
kubectl -n demo logs -l app=demo-api --all-containers=true --prefix=true --tail=100 # 标签聚合

示例：Pod出现 CrashLoopBackOff，优先看 --previous，当前实例可能尚未打印完整错误。init容器日志也用其名字指定 -c。上次日志是否还在取决于容器与节点保留情况，不是永久历史；长期检索需要集中日志。

日志跟踪按 Ctrl+C 只结束查看。logs 读取标准输出与错误，不主动读取应用在PVC中的日志文件。

5. 容器命令、文件复制和临时调试

kubectl -n demo exec -it demo-api-abc-123 -c app -- sh # 进入容器
kubectl -n demo exec demo-api-abc-123 -c app -- cat /etc/resolv.conf # DNS配置
kubectl -n demo cp demo-api-abc-123:/tmp/report.txt ./report.txt -c app # 拷出
kubectl -n demo cp ./config-test.yaml demo-api-abc-123:/tmp/config-test.yaml -c app # 拷入临时位置

示例：-- 后面是容器内命令；镜像没有shell时 sh 也不能用。kubectl cp 通常要求容器内有 tar，不适合当作完整备份方案；容器文件修改可能随重建丢失。

kubectl -n demo debug pod/demo-api-abc-123 -it \
  --image=busybox:1.37 --target=app -- sh

示例：给目标Pod添加临时调试容器，需要集群功能、运行时和权限支持；会修改Pod，可能被安全策略拒绝。使用受信任的调试镜像，结束shell不代表调试容器记录从Pod规格中消失。

6. CPU、内存、限制与 OOM

kubectl top 报错：检查指标服务，不是再装一个top命令 
kubectl get apiservice v1beta1.metrics.k8s.io
kubectl -n kube-system get deployment metrics-server
kubectl -n kube-system logs deployment/metrics-server --tail=100

示例：资源不存在或指标API不可用时，需要集群管理员检查或部署与集群兼容的 metrics-server。部署名称/命名空间可能不同，按实际安装查找。不要直接把最新版清单套进旧集群，或为了绕过证书问题默认加跳过kubelet证书校验的参数。

kubectl top nodes                                  # 节点资源
kubectl -n demo top pods --containers              # 容器资源
kubectl -n demo describe pod demo-api-abc-123       # requests/limits、last state
kubectl describe node worker-1                     # 可分配资源、已分配请求、压力
kubectl -n demo get resourcequota,limitrange        # 命名空间约束
kubectl -n demo get hpa                            # 自动扩缩容状态

示例：top 需要资源指标API（通常由metrics-server提供），不是历史监控。OOMKilled 结合内存limit、节点压力和应用峰值判断；CPU限制可能导致节流，不一定表现为进程退出。

7. 清单校验、比较与应用

kubectl apply --dry-run=client -f deployment.yaml -o yaml # 客户端预览
kubectl apply --dry-run=server -f deployment.yaml         # 服务端校验，不落库
kubectl diff -f deployment.yaml                          # 对比现有配置
kubectl apply -f deployment.yaml                         # 应用变更
kubectl -n demo rollout status deployment/demo-api --timeout=180s # 等待滚动结果

示例：清单中明确 metadata.namespace: demo，先校验和diff，再apply。diff 有差异时退出码为1，不必把它当成命令故障；输出可能含配置内容，分享前检查敏感值。dry-run不验证实际业务或外部数据库。

如果资源由 Helm、Operator 或 GitOps 管理，应更新其源配置，临时 edit/apply 可能被控制器覆盖。

8. 更新、重启、回滚与扩缩容

kubectl -n demo set image deployment/demo-api app=registry.example.com/team/demo-api:1.1.0 # 更新镜像
kubectl -n demo rollout status deployment/demo-api --timeout=180s # 查看发布结果
kubectl -n demo rollout history deployment/demo-api              # 修订历史
kubectl -n demo rollout history deployment/demo-api --revision=2 # 指定修订
kubectl -n demo rollout undo deployment/demo-api --to-revision=2 # 回滚

示例：app 是容器名，必须与清单一致；镜像地址为占位示例。回滚依赖保留的修订，只回滚Pod模板，不会恢复数据库、独立ConfigMap或PVC中的数据。

kubectl -n demo rollout restart deployment/demo-api    # 触发滚动重建
kubectl -n demo rollout pause deployment/demo-api      # 暂停Deployment滚动
kubectl -n demo rollout resume deployment/demo-api     # 恢复
kubectl -n demo scale deployment/demo-api --replicas=3 # 改副本数
kubectl -n demo get hpa demo-api                       # 核对HPA

示例：这些操作可能影响流量与容量，按需单独执行。HPA可再次调整人工设置的副本数；暂停滚动不等于暂停现有业务。滚动可用性取决于副本、探针、更新策略和容量，不能默认零中断。

删除受控制器管理的Pod通常会被重建，不是永久停服；缩容到0也要考虑HPA或其他控制器。

9. ConfigMap、Secret 和配置生效

kubectl -n demo get configmap                      # ConfigMap列表
kubectl -n demo describe configmap demo-config     # 内容与键，分享前检查
kubectl -n demo get secret                         # Secret名称与类型，不解码
kubectl -n demo get secret demo-secret -o jsonpath='{.type}' # 仅查询类型
kubectl -n demo create configmap demo-config --from-file=application.yaml --dry-run=client -o yaml

示例：最后一条只生成清单，不创建资源；可通过项目审批流程应用。Secret的base64不是加密，不把解码结果、完整Secret YAML或带秘密的命令记录公开。

配置注入方式 更新后的常见行为
环境变量 已运行进程不会自动更新，需要重建Pod
普通投射卷 通常最终更新，有传播延迟；应用仍需重新读取
subPath 挂载 不会自动接收对应ConfigMap/Secret更新
immutable对象 不能直接修改内容，需要采用新对象等方式

示例：ConfigMap已更新而应用还是旧配置，先查注入方式及应用重载能力，再决定是否滚动重启，不直接假设更新失败。

10. Service、DNS、EndpointSlice 与 Ingress

kubectl -n demo get svc demo-api -o wide          # Service类型与端口
kubectl -n demo describe svc demo-api            # selector、端口、后端信息
kubectl -n demo get endpointslices -l kubernetes.io/service-name=demo-api -o wide
kubectl -n demo get pods --show-labels           # 核对 selector
kubectl -n demo get ingress                     # 入口地址
kubectl -n demo describe ingress demo-web        # 规则、控制器事件
kubectl -n demo get networkpolicy               # 网络访问限制

示例：Service没有可用后端时，检查selector是否匹配、Pod是否Ready、targetPort 是否正确。优先使用EndpointSlice，旧Endpoints接口已逐步弃用。get networkpolicy 无资源不代表外部防火墙或平台策略都放行。

从已有且具备工具的业务Pod内部验证：

kubectl -n demo exec demo-api-abc-123 -c app -- nslookup cache.demo.svc.cluster.local

示例：此域名采用常见的 cluster.local 集群域，实际域可不同。镜像无nslookup时，使用已批准的调试容器。先查DNS，再查目标端口、协议、认证、网络策略；同Pod内容器可通过localhost通信，跨Pod不能这样理解。

11. 临时端口转发

kubectl -n demo port-forward service/demo-api 18080:8080 --address=127.0.0.1

示例：8080必须是Service已有端口；保持命令运行，在本机另一个终端访问：

curl -i --connect-timeout 3 --max-time 5 http://127.0.0.1:18080/health

示例：/health 为应用实际提供的只读检查路径。转发成功不代表Ingress、LoadBalancer或正常Service数据路径都正常；此功能用于临时排查，Pod替换可能使会话中断，按 Ctrl+C 停止转发。

12. PVC、PV 与存储故障

kubectl -n demo get pvc -o wide              # 申请状态与容量
kubectl -n demo describe pvc demo-data       # 绑定和挂载相关事件
kubectl get pv                              # 集群级卷
kubectl describe pv demo-pv                 # 回收策略、绑定、卷属性
kubectl get storageclass                    # 存储类与绑定模式

示例：PVC Pending 可能是供给失败、容量、存储类或 WaitForFirstConsumer 等待调度；Bound 也不代表节点挂载成功，要结合Pod事件。访问模式、挂载权限、文件系统和存储后端状态分别核对。

PVC删除可能触发底层卷回收，受PV回收策略及存储实现影响。不要通过删PVC、改finalizer强行解决挂载问题。StatefulSet的扩缩容和卷保留行为也受其配置影响，操作前查清数据生命周期。

13. Job 与 CronJob

kubectl -n demo get jobs,cronjobs                 # 批处理任务
kubectl -n demo describe job report-job           # 完成、失败与重试
kubectl -n demo logs job/report-job --tail=100    # 某个任务Pod的日志
kubectl -n demo get pods -l job-name=report-job   # 定位全部任务Pod
kubectl -n demo create job report-manual-001 --from=cronjob/report # 手动触发新任务

示例：手动触发会实际执行业务，须确认幂等和执行范围；名字需唯一，不能把只读巡检和执行任务混为一谈。多个Pod时分别查看日志。

kubectl -n demo patch cronjob report -p '{"spec":{"suspend":true}}'  # 暂停后续调度
kubectl -n demo patch cronjob report -p '{"spec":{"suspend":false}}' # 恢复调度

示例：暂停CronJob不会自动终止已经创建的Job；恢复时需考虑错过的调度、并发策略和业务重复执行。以上JSON引号按Linux shell写法，Windows shell需相应调整。

14. 节点排障与计划维护

kubectl describe node worker-1                         # Conditions、污点、事件
kubectl get pods -A --field-selector spec.nodeName=worker-1 -o wide # 节点上的Pod
kubectl -n kube-system get pods -o wide                # 系统组件
kubectl get pdb -A                                    # 驱逐预算

示例：节点 NotReady 时查kubelet、运行时、网络和磁盘压力。节点上有状态服务、local PV或emptyDir时先确认迁移与数据影响。

维护操作按步骤执行：

kubectl cordon worker-1                      # 禁止新调度，不迁移已有Pod
kubectl drain worker-1 --ignore-daemonsets --timeout=10m # 驱逐普通工作负载
kubectl uncordon worker-1                    # 维护验收后恢复调度

示例：先确认有其他节点容量且业务可迁移。drain受PDB等约束；默认遇到emptyDir或不受控制器管理的Pod可能中止。不要为通过命令直接加 --force、--delete-emptydir-data 或绕过驱逐的参数。

节点缺少 crictl：安装 cri-tools 并配置运行时端点

仅在需要排查的Kubernetes节点操作，不在普通办公电脑上假设存在运行时socket。优先沿用集群维护的软件源与对应版本。

command -v crictl
# Ubuntu / Debian，前提是已配置与集群匹配的Kubernetes软件源
apt-cache policy cri-tools
sudo apt-get install cri-tools
# RHEL系使用其匹配源时，改选：
# dnf info cri-tools
# sudo dnf install cri-tools
# CentOS 7已有节点：仅在现有批准的集群源中查询并选择匹配版本
# yum --showduplicates list cri-tools
# sudo yum install cri-tools-具体版本 # 替换成查询出的版本，不自动升级到最新版

示例：未配置源时不要直接加入另一小版本仓库；由管理员按集群发行方式提供匹配包，或按照 cri-tools安装说明 下载对应架构的正式发行文件并验证校验和。

containerd节点的单次查询示例：

sudo crictl --runtime-endpoint unix:///run/containerd/containerd.sock info
sudo crictl --runtime-endpoint unix:///run/containerd/containerd.sock ps -a

示例：socket路径以实际containerd配置为准；CRI-O、K3s、RKE2等可能使用不同端点。确认后可由管理员配置 /etc/crictl.yaml，不要把私有socket开放成所有用户可写。

登录目标节点后的只读检查，需匹配实际运行时：

systemctl status kubelet --no-pager -l         # kubelet状态
sudo journalctl -u kubelet -b -n 100 --no-pager # 日志
systemctl status containerd --no-pager -l      # 使用containerd时
sudo crictl ps -a                             # CRI容器，需已正确配置endpoint
sudo crictl pods                              # Pod沙箱
df -h                                        # 磁盘空间
df -i                                        # inode

示例：现代Kubernetes不要求使用Docker，不能默认通过 docker ps 看见所有Pod容器。先确认节点运行时与crictl连接端点，不用运行时命令绕过Kubernetes直接删除业务容器。

15. RBAC、ServiceAccount、标签与污点

kubectl auth can-i get pods -n demo             # 当前身份能否查询
kubectl auth can-i create pods/exec -n demo     # 能否进入容器
kubectl -n demo get serviceaccounts,roles,rolebindings # 命名空间权限配置
kubectl get clusterroles,clusterrolebindings    # 集群权限配置
kubectl -n demo get pods --show-labels          # Pod标签
kubectl get nodes --show-labels                 # 节点标签

示例：Forbidden 先确认身份、context和RBAC，不能通过临时授予cluster-admin来替代定位。can-i只是当前权限判断，仍可能被准入策略约束。

kubectl label node worker-1 workload=batch          # 新增调度相关标签
kubectl label node worker-1 workload-               # 移除标签
kubectl taint node worker-1 dedicated=batch:NoSchedule # 增加污点
kubectl taint node worker-1 dedicated:NoSchedule-    # 删除污点

示例：标签和污点可能改变后续调度，不作为无害的查询命令。NoSchedule 一般阻止不容忍的新Pod；NoExecute 还可能驱逐已有Pod，不能随意替换。

16. 删除操作与排障顺序

kubectl -n demo delete pod demo-api-abc-123 # 优雅删除指定Pod，可能被重建
kubectl -n demo delete -f obsolete.yaml     # 删除清单对应资源，逐项核对

示例：删除前核对对象、控制器和数据归属；删除namespace会删除其中大量资源，不能当成重启。强制删除Pod不保证原节点上的进程已真正结束，有状态服务可能出现双写，避免常规使用。

现象 排查顺序
Pending describe事件 → requests/容量 → 污点/亲和性 → PVC
ImagePullBackOff 镜像名/digest → 凭证 → 节点网络/DNS/证书 → 架构
CrashLoopBackOff previous日志 → 退出原因 → 配置/权限 → 依赖 → 探针
OOMKilled limit → 峰值与泄漏 → 节点压力 → 应用内存配置
Running但不Ready readiness结果 → 应用监听 → 配置与依赖
Service不可达 Pod就绪 → selector → EndpointSlice → targetPort → 网络策略
Ingress 502/504 入口控制器 → Service → 后端端口与协议 → 应用超时
Node NotReady kubelet → 运行时 → 网络插件 → 磁盘/内存/证书
FailedMount PVC/PV → 节点事件 → 存储驱动 → 权限和后端
Forbidden 当前context与身份 → RBAC → 准入限制

liveness失败可能重启容器，readiness失败影响流量就绪，startup探针保护启动阶段。不要把业务暂不可用直接等同于应该删Pod重启。

17. 发布后的验收清单

kubectl -n demo rollout status deployment/demo-api --timeout=180s
kubectl -n demo get pods -l app=demo-api -o wide
kubectl -n demo get events --sort-by=.metadata.creationTimestamp
kubectl -n demo logs deployment/demo-api --tail=100

示例：确认副本就绪、重启次数不持续增长、无新增关键告警，并从真实入口验证只读接口和关键业务。最后一条可能只选择一个Pod，多个副本需结合标签聚合或集中日志检查。

命令和可用参数以客户端与集群版本为准，详见 kubectl 官方速查。另见 Docker 与 Compose 运维、服务器常用命令。
