Linux 性能瓶颈排查与优化

知知行笔记·2026-11-04·约 15 分钟阅读
linuxperformancecpuionetworktroubleshooting

接口慢、机器卡、吞吐下降时，先确定慢在哪里，再找占用资源的进程和操作。下文PID 24680、网卡 eth0、域名 app.example.com、IP 192.0.2.10 都需要替换。

1. 服务慢了，先用一分钟判断方向

date
uptime
free -h
vmstat 1 5
top

示例：vmstat后几行的 r 持续超过可用CPU数量、us很高，优先查计算热点；b增多、wa升高则查I/O和阻塞。第一行通常是开机以来的平均值，不能当成刚发生的变化。top按 q 退出，也可以按Ctrl+C。

同时记录故障时间、请求量、错误率、P95/P99延迟，以及最近发布、流量和数据量变化。平均响应时间正常，也可能有少量请求非常慢。

现象 下一步 判断时注意
CPU忙 看每核、每进程、热点函数 整机均值会掩盖单核跑满
load高但CPU不忙 看D状态、存储、回收 load不是CPU使用率
内存紧张 看Available、换页、OOM free低不等于内存不足
磁盘慢 看延迟、队列、进程读写 不能只看util
连接慢、偶发超时 拆分DNS、建连、TLS、响应 本地快不等于远端链路正常
资源都不忙但服务慢 看线程池、锁、连接池和下游 等待可能发生在应用内部
仅容器慢 看配额、节流、探针和容器内依赖 宿主机空闲不代表容器资源充足
安装诊断工具：按发行版展开查看 
# Ubuntu / Debian，按需安装
sudo apt-get update
sudo apt-get install sysstat lsof strace tcpdump dnsutils iproute2 ethtool

# RHEL / Rocky / AlmaLinux，按需安装
sudo dnf install sysstat lsof strace tcpdump bind-utils iproute ethtool perf

# 检查常用工具是否可用
command -v pidstat iostat mpstat sar lsof strace tcpdump dig perf

示例：安装sysstat后可使用 pidstat、iostat、mpstat、sar。安装并不代表已经有历史采样；sar历史数据需要事先启用采集。旧系统可能使用yum；Ubuntu的perf包需要与发行版和内核版本匹配。

当前用户不是root时，先直接运行查看命令。查看其他用户进程、内核日志、抓包和性能采样可能需要在命令前加 sudo；没有sudo权限时请管理员执行对应命令，不要直接放宽整个系统的权限设置。

2. CPU高：找到哪一核、哪个线程、哪段代码

# 看每个CPU，而不只是整机平均值
mpstat -P ALL 1 5

# 找CPU占用高的进程
pidstat -u 1 5

# 看目标进程的线程
pidstat -u -t -p 24680 1 5

示例：只有一核接近100%，其他核空闲，可能是单线程热点或流量集中；目标进程只有一个线程忙，增加服务器核数未必改善。

指标 优先调查
us高 计算、循环、序列化、正则、运行时GC
sy高 系统调用、内存回收、线程切换、内核路径
soft高 网络包速率、中断分布、转发
st高 虚拟机CPU被宿主机占用，需要结合云平台或宿主机证据

需要代码热点时做短时采样：

sudo perf record -F 49 -g -p 24680 -o /tmp/demo-cpu.data -- sleep 15
sudo perf report -i /tmp/demo-cpu.data

示例：热点长期集中在某个解析函数，就检查输入规模和重复解析；热点在GC则结合堆占用、分配速率、GC日志分析。Java等JIT程序可能需要运行时专用工具或符号配置，无法解析的地址不能直接当结论。

**处理：**减少热点路径上的重复工作、无效轮询和过量分配；并行能力不足时再考虑拆分任务。短时采样也有开销，先限定进程和时长。

**复查：**在相近吞吐下比较CPU、P99、错误率和每请求CPU成本，避免通过少处理请求换来“CPU下降”。

3. load高，CPU却不高：区分阻塞与僵尸

ps -eo pid,ppid,stat,wchan:28,comm --sort=stat
vmstat 1 5
iostat -xz -y 1 5

示例：大量 D 状态进程且 wchan指向I/O等待，继续查磁盘、NFS、驱动或内存回收；Z 是进程已退出但父进程未回收，通常不消耗CPU，不能把它当作计算热点。

**处理：**D状态先恢复依赖的存储或内核路径，kill -9也可能要等内核等待结束才生效。Z状态应查PPID对应的父进程为什么没有回收子进程，安排修复或重启父服务。

**复查：**等待队列和D状态数量下降、业务延迟恢复。僵尸问题则看数量是否停止增长、父进程是否正常回收。

4. sy高、切换多，但看不到持续占CPU的进程

vmstat 1 5
pidstat -w -t 1 5
ps -eLf | wc -l

示例：cs明显高于平时且线程数激增，可能是线程池过大、锁竞争或大量短任务；进程不断启动退出时，一次top截图可能抓不到。

**处理：**对照同等流量下的正常基线，查频繁调用外部命令的脚本、进程创建循环、过量线程以及高频锁竞争。切换次数没有适用于所有机器的固定告警值；pidstat的自愿切换多也可能只是正常等待。

**复查：**线程数、创建速率和每请求切换成本回落，同时吞吐和延迟改善。短命进程需要进程创建事件采样时，使用当前发行版支持的追踪工具，并限定时长。

5. 内存低、Swap已使用：先看现在是否有压力

free -h
swapon --show
vmstat 1 5
pidstat -r -p 24680 1 5

示例：Swap有历史占用，但 si/so长期接近0、Available稳定、延迟正常，不代表正在频繁换页。反之，Available持续下降且换入换出、major fault和延迟同步升高，需要查工作集和内存限制。major fault也可能来自文件读盘，不能单独认定为Swap问题。

**处理：**先定位增长的是进程堆、文件缓存、共享内存还是内核内存；容器另查cgroup限制。减少无界缓存、批量大小和并发峰值，必要时扩容。内存紧张时直接 swapoff 可能加剧压力，不把清缓存或关Swap作为通用修复。

**复查：**持续比较Available、换页速率、OOM事件和业务延迟。进一步分类见内核内存排查。

6. 磁盘I/O高：定位设备、进程和具体操作

# 看设备延迟、队列和读写量；-y跳过开机以来的首份累计报告
iostat -xz -y 1 5

# 找进程读写来源
pidstat -d 1 5

# 看目标进程打开的文件
sudo lsof -p 24680

示例：日志目录写入明显增加，同时目标进程写速率高、设备延迟上升，先检查日志级别和重复报错。读请求变成大量写入，也可能是临时文件、排序落盘或请求路径中意外写数据。

await是已完成I/O请求的平均耗时，需结合读写类型和队列观察；多队列NVMe、RAID和虚拟磁盘不能仅凭 %util=100 断言全部性能已用尽。网络文件系统还要查远端，不能只看本地块设备。

需要确认系统调用时，短时观察目标进程：

sudo timeout 10s strace -f -c -p 24680

示例：fsync、文件创建和删除异常频繁，回查业务是否每次请求都落盘或生成临时文件。-c输出汇总统计；-f跟踪线程与后续子进程。strace会影响被观察程序，繁忙服务应缩短采样或在复现环境使用；被timeout结束时退出码124通常表示采样到时。

**处理：**修复日志风暴，合并小写入，减少重复读写和临时文件。调整刷盘频率前明确持久性要求，不能直接关闭fsync来换速度。

**复查：**比较同等业务量下读写次数、设备延迟、队列、应用P99及异常重启后的数据可靠性。

7. 磁盘满、inode满，或删了文件空间没回来

df -hT
df -i
sudo du -xhd1 /var/log
sudo lsof +L1

示例：df -i为100%但容量还有空余，可能是大量小文件耗尽inode；lsof +L1看到大日志仍被进程打开，说明文件名删除后空间尚未释放。du -x限制在同一文件系统，避免扫进其他挂载盘。

**处理：**确认文件归属和保留策略后清理历史文件；对已删除仍打开的日志，让应用按文档重新打开日志或安排重启，并修正轮转方式。不要直接删数据库文件、活动日志或容器数据目录。

**复查：**容量和inode恢复，相关文件句柄释放，应用能继续正常写入。

8. CPU、磁盘都空闲，接口依然慢

ps -L -p 24680 -o pid,tid,stat,wchan:28,comm
ss -tanp

示例：线程多数在等待，并不能直接判为死锁。可能在等连接池、锁、下游响应或队列；大量 futex 等待也可能是空闲线程的正常行为。

**处理：**把总耗时拆成排队、业务执行、SQL、缓存、外部HTTP几段；结合线程栈、链路追踪和连接池指标定位。连接池满时，先查连接持有过久、泄漏和下游变慢，再决定是否增加连接数。

**复查：**等待时长和队列长度降低，下游吞吐、错误率没有恶化。单纯扩大线程池可能把压力转移到数据库。

9. SQL或Redis拖慢请求

数据库先看慢查询、当前执行语句、锁等待和连接数。以MySQL为例，在已有连接中执行：

SHOW FULL PROCESSLIST;

示例：许多请求等待同一事务释放锁，应查阻塞事务的持有时间和访问顺序；同一SQL扫描量持续增长，应查索引、过滤条件、排序和分页，而非先扩大连接池。查看全部会话需要相应数据库权限。

Redis可先查看持久化状态、命令统计和慢日志：

# 默认本机端口；非本机实例补充实际-h、-p及TLS等参数
# --askpass交互输入密码，避免写入命令行历史
redis-cli --askpass INFO persistence
redis-cli --askpass INFO commandstats
redis-cli --askpass SLOWLOG GET 10

示例：本以为是纯读接口，命令统计却显示持续写集合，同时持久化和磁盘延迟升高，应检查实际请求路径。慢日志可能包含业务键或参数，转发前先脱敏；它主要记录命令执行耗时，日志为空不能排除网络和其他等待。

**处理：**优先修复大键、长命令、全量扫描、意外写入和慢SQL。生产排查避免直接执行 KEYS *、长时间MONITOR或无边界全量扫描。改变AOF刷盘策略前先确定允许丢失多少数据。

**复查：**对比命令/SQL耗时、连接等待、持久化状态与接口P99。Redis诊断指标可参考延迟排查说明。

10. HTTP慢：拆开DNS、TCP、TLS和首字节

curl -sS -o /dev/null --connect-timeout 3 --max-time 10 \
  -w 'dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} first=%{time_starttransfer} total=%{time_total}\n' \
  https://app.example.com/health

getent ahosts app.example.com
dig +tries=1 +time=2 app.example.com

示例：dns=1.2 connect=1.21 tls=1.24 first=1.30 total=1.30，说明大部分耗时在解析阶段。curl这些值是从请求开始累计计时，不能把connect和tls直接当作各阶段独立耗时；在无代理、无跳转、单次直连情况下可用相邻值相减辅助判断。

绕过DNS做对照，同时保留Host和TLS域名校验：

curl --resolve app.example.com:443:192.0.2.10 \
  --connect-timeout 3 --max-time 10 -I https://app.example.com/health

示例：指定地址明显变快，回查解析链路；两者都慢则继续查建连、TLS和应用。-I使用HEAD，需选择支持HEAD的接口；它适合连通性对照，不能替代真实业务请求的性能测量。

**处理：**核查解析服务可达性、域名记录、缓存和应用连接复用。DNS配置可能由NetworkManager、systemd-resolved或容器管理，不直接覆盖 /etc/resolv.conf，也不把内部域名统一交给公网DNS。

**复查：**重复测试冷/热解析和真实请求，比较错误率及各阶段分布，避免只凭一次curl得出结论。

11. 网络超时、丢包、重传：先保留连接证据

ss -tin
ip -s link show dev eth0
sar -n DEV,EDEV 1 5

# 只抓指定对端和端口，限制时长、包数与每包长度
sudo timeout 15s tcpdump -i eth0 -nn -s 128 -c 200 \
  -w /tmp/demo-network.pcap 'host 192.0.2.10 and tcp port 8080'

示例：网卡丢包计数持续增加且softirq集中在单核，检查网卡队列和处理能力；重传上升但本机网卡正常，需要结合另一端及中间链路定位。计数多为累计值，要看故障窗口的增量。

**处理：**按握手、请求发送、响应返回分段定位。抓包仍可能包含业务数据，应限制对象并妥善保管；抓包位置、网卡卸载和抓包自身丢包都会影响分析，单端出现“重传”标记不是最终根因证据。

小包交互固定增加延迟时，核对应用写入方式、Nagle和延迟确认的配合；先优化写入批次，再按连接测试TCP_NODELAY，不做全局盲改。队列和窗口分析见内核网络排查。

**复查：**连接成功率、RTT、重传增量和业务P99同时改善。

12. 经过NAT或容器网络后才出现连接失败

ss -s
sysctl net.netfilter.nf_conntrack_count net.netfilter.nf_conntrack_max
sudo journalctl -k --since '30 minutes ago' --no-pager | \
  grep -Ei 'conntrack|table full|drop'

示例：连接跟踪数量逼近限制，并出现 table full，优先查连接创建速率、短连接风暴和容量；相关sysctl不存在可能是模块未加载或当前环境不提供，不能因此直接认定网络故障。

**处理：**核查连接复用、NAT源端口容量、状态表和防火墙丢弃。扩大conntrack上限会增加内存消耗，需先估算容量并验证；不要直接关闭防火墙，也不要照搬已移除的 tcp_tw_recycle 等旧参数。

**复查：**在流量高峰确认新连接成功率、连接创建速率及状态表余量稳定。

13. 容器慢、启动慢：查限制与启动阶段

docker stats --no-stream
docker inspect --format '{{json .HostConfig}}' demo-api
docker logs --since 10m --tail 100 demo-api

# Kubernetes：top需要集群提供Metrics API
kubectl top pod demo-api-0 -n demo
kubectl describe pod demo-api-0 -n demo
kubectl logs demo-api-0 -n demo --since=10m --tail=100

示例：宿主机空闲，但容器CPU到配额后开始节流，或达到内存上限后OOM；另一类启动慢发生在拉镜像、挂载、DNS、初始化和依赖重试阶段，不应只看应用启动后的CPU。

在cgroup v2环境，先通过 /proc/<PID>/cgroup 查实际路径，再读取该目录的 cpu.stat、memory.events。nr_throttled、throttled_usec 和OOM等字段应比较两次采样的增量；不同层级和cgroup版本的接口不同，不拼一个固定路径套用所有容器。

**处理：**调整不合理的资源限制、初始化逻辑和依赖重试；结合实测启动时间配置startup/readiness/liveness探针。探针失败引发重复重启时，单纯加大重启次数不能解决问题。

**复查：**检查启动耗时各阶段、节流增量、OOM与重启次数，以及高峰期服务延迟。常用操作见Docker运维和Kubernetes运维。

14. 优化后怎样确认真的解决了

改动 至少比较这些结果
减少计算或分配 同吞吐下CPU、GC、P99、错误率
减少日志或落盘 每请求写入量、I/O延迟、持久性要求
调整缓存 命中率、内存上限、冷启动和失效时的延迟
调整线程池或连接池 排队、连接等待、下游负载、超时
调整网络队列或连接复用 建连速率、丢包、重传、总CPU、尾延迟
调整容器限制 节流、OOM、启动时间、节点其他服务表现

固定测试入口、并发、数据量和持续时间，保留改动前后的采样。一次只改一个主要变量，准备恢复方式；先在测试或灰度环境验证，再扩大范围。线上不直接运行无边界压测、磁盘写满测试或故障注入。

相关内容：内核问题排查、系统状态命令、服务器运维命令。
