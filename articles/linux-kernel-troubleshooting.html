Linux 内核问题排查与处理

知知行笔记·2026-11-04·约 14 分钟阅读
linuxkernelmemorypage-cacheoomtcptroubleshooting

遇到内存异常、系统卡顿、TCP重传或网络吞吐下降时，从这里按现象定位。示例PID 24680、服务 demo-api、网卡 eth0 和IP 192.0.2.10 均按实际值替换；采样命令默认只观察，不修改内核参数。

1. 先决定查哪条线

现象 优先检查 后续动作
load升高、进程卡住 vmstat、D状态、回收和I/O 区分CPU排队、存储等待、内存回收
内存越来越少 meminfo、进程RSS/PSS、Shmem、Slab 找到增长的内存类型，再查归属
机器有空闲内存，容器却OOM cgroup限制及事件 查容器边界，而非只查整机
短时延迟毛刺、sys CPU升高 回收、规整、THP、热点栈 按毛刺发生时间关联证据
新连接超时或排队 SYN队列、accept队列、应用处理能力 查连接阶段与监听队列
已连接但传输慢 RTT、重传、收发队列、窗口 查链路及收发两端
单核软中断高 网卡队列、中断分布、包速率 查流量分布和CPU余量 
date
uname -r
uptime
vmstat 1 5
free -h

示例：load升高且 vmstat 的 b 增多，就继续查阻塞和I/O；r持续高、CPU忙则转查CPU。不要看到load高就直接认定CPU不够。vmstat第一行通常包含开机以来的平均值，后续才是间隔采样。

安装排查工具与确认内核功能 
# Ubuntu / Debian，按需选包
sudo apt-get update
sudo apt-get install sysstat lsof tcpdump iproute2 ethtool numactl strace

# RHEL系，改选本机对应仓库中的包
# sudo dnf install sysstat lsof tcpdump iproute ethtool numactl strace perf

示例：sysstat提供sar、mpstat、pidstat、iostat；Ubuntu的perf通常来自匹配内核的linux-tools包，Debian常见包名为linux-perf，先核对系统和仓库。不要为运行perf安装不匹配的内核工具或修改整机安全限制。

command -v sar iostat numactl ethtool perf
perf --version
perf list

示例：PSI、smaps_rollup、tracepoint、cgroup文件依赖内核版本及配置。文件不存在或权限不足时，先确认功能支持与授权；CentOS 7等旧环境不能照搬新内核路径。

2. free很少，是否真的缺内存

grep -E '^(MemTotal|MemFree|MemAvailable|Cached|Buffers|AnonPages|Shmem|Slab|SReclaimable|SUnreclaim|Dirty|Writeback|SwapTotal|SwapFree):' /proc/meminfo
ps -eo pid,comm,rss,vsz --sort=-rss | head -n 15

示例：Cached较大但MemAvailable仍充足、业务正常，不需要“清缓存”。AnonPages增长查进程匿名内存；Shmem增长查共享内存/tmpfs；SUnreclaim增长查内核分配。| head只保留前15行输出。

**处理：**以可用内存、交换活动、业务延迟及增长趋势判断压力。不能直接把各进程RSS相加当成实际物理占用，共享页会重复计数；meminfo里的不同分类也不应简单相加。

**复查：**在同类负载下连续观察，确认MemAvailable不再持续下降、没有回收抖动和OOM。字段说明

3. load飙高、延迟变大：检查回收和脏页

sar -B 1 5
iostat -xz -y 1 5
grep -E '^(Dirty|Writeback):' /proc/meminfo
grep -E 'pgscan|pgsteal|allocstall|compact_stall|nr_dirty|nr_writeback' /proc/vmstat

示例：sar显示直接回收活动增加，且存储延迟和Dirty/Writeback在同一时间异常，才进一步怀疑回收/回写拖慢应用。/proc/vmstat里的许多值是累计计数，应间隔采样看增量，不能凭非零就认定正在故障。

**处理：**先减少批处理、突发写入和内存竞争，定位慢存储；有泄漏先处理泄漏。确需调整回收水位或脏页策略时，先记录现值，再按机器内存和存储能力做小范围试验，不直接套固定GB值或比例。

sysctl vm.min_free_kbytes vm.watermark_scale_factor
sysctl vm.dirty_background_ratio vm.dirty_ratio
sysctl vm.dirty_background_bytes vm.dirty_bytes

示例：这些命令只读取参数；旧内核可能没有其中某项。bytes与ratio控制方式需按内核规则选择，不能把两组值当作互不相关的限制随意同时配置。

**复查：**比较相近流量下的直接回收增量、I/O延迟和P95/P99；内存预留增加也会压缩应用可用容量。VM参数说明

4. 清过缓存后更慢：检查热点数据反复读盘

sar -B 1 5
pidstat -r -p 24680 1 5
pidstat -d -p 24680 1 5

示例：延迟升高同时出现主要缺页、读盘增加和缓存下降，要检查是否有人定时执行drop_caches，或其他大扫描挤出了热点缓存。主要缺页增加也可能涉及交换，需结合I/O和映射判断。

**处理：**取消无依据的周期清缓存，错开全盘扫描/备份和在线业务；对延迟敏感服务合理预热、隔离竞争和配置内存。不要为了让free数字变大而每天清Page Cache。

**复查：**观察热点请求的读盘量、缺页活动和延迟是否恢复；冷启动与缓存预热后的结果分别记录。

5. 进程RSS持续涨：区分堆、映射与共享页

grep -E 'VmRSS|VmSize|RssAnon|RssFile|RssShmem|VmSwap' /proc/24680/status
sudo cat /proc/24680/smaps_rollup
pmap -x 24680

示例：匿名常驻页持续增长时继续查堆/匿名映射；文件映射增长时查映射文件及生命周期。smaps_rollup中的PSS按共享比例分摊，更适合辅助判断归属；文件存在与读取权限以系统为准。

**处理：**先按应用语言使用堆分析、分配采样或运行时诊断，区分泄漏、缓存、分配器保留和负载增长；为异常服务限制流量并保留现场。生产上不直接启动全量Valgrind或无上限采样。

**复查：**在稳定负载和相近运行时长下，检查内存是否趋稳、GC后是否回落，以及错误率和延迟有没有恶化。

6. RSS不高、Shmem很大：查tmpfs与共享内存

grep '^Shmem:' /proc/meminfo
findmnt -t tmpfs
df -hT /dev/shm /run
sudo du -xhd1 /dev/shm /run
ipcs -m
sudo lsof +L1

示例：/run或 /dev/shm占用增长，且Shmem同步增长，即使应用已经关闭文件也可能保留数据；ipcs -m查看System V共享内存，不能覆盖所有共享内存类型。已删除但仍打开的文件还会占用空间。

**处理：**找到创建者与保留规则，再清理确认无用的临时文件或修复应用生命周期。不要清空 /run、盲目 ipcrm 或直接删除仍被业务使用的共享文件；tmpfs数据也不等于可随时丢弃。

**复查：**文件系统占用与Shmem均回落，并确认服务连接、锁、PID和共享数据仍正常。

7. 内核内存持续增长：查Slab、驱动与分配点

grep -E '^(Slab|SReclaimable|SUnreclaim|VmallocUsed|KernelStack|PageTables):' /proc/meminfo
sudo slabtop -o
lsmod
sudo journalctl -k -b -n 100 --no-pager

示例：SUnreclaim持续上升而进程占用相对稳定，记录slab对象类别的变化；必要时让内核/驱动维护人员进一步检查vmallocinfo与分配栈。某个值大并不足以证明泄漏。

**处理：**关联近期驱动、模块和内核更新，优先在测试环境复现并升级/回退问题组件；内核态泄漏不会因为重启一个Java进程就必然释放。kmemleak、kprobe等依赖构建选项与诊断成本，不在生产临时随意开启。

**复查：**对比相同负载下对象数量、内存增长斜率及错误日志，确认不是暂时缓存下降。

8. 服务被杀、容器OOM：先确认边界

sudo journalctl -k -b --no-pager | grep -Ei 'out of memory|oom-kill|killed process'
cat /proc/24680/cgroup
systemctl show demo-api -p ControlGroup -p MemoryMax

示例：整机还有空闲内存，不代表服务没有超出cgroup限额；OOM被杀的进程也不一定是最早引起压力的进程。结合时间、PID、分组和实际限额判断。

确认使用cgroup v2、ControlGroup为 /system.slice/demo-api.service 后读取：

cat /sys/fs/cgroup/system.slice/demo-api.service/memory.current
cat /sys/fs/cgroup/system.slice/demo-api.service/memory.max
cat /sys/fs/cgroup/system.slice/demo-api.service/memory.events

示例：关注 oom/oom_kill计数是否在事故期间增加，区分达到限额与实际杀进程；这些是累计事件，需结合分组生命周期。cgroup v1用其对应控制器文件，不能硬套v2路径。

**处理：**先减负载、处理泄漏或在容量允许时调整限额；JVM堆外、线程栈、页缓存等也需预留空间。避免给所有业务设置不可被OOM杀死的保护，导致压力转嫁给整机。

**复查：**观察同类负载下的memory.current、事件增量和业务状态。cgroup v2说明

9. 有空闲内存还卡顿：查NUMA和透明大页

numactl --hardware
numastat -p 24680
sysctl vm.zone_reclaim_mode
cat /sys/kernel/mm/transparent_hugepage/enabled
cat /sys/kernel/mm/transparent_hugepage/defrag
grep -E 'compact_stall|compact_fail|compact_success|thp_' /proc/vmstat

示例：NUMA可能出现某节点紧张、其他节点空闲；THP启用状态本身不是故障证据，需要结合毛刺期间规整活动、热点栈及应用特征。THP当前模式通常由方括号标出，新内核还可能有按页大小的独立策略。

**处理：**检查不合理绑核/绑内存和本地回收策略；THP按数据库/JVM等具体版本的建议及A/B测试选择，不对所有业务统一“always”或“never”。切换策略不代表现有大页立即全部拆分，也不自动持久化。

**复查：**比较延迟尾部、CPU、内存占用和吞吐，不能只看平均延迟。THP当前接口

10. 新连接超时：分清握手与accept排队

sudo ss -lntp 'sport = :8080'
ss -nt state syn-recv '( sport = :8080 )'
nstat -az TcpExtListenOverflows TcpExtListenDrops TcpExtSyncookiesSent
sysctl net.core.somaxconn net.ipv4.tcp_max_syn_backlog net.ipv4.tcp_syncookies

示例：监听socket的Recv-Q反映等待应用accept的连接，Send-Q对应其backlog上限含义；不能用ESTABLISHED连接的队列含义直接解释。ListenOverflows在事故窗口增加时，进一步查应用是否accept慢、线程池/依赖是否阻塞。

**处理：**先恢复应用消费连接的能力，控制突发连接并合理复用连接；确需增大backlog时，同时核对应用listen参数与系统上限。SYN压力、accept排队和连接跟踪耗尽是不同问题，不能靠调大一个参数包治。

**复查：**以连接成功率、建连耗时、队列趋势和溢出计数增量验收。TCP参数说明

11. 连接已建立但很慢：检查重传、RTT和收发窗口

ss -tin '( dport = :8080 or sport = :8080 )'
nstat -az TcpRetransSegs TcpOutSegs
ip -s link show dev eth0

示例：同一连接重传增加、RTT升高与请求变慢同时出现时，再定位链路；全机TCP重传计数不能直接算作某个服务的重传率。Recv-Q长时间积压要查应用是否及时读，Send-Q积压可能涉及对端接收、链路或发送阻塞。

**处理：**两端按同一时间窗口采样，结合抓包分辨发送迟、链路丢、接收不及时。零窗口通常应查接收方应用与内存压力；只换拥塞控制算法不会修复对端不读数据的问题。

**复查：**比较目标连接的重传、RTT、队列及业务延迟；不要把调整应用发送超时等同于直接改变TCP内核RTO。

12. 软中断占满单核：检查网卡队列和流量分布

mpstat -P ALL 1 5
sar -n DEV,EDEV 1 5
grep -E 'NET_RX|NET_TX' /proc/softirqs
cat /proc/interrupts
sudo ethtool -l eth0
sudo ethtool -k eth0
sudo ethtool -S eth0

示例：单核soft高且包速率/丢包同时异常，查中断是否集中、是否大量小包。softirqs/interrupts为累计值，要比较增量；ethtool能查看的队列/统计因驱动和虚拟网卡而异。

**处理：**先查异常流量和硬件RSS/IRQ分配，再评估RPS/RFS与offload。软件分流也消耗CPU，整机已忙时可能进一步压缩业务时间；不要默认把所有卸载特性关闭，或给所有网卡写相同CPU掩码。

**复查：**同时看总CPU、单核soft、丢包、吞吐和P99；分布变均匀但吞吐下降不算优化成功。网络扩展机制

13. 间歇性卡顿：用压力与短时采样留证

cat /proc/pressure/cpu
cat /proc/pressure/memory
cat /proc/pressure/io
sudo perf record -F 49 -g -p 24680 -o /tmp/demo-kernel-perf.data -- sleep 15
sudo perf report -i /tmp/demo-kernel-perf.data --stdio

示例：PSI反映资源争用造成的停顿趋势，不是资源使用率；系统级CPU的full不能照搬内存/I/O的解读。perf只在获得授权、可承受开销时对目标进程短时采样，-- sleep 15限定采样时段。PSI接口

**处理：**先把毛刺时间与回收、规整、软中断、业务指标对齐，再由热点栈决定是否深入tracepoint/eBPF。不要一开始就全机长期开高频追踪。

**复查：**在同等请求量下，确认停顿与业务尾延迟一起改善；保留内核版本、旧配置、变更项及回退方法。
