Linux 内核问题排查与处理

知知行笔记·约 37 分钟阅读
linuxkernelmemorypage-cacheoomtcptroubleshooting

遇到内存异常、系统卡顿、TCP重传或网络吞吐下降时，从这里按现象定位。示例PID 24680、服务 demo-api、网卡 eth0 和IP 192.0.2.10 均按实际值替换；采样命令默认只观察，不修改内核参数。

1. 先决定查哪条线

执行顺序：按现象选分支 → 记录时间和内核 → 看整机趋势 → 再进入对应章节。

现象 优先检查 后续动作
load升高、进程卡住 vmstat、D状态、回收和I/O 区分CPU排队、存储等待、内存回收
内存越来越少 meminfo、进程RSS/PSS、Shmem、Slab 找到增长的内存类型，再查归属
机器有空闲内存，容器却OOM cgroup限制及事件 查容器边界，而非只查整机
短时延迟毛刺、sys CPU升高 回收、规整、THP、热点栈 按毛刺发生时间关联证据
新连接超时或排队 SYN队列、accept队列、应用处理能力 查连接阶段与监听队列
已连接但传输慢 RTT、重传、收发队列、窗口 查链路及收发两端
单核软中断高 网卡队列、中断分布、包速率 查流量分布和CPU余量 
# 记录当前时间，方便与业务和系统日志对齐
date
# 确认正在运行的内核版本
uname -r
# 查看运行时长和1、5、15分钟平均负载
uptime
# 每秒采样整机运行队列、阻塞、换页、I/O和CPU，共5次
vmstat 1 5
# 查看整机可用内存、缓存和Swap占用
free -h

示例：load升高且 vmstat 的 b 增多，就继续查阻塞和I/O；r持续高、CPU忙则转查CPU。不要看到load高就直接认定CPU不够。vmstat第一行通常包含开机以来的平均值，后续才是间隔采样。

示例：CentOS 7常见3.10内核，但包含发行版回移补丁，能力以实际配置和事件为准。仓库失效处理见服务器常用命令。

示例：PSI、smaps_rollup、tracepoint、cgroup文件依赖内核版本及配置。文件不存在或权限不足时，先确认功能支持与授权；CentOS 7等旧环境不能照搬新内核路径。

2. free很少，是否真的缺内存

执行顺序：先看meminfo分类 → 再按RSS找进程 → 用趋势确认增长来源。

# 读取内存分类，区分匿名页、文件缓存、共享内存与Slab
grep -E '^(MemTotal|MemFree|MemAvailable|Cached|Buffers|Active\(file\)|Inactive\(file\)|AnonPages|Shmem|Slab|SReclaimable|SUnreclaim|Dirty|Writeback|SwapTotal|SwapFree):' /proc/meminfo
# 按常驻内存RSS倒序显示进程，含表头最多15行
ps -eo pid,comm,rss,vsz --sort=-rss | head -n 15

示例：Cached较大但MemAvailable仍充足、业务正常，不需要“清缓存”。AnonPages增长查进程匿名内存；Shmem增长查共享内存/tmpfs；SUnreclaim增长查内核分配。| head只保留前15行输出。

处理：以可用内存、交换活动、业务延迟及增长趋势判断压力。不能直接把各进程RSS相加当成实际物理占用，共享页会重复计数；meminfo里的不同分类也不应简单相加。

复查：在同类负载下连续观察，确认MemAvailable不再持续下降、没有回收抖动和OOM。字段说明

3. load飙高、延迟变大：检查回收和脏页

执行顺序：先看sar回收 → 同时看设备延迟和脏页 → 只读现有参数 → 再选处理办法。

# 每秒采样缺页和内存回收指标，共5次
sar -B 1 5
# 每秒采样设备I/O延迟、队列和读写量，共5次；-y跳过首份累计报告
iostat -xz -y 1 5
# 查看脏页和正在回写的数据量
grep -E '^(Dirty|Writeback):' /proc/meminfo
# 读取回收、规整和脏页指标；累计项需要比较两次采样增量
grep -E 'pgscan|pgsteal|allocstall|compact_stall|nr_dirty|nr_writeback' /proc/vmstat

示例：sar显示直接回收活动增加，且存储延迟和Dirty/Writeback在同一时间异常，才进一步怀疑回收/回写拖慢应用。/proc/vmstat里的许多值是累计计数，应间隔采样看增量，不能凭非零就认定正在故障。

sar -B字段 看什么 下一步
pgscank/s 后台kswapd每秒扫描页数 结合可用内存判断回收压力
pgscand/s 应用分配路径直接扫描页数 若与延迟同步升高，继续追直接回收事件
pgsteal/s 每秒实际回收页数 与扫描量一起看，不能单独按大/小判断好坏
%vmeff 回收量与扫描量的比值 低值提示扫描收益差，但不是业务是否正常的唯一标准
majflt/s 需要I/O等处理的主要缺页 对照读盘、Swap及进程映射

示例：pgscand/s从平时接近0变为持续较高，同时P99抖动，说明应用可能在同步参与回收；若扫描很多、回收很少，再查页是否被引用、脏页回写或其他回收限制。字段及计数口径以本机sysstat和内核版本为准。

处理：先减少批处理、突发写入和内存竞争，定位慢存储；有泄漏先处理泄漏。确需调整回收水位或脏页策略时，先记录现值，再按机器内存和存储能力做小范围试验，不直接套固定GB值或比例。

# 只读：查看内存预留水位相关参数
sysctl vm.min_free_kbytes vm.watermark_scale_factor
# 只读：查看按比例配置的脏页后台回写和写入限制
sysctl vm.dirty_background_ratio vm.dirty_ratio
# 只读：查看按字节配置的脏页后台回写和写入限制
sysctl vm.dirty_background_bytes vm.dirty_bytes

示例：这些命令只读取参数；旧内核可能没有其中某项。bytes与ratio控制方式需按内核规则选择，不能把两组值当作互不相关的限制随意同时配置。

复查：比较相近流量下的直接回收增量、I/O延迟和P95/P99；内存预留增加也会压缩应用可用容量。VM参数说明

4. 清过缓存后更慢：检查热点数据反复读盘

执行顺序：先确认缺页与读盘增加 → 对照缓存变化 → 查清缓存或竞争任务 → 恢复热点工作集。

# 每秒采样缺页和内存回收指标，共5次
sar -B 1 5
# 每秒观察目标进程的缺页、RSS和虚拟内存，共5次
pidstat -r -p 24680 1 5
# 每秒观察目标进程实际存储读写量，共5次
pidstat -d -p 24680 1 5

示例：延迟升高同时出现主要缺页、读盘增加和缓存下降，要检查是否有人定时执行drop_caches，或其他大扫描挤出了热点缓存。主要缺页增加也可能涉及交换，需结合I/O和映射判断。

处理：取消无依据的周期清缓存，错开全盘扫描/备份和在线业务；对延迟敏感服务合理预热、隔离竞争和配置内存。不要为了让free数字变大而每天清Page Cache。

# 查看热点页被回收后再次访问的计数线索，采样两次比较增量
grep -E '^workingset_(refault|activate|restore)' /proc/vmstat
# 只读确认是否存在定时清缓存任务；仅查常见系统任务目录，不代表覆盖所有自动化来源
sudo grep -Rns 'drop_caches' /etc/cron.d /etc/cron.daily /etc/cron.hourly /etc/crontab

示例：refault增量、读盘和业务延迟一起升高，说明热点数据可能被反复挤出；该计数为整机线索，仍要确认具体进程及文件。write成功也不等于数据已经持久化到存储；脏页回写、fsync语义和设备持久性要按应用要求分别核对。

复查：观察热点请求的读盘量、缺页活动和延迟是否恢复；冷启动与缓存预热后的结果分别记录。

5. 进程RSS持续涨：区分堆、映射与共享页

执行顺序：先看status分类 → 再看smaps/PSS → 用pmap找增长映射 → 选运行时或分配追踪工具。

# 读取目标进程的匿名、文件、共享常驻页和Swap分类
grep -E 'VmRSS|VmSize|RssAnon|RssFile|RssShmem|VmSwap' /proc/24680/status
# 读取目标进程的RSS、PSS与私有/共享页汇总，需要相应权限
sudo cat /proc/24680/smaps_rollup
# 查看目标进程各内存映射的大小与常驻量
pmap -x 24680

示例：匿名常驻页持续增长时继续查堆/匿名映射；文件映射增长时查映射文件及生命周期。smaps_rollup中的PSS按共享比例分摊，更适合辅助判断归属；文件存在与读取权限以系统为准。

CentOS 7等旧内核没有 smaps_rollup 时，读取同一进程的 smaps 汇总；先替换PID，并使用有读取权限的身份：

sudo awk '/^Rss:/ {rss+=$2} /^Pss:/ {pss+=$2} END {printf "RSS=%d kB PSS=%d kB\n",rss,pss}' /proc/24680/smaps # 汇总映射的RSS与PSS

示例：RSS可能重复计算共享页；这些是读取期间的近似快照，不能把两次不同时间的值当作同一个瞬间。

处理：先按应用语言使用堆分析、分配采样或运行时诊断，区分泄漏、缓存、分配器保留和负载增长；为异常服务限制流量并保留现场。生产上不直接启动全量Valgrind或无上限采样。

复查：在稳定负载和相近运行时长下，检查内存是否趋稳、GC后是否回落，以及错误率和延迟有没有恶化。

6. RSS不高、Shmem很大：查tmpfs与共享内存

执行顺序：先看Shmem → 找tmpfs挂载和占用 → 查共享段及删除后未释放的文件 → 确认创建者。

# 查看整机共享内存/tmpfs相关内存占用
grep '^Shmem:' /proc/meminfo
# 列出tmpfs挂载点，确认临时文件存在哪里
findmnt -t tmpfs
# 查看共享内存和运行目录所在文件系统的容量与类型
df -hT /dev/shm /run
# 按一级目录统计占用，-x不跨文件系统，扫描可能产生I/O
sudo du -xhd1 /dev/shm /run
# 列出System V共享内存段
ipcs -m
# 查找已删除但仍被进程打开、尚未释放空间的文件
sudo lsof +L1

示例：/run或 /dev/shm占用增长，且Shmem同步增长，即使应用已经关闭文件也可能保留数据；ipcs -m查看System V共享内存，不能覆盖所有共享内存类型。已删除但仍打开的文件还会占用空间。

处理：找到创建者与保留规则，再清理确认无用的临时文件或修复应用生命周期。不要清空 /run、盲目 ipcrm 或直接删除仍被业务使用的共享文件；tmpfs数据也不等于可随时丢弃。

复查：文件系统占用与Shmem均回落，并确认服务连接、锁、PID和共享数据仍正常。

7. 内核内存持续增长：查Slab、驱动与分配点

执行顺序：先确认内核内存类型 → slabtop找增长对象 → 对照模块和内核日志 → 再深入分配栈。

# 读取内核内存分类，判断哪一类持续增长
grep -E '^(Slab|SReclaimable|SUnreclaim|VmallocUsed|KernelStack|PageTables):' /proc/meminfo
# 输出一份Slab对象和缓存占用快照
sudo slabtop -o
# 列出已加载模块，辅助关联驱动或模块变化
lsmod
# 查看本次开机最近100条内核日志
sudo journalctl -k -b -n 100 --no-pager

示例：SUnreclaim持续上升而进程占用相对稳定，记录slab对象类别的变化；必要时让内核/驱动维护人员进一步检查vmallocinfo与分配栈。某个值大并不足以证明泄漏。

处理：关联近期驱动、模块和内核更新，优先在测试环境复现并升级/回退问题组件；内核态泄漏不会因为重启一个Java进程就必然释放。kmemleak、kprobe等依赖构建选项与诊断成本，不在生产临时随意开启。

复查：对比相同负载下对象数量、内存增长斜率及错误日志，确认不是暂时缓存下降。

8. 服务被杀、容器OOM：先确认边界

执行顺序：先查OOM日志 → 确认目标进程及cgroup → 读取真实限制与事件 → 判断整机还是分组不足。

# 从本次开机内核日志中筛选OOM和被杀进程记录
sudo journalctl -k -b --no-pager | grep -Ei 'out of memory|oom-kill|killed process'
# 读取目标进程所在的cgroup路径
cat /proc/24680/cgroup
# 查看服务的cgroup路径及systemd配置的内存上限
systemctl show demo-api -p ControlGroup -p MemoryMax

示例：整机还有空闲内存，不代表服务没有超出cgroup限额；OOM被杀的进程也不一定是最早引起压力的进程。结合时间、PID、分组和实际限额判断。

确认使用cgroup v2、ControlGroup为 /system.slice/demo-api.service 后读取：

# cgroup v2：查看此服务当前内存占用，单位为字节
cat /sys/fs/cgroup/system.slice/demo-api.service/memory.current
# cgroup v2：查看内存硬上限；max表示此层不设上限
cat /sys/fs/cgroup/system.slice/demo-api.service/memory.max
# cgroup v2：读取达到限制、OOM及杀进程等累计事件
cat /sys/fs/cgroup/system.slice/demo-api.service/memory.events

示例：关注 oom/oom_kill计数是否在事故期间增加，区分达到限额与实际杀进程；这些是累计事件，需结合分组生命周期。cgroup v1用其对应控制器文件，不能硬套v2路径。

CentOS 7常见cgroup v1。先执行 cat /proc/24680/cgroup、findmnt -t cgroup，找到memory控制器路径及挂载点。以下假设确认为 /sys/fs/cgroup/memory/system.slice/demo-api.service；容器、用户slice和非默认挂载必须改成实际目录：

systemctl show demo-api -p ControlGroup -p MemoryLimit # systemd 219读取旧版限制属性
cat /sys/fs/cgroup/memory/system.slice/demo-api.service/memory.usage_in_bytes # 当前分组用量
cat /sys/fs/cgroup/memory/system.slice/demo-api.service/memory.limit_in_bytes # 分组内存硬上限
cat /sys/fs/cgroup/memory/system.slice/demo-api.service/memory.failcnt # 累计触及限额的次数
cat /sys/fs/cgroup/memory/system.slice/demo-api.service/memory.oom_control # 当前OOM相关状态，可用字段随内核变化
sudo journalctl -k --since '30 minutes ago' --no-pager # 结合内核日志确认实际OOM及被杀进程

示例：memory.failcnt增长表示触及限额，不等于杀进程次数；under_oom=0也不能证明过去没发生过OOM。比较事故前后增量并查日志，还需检查父分组限制；v1没有v2的 memory.events。

处理：先减负载、处理泄漏或在容量允许时调整限额；JVM堆外、线程栈、页缓存等也需预留空间。避免给所有业务设置不可被OOM杀死的保护，导致压力转嫁给整机。

复查：观察同类负载下的memory.current、事件增量和业务状态。cgroup v2说明

9. 有空闲内存还卡顿：查NUMA和透明大页

执行顺序：先看NUMA分布 → 查绑核/节点及回收策略 → 对照THP模式和规整增量 → 做有范围的对照。

# 查看NUMA节点、各节点CPU及内存分布
numactl --hardware
# 查看目标进程的NUMA内存分布
numastat -p 24680
# 只读：查看NUMA本地内存回收策略
sysctl vm.zone_reclaim_mode
# 查看透明大页启用策略，方括号中的值为当前模式
cat /sys/kernel/mm/transparent_hugepage/enabled
# 查看透明大页内存规整策略
cat /sys/kernel/mm/transparent_hugepage/defrag
# 查看内存规整和透明大页指标，累计项需比较增量
grep -E 'compact_stall|compact_fail|compact_success|thp_' /proc/vmstat

示例：NUMA可能出现某节点紧张、其他节点空闲；THP启用状态本身不是故障证据，需要结合毛刺期间规整活动、热点栈及应用特征。THP当前模式通常由方括号标出，新内核还可能有按页大小的独立策略。

处理：检查不合理绑核/绑内存和本地回收策略；THP按数据库/JVM等具体版本的建议及A/B测试选择，不对所有业务统一“always”或“never”。切换策略不代表现有大页立即全部拆分，也不自动持久化。

复查：比较延迟尾部、CPU、内存占用和吞吐，不能只看平均延迟。THP当前接口

10. 新连接超时：分清握手与accept排队

执行顺序：先查端口监听与accept队列 → 查半连接 → 对比溢出计数增量 → 确认应用是否及时accept。

# 查看8080监听端口、accept队列和所属进程
sudo ss -lntp 'sport = :8080'
# 查看8080端口仍处于SYN-RECV的连接
ss -nt state syn-recv '( sport = :8080 )'
# 读取监听队列溢出、丢弃及SYN Cookie累计计数
nstat -az TcpExtListenOverflows TcpExtListenDrops TcpExtSyncookiesSent
# 只读：查看accept队列上限、SYN队列限制和SYN Cookie策略
sysctl net.core.somaxconn net.ipv4.tcp_max_syn_backlog net.ipv4.tcp_syncookies

示例：监听socket的Recv-Q反映等待应用accept的连接，Send-Q对应其backlog上限含义；不能用ESTABLISHED连接的队列含义直接解释。ListenOverflows在事故窗口增加时，进一步查应用是否accept慢、线程池/依赖是否阻塞。

处理：先恢复应用消费连接的能力，控制突发连接并合理复用连接；确需增大backlog时，同时核对应用listen参数与系统上限。SYN压力、accept排队和连接跟踪耗尽是不同问题，不能靠调大一个参数包治。

复查：以连接成功率、建连耗时、队列趋势和溢出计数增量验收。TCP参数说明

11. 连接已建立但很慢：检查重传、RTT和收发窗口

执行顺序：先看目标连接RTT与队列 → 查重传趋势 → 对照网卡 → 必要时双端抓包。

# 查看指定端口连接的队列、RTT、重传与拥塞窗口
ss -tin '( dport = :8080 or sport = :8080 )'
# 读取整机TCP重传和输出分段累计计数
nstat -az TcpRetransSegs TcpOutSegs
# 查看网卡收发字节、包数、错误与丢弃累计计数
ip -s link show dev eth0

示例：同一连接重传增加、RTT升高与请求变慢同时出现时，再定位链路；全机TCP重传计数不能直接算作某个服务的重传率。Recv-Q长时间积压要查应用是否及时读，Send-Q积压可能涉及对端接收、链路或发送阻塞。

处理：两端按同一时间窗口采样，结合抓包分辨发送迟、链路丢、接收不及时。零窗口通常应查接收方应用与内存压力；只换拥塞控制算法不会修复对端不读数据的问题。

复查：比较目标连接的重传、RTT、队列及业务延迟；不要把调整应用发送超时等同于直接改变TCP内核RTO。

12. 软中断占满单核：检查网卡队列和流量分布

执行顺序：先找高soft的CPU → 看包速率与丢弃 → 比较中断增量 → 核对网卡队列与卸载。

# 每秒查看各CPU忙闲、中断和I/O等待，共5次
mpstat -P ALL 1 5
# 每秒查看网卡吞吐、包速率和错误/丢弃，共5次
sar -n DEV,EDEV 1 5
# 读取每核网络收发软中断累计次数
grep -E 'NET_RX|NET_TX' /proc/softirqs
# 读取硬中断在各CPU上的累计分布
cat /proc/interrupts
# 查看网卡支持及当前启用的队列数
sudo ethtool -l eth0
# 查看网卡协议卸载等功能的启用状态
sudo ethtool -k eth0
# 查看驱动提供的网卡详细统计
sudo ethtool -S eth0

示例：单核soft高且包速率/丢包同时异常，查中断是否集中、是否大量小包。softirqs/interrupts为累计值，要比较增量；ethtool能查看的队列/统计因驱动和虚拟网卡而异。

处理：先查异常流量和硬件RSS/IRQ分配，再评估RPS/RFS与offload。软件分流也消耗CPU，整机已忙时可能进一步压缩业务时间；不要默认把所有卸载特性关闭，或给所有网卡写相同CPU掩码。

复查：同时看总CPU、单核soft、丢包、吞吐和P99；分布变均匀但吞吐下降不算优化成功。网络扩展机制

13. 间歇性卡顿：用压力与短时采样留证

执行顺序：先对齐毛刺时间 → 看PSI → 对目标进程短采样 → 按热点进入回收、I/O或调度分支。

# 读取CPU争用造成的停顿指标，需内核支持PSI
cat /proc/pressure/cpu
# 读取内存压力造成的停顿指标
cat /proc/pressure/memory
# 读取I/O压力造成的停顿指标
cat /proc/pressure/io
# 对目标进程按49Hz采集调用栈15秒，并保存采样文件
sudo perf record -F 49 -g -p 24680 -o /tmp/demo-kernel-perf.data -- sleep 15
# 读取上一步的采样文件，分析热点调用栈
sudo perf report -i /tmp/demo-kernel-perf.data --stdio

示例：PSI反映资源争用造成的停顿趋势，不是资源使用率；系统级CPU的full不能照搬内存/I/O的解读。perf只在获得授权、可承受开销时对目标进程短时采样，-- sleep 15限定采样时段。PSI接口

CentOS 7等旧内核可能没有 /proc/pressure/，这表示该接口不可用，不表示压力为零。此时把上面的三条PSI读取改成以下采样，perf是否可用另行核对：

vmstat 1 5              # 看运行/阻塞队列、换页与CPU等待，首行常为开机以来平均
pidstat -r -u -d 1 5    # 看各进程CPU、缺页和I/O，按本机sysstat表头阅读
iostat -xz 1 5         # 看设备延迟与队列，首份报告常为开机以来累计平均

示例：这些采样用于关联事故时段，不能换算成PSI百分比；短时毛刺可能被一秒采样平滑，需要结合业务时间线和短时perf采样。

处理：先把毛刺时间与回收、规整、软中断、业务指标对齐，再由热点栈决定是否深入tracepoint/eBPF。不要一开始就全机长期开高频追踪。

复查：在同等请求量下，确认停顿与业务尾延迟一起改善；保留内核版本、旧配置、变更项及回退方法。

14. CLOSE_WAIT、TIME_WAIT或FIN_WAIT_2很多

执行顺序：先统计状态 → 按业务端口找归属 → 对照连接创建/关闭速率 → 查应用关闭逻辑或端口容量。

# 第1步：查看整机TCP状态概况
ss -s
# 第2步：查8080服务未及时关闭的连接及其进程，需有查看对应进程的权限
sudo ss -ntp state close-wait '( sport = :8080 or dport = :8080 )'
# 第3步：查向8080发起连接的一侧有哪些TIME-WAIT连接
ss -nt state time-wait '( dport = :8080 )'
# 第4步：检查本端已发送FIN、仍等待对端FIN的连接
ss -nto state fin-wait-2
# 第5步：只读当前临时端口范围、端口保留和关闭相关策略
sysctl net.ipv4.ip_local_port_range net.ipv4.ip_local_reserved_ports
# 第6步：只读相关TCP策略，先记录现值，不直接调小
sysctl net.ipv4.tcp_fin_timeout net.ipv4.tcp_tw_reuse

示例：CLOSE_WAIT长期集中在同一PID，优先查该进程是否遗漏关闭连接、异常路径没释放资源；TIME_WAIT随短连接请求量升高，优先查连接复用。TIME_WAIT本身是正常协议保护，不等于泄漏。

状态 接下来查什么 容易误用的处理
CLOSE_WAIT 被动关闭端的close逻辑、线程阻塞、连接泄漏 调tcp_fin_timeout无法替应用close
TIME_WAIT 主动关闭频率、到同一对端的端口容量、连接池 不靠压低数量上限来“清理”连接
FIN_WAIT_2 对端是否正常关闭、本端是否仍持有socket tcp_fin_timeout主要针对孤儿连接，不是所有连接的统一超时
SYN_SENT 路由、防火墙、对端监听、握手重试 优先设应用连接期限与故障切换，不盲改整机重试次数

处理：修复连接释放和复用；端口确实耗尽时核对源IP、目标IP/端口和保留端口后再评估扩容。TCP连接按地址和端口组合区分，服务端总连接数并非只能有65535个；客户端向不同对端建连也不能一概按全机65535封顶。

复查：看连接数是否随业务回落、端口分配错误是否消失，以及建连成功率和延迟。

15. send阻塞或接收丢弃：查socket缓冲与总内存

执行顺序：先查目标连接队列和内存 → 查整机socket占用 → 查限制与应用设置 → 再判断是否需要扩缓冲。

# 第1步：查看8080连接的队列、TCP内部信息和socket内存
sudo ss -tinmp '( sport = :8080 or dport = :8080 )'
# 第2步：读取整机socket数量与TCP内存统计
cat /proc/net/sockstat
# 第3步：只读TCP自动调节范围及接收自动调节开关
sysctl net.ipv4.tcp_rmem net.ipv4.tcp_wmem net.ipv4.tcp_moderate_rcvbuf
# 第4步：只读应用显式设置socket缓冲时涉及的系统上限
sysctl net.core.rmem_max net.core.wmem_max
# 第5步：只读全局TCP内存水位，单位为页；不是每连接的字节上限
sysctl net.ipv4.tcp_mem
# 第6步：确认本机基础页大小，不能一概认为所有架构都是4KB
getconf PAGESIZE

示例：skmem中的 r/rb 分别辅助观察已分配接收内存与接收缓冲上限，w/tb辅助观察待发送内存与发送缓冲上限；字段按本机ss版本解释。接收队列持续积压时，先查应用不读或处理太慢，扩缓冲只能延后积压暴露。

处理：区分三种限制：应用显式SO_RCVBUF/SO_SNDBUF、TCP自动调节、整机TCP内存。应用锁定缓冲后，改自动调节参数可能无效；部分socket值包含内核记账开销，不能和有效载荷大小直接相等比较。高带宽长RTT链路再用带宽时延积估算需求，例如100MB/s×0.02s约2MB在途数据，同时预算大量连接的总内存。

复查：比较目标连接吞吐、发送阻塞、零窗口、丢弃和整机内存；不要只验证“缓冲变大了”。ss内存字段

16. VIRT涨、RSS不涨，最后却申请失败

执行顺序：持续观察VSZ/RSS → 查映射数量和资源限制 → 对照映射新增规律 → 追踪申请/释放是否配对。

# 第1步：每秒观察虚拟内存和常驻内存，采样10次
pidstat -r -p 24680 1 10
# 第2步：统计此进程的VMA数量，每行通常对应一个映射区域
wc -l /proc/24680/maps
# 第3步：查看进程真实生效的地址空间、栈和进程等资源限制
cat /proc/24680/limits
# 第4步：只读全机每进程映射数量上限
sysctl vm.max_map_count
# 第5步：追踪10秒内的映射、释放、堆扩展和线程创建；会增加目标进程开销
sudo timeout 10s strace -f -tt -T -e trace=mmap,munmap,brk,clone \
  -p 24680 -o /tmp/demo-memory-syscalls.log

示例：VSZ每隔固定时间增加相近大小，RSS却稳定，新增映射旁有保护页，且clone后缺少对应释放，需查线程栈或自定义映射的生命周期。线程结束不一定代表应用自行分配的栈已释放；但运行库保留栈缓存也可能是正常行为，要看是否有上界。

处理：核实32位地址空间、RLIMIT_AS、VMA上限及分配失败位置；修复漏掉的munmap或线程资源回收。提高max_map_count只适用于映射数量确实是合理需求的情况，不能代替修复无限增长。

复查：在相近运行时长下观察VMA、VSZ和未释放分配是否趋稳，并确认线程创建及内存分配错误停止。

17. 内存没用完，却出现page allocation failure

执行顺序：保留失败日志的order、GFP、调用栈 → 看节点/zone和连续页 → 比较规整与回收 → 按内核版本确认缺陷或驱动需求。

# 第1步：从最近1小时内核日志中找分配失败及周边上下文
sudo journalctl -k --since '1 hour ago' --no-pager | \
  grep -Ei -A 40 -B 5 'page allocation failure|warn_alloc|out of memory'
# 第2步：查看各节点和zone按阶数分布的空闲块
cat /proc/buddyinfo
# 第3步：查看各zone水位和空闲页等信息，输出较长
cat /proc/zoneinfo
# 第4步：读取规整与回收计数，间隔采样后对比增量
grep -E 'compact_|allocstall|pgscan|pgsteal' /proc/vmstat
# 第5步：确认故障机器实际内核版本，查询修复时要匹配发行版回移补丁
uname -r

示例：order=5表示需要32个基础页连续分配，4KB基础页时为128KB。整机有空闲内存，也可能没有适合的连续块，或当前分配上下文不允许等待、回收、I/O或跨节点。

处理：将日志、节点水位、buddyinfo和计数交给内核/驱动维护人员核对。能确认版本缺陷时优先使用发行版修复；不根据一条日志就全机清缓存、强制规整或升级未知来源内核。GFP标志及水位逻辑随版本变化，不能把旧版本代码结论套在新内核。

复查：用相同负载确认分配失败停止，应用错误和尾延迟恢复，不能只看free变大。

18. 重传间歇发生，普通采样抓不到连接

执行顺序：先用nstat确认窗口内有重传 → 找到可用重传tracepoint → 短时记录 → 按地址、端口和状态缩小范围 → 必要时双端抓包。

# 第1步：确认内核是否提供TCP重传事件；无输出时不执行后续记录
sudo perf list 'tcp:tcp_retransmit_skb'
# 第2步：只记录TCP重传事件10秒；-a覆盖软中断等上下文，不按业务PID误过滤
sudo perf record -a -e tcp:tcp_retransmit_skb \
  -o /tmp/demo-retrans.data -- sleep 10
# 第3步：展开事件，查看发生重传的地址、端口和连接状态
sudo perf script -i /tmp/demo-retrans.data

示例：事件集中在SYN_SENT，先查握手路径；集中在ESTABLISHED，再查传输、接收窗口和链路。字段随版本变化，不保证都有状态信息。重传可能发生在软中断上下文，事件显示的当前PID未必就是连接的应用PID。

处理：按四元组与时间关联服务和抓包；该事件主要观察本机重传，不等于能看见对端所有重传。没有事件时用限定目标、时长和包数的tcpdump；不要为了这个工具临时更换生产内核。

复查：对比同类流量下重传事件增量、连接失败和P99，不将全机累计重传数当作目标业务数据。

19. 已知pread/read很慢：继续追到内核等待位置

执行顺序：strace确认慢调用和线程 → 检查本机可追踪函数 → 用独立trace实例做短采样 → 回到磁盘、页锁或回收对应分支。

安装trace-cmd，以及使用前的检查 
# Ubuntu / Debian：安装ftrace的命令行工具，会修改已安装软件
sudo apt-get install trace-cmd
# RHEL系：选择此命令安装，不必把两种包管理器命令都执行
sudo dnf install trace-cmd
# CentOS 7：改选已有批准仓库中的包，不执行上面的dnf命令
# sudo yum install trace-cmd
# 查看工具支持的选项，确认有-B实例和-P线程过滤
trace-cmd record -h

示例：内核须支持function_graph及独立实例。旧系统不支持时保留strace、iostat和perf证据，不直接改全局current_tracer覆盖其他采集任务。

# 第1步：追踪目标进程和线程5秒，记录绝对时间及每个调用耗时
sudo timeout 5s strace -ff -tt -T -p 24680 -o /tmp/demo-read-strace
# 第2步：确认pread相关函数在本机可追踪；名称可能与示例不同
sudo trace-cmd list -f | grep -E '(^|[[:space:]])(ksys_pread64|__x64_sys_pread64)'
# 第3步：确认实例名未被其他任务占用；任一位置已存在时改用新的唯一名字
sudo ls -d /sys/kernel/tracing/instances/demo-read-24680 /sys/kernel/debug/tracing/instances/demo-read-24680

示例：strace显示线程24681的pread64一次耗时80ms，先确认不是工具自身放大的延迟；随后将下面的 -P 24681 替换成真正慢的TID，并将函数名替换为上一步确实存在的函数。上面ls提示路径不存在，才表示这两个位置没有同名实例；权限错误不等于不存在。

# 第4步：在新建独立实例中，只追踪目标线程的pread调用树5秒，写出本次数据
sudo trace-cmd record -o /tmp/demo-read.dat -B demo-read-24680 \
  -p function_graph -g ksys_pread64 -P 24681 sleep 5
# 第5步：读取调用树，观察页锁、I/O等待或回收等耗时位置
sudo trace-cmd report -i /tmp/demo-read.dat

示例：调用树沿页锁进入io_schedule，说明线程因等待被调度走，不能据此认定磁盘损坏。继续对齐iostat、Dirty/Writeback、pidstat，检查是否被其他进程写入或页回写阻塞。

处理：修复对应的竞争或慢存储。追踪会改变时序，优先在可复现环境验证；正常结束后工具会关闭本次启用的追踪并移除新建实例。异常退出需核查本次实例状态，不能一键关闭全机追踪。trace-cmd记录选项

复查：重新比较真实业务请求与目标调用耗时，同时确认没有遗留本次追踪。

20. 加线程反而变慢：查CPU竞争、绑核与缓存

执行顺序：确认有效CPU范围 → 看线程调度等待 → 再采样IPC和缓存事件 → 在代码或调度策略上做对照。

# 第1步：查看CPU、核心、线程和NUMA拓扑，具体缓存共享关系取决于硬件
lscpu
# 第2步：只读目标进程的CPU亲和性
taskset -pc 24680
# 第3步：只读当前调度策略与优先级
chrt -p 24680
# 第4步：查看各线程CPU占用及等待，共5次
pidstat -u -w -t -p 24680 1 5
# 第5步：统计10秒指令、周期与缓存事件；部分虚拟机/CPU不提供这些事件
sudo perf stat -e cycles,instructions,cache-references,cache-misses \
  -p 24680 -- sleep 10

示例：线程多、非自愿切换和调度等待高，先查CPU配额、亲和性和过量并发；增加线程后每请求周期增多、缓存事件异常，再考虑共享热点、数据局部性或伪共享。cache-misses高本身不能证明伪共享，必要时在支持的硬件上进一步用perf c2c。

处理：减少共享计数器争用，使用分片/批量聚合，避免无效轮询；确有伪共享再改数据布局。绑核可能把任务挤在少数CPU上，实时调度也可能饿死其他工作，不作为通用提速开关。

复查：对比同等吞吐下每请求CPU成本、调度等待和P99；检查其他服务是否受到影响。

21. 故障过去了，如何追查当时的回收或卡顿

执行顺序：确定日期和时间窗口 → 找到事先采集的数据 → 对齐业务延迟 → 判断相关性 → 下次补采最缺的证据。

# 第1步：查看两种常见目录，找故障日期对应的sar二进制文件
ls -lh /var/log/sa /var/log/sysstat
# 第2步：示例读取sa03文件的22:30至22:45分页与回收记录，目录和文件名按实际替换
sar -B -f /var/log/sa/sa03 -s 22:30:00 -e 22:45:00
# 第3步：读取同一文件、同一时间段的内存指标
sar -r -f /var/log/sa/sa03 -s 22:30:00 -e 22:45:00

示例：业务P99升高的多个时间点与直接回收同时出现，可以作为进一步采样的方向；几条历史曲线吻合仍不等于已证明因果。

处理：没有事先采集就无法靠现在的sar还原过去。为反复发生的问题补充回收/规整/重传计数、PSI及业务延迟的定时采样，统一时区并设保留期；不把瞬时累计计数当作昨日现场。

复查：下一次毛刺发生时能同时找到业务、进程与内核层的证据，采集本身没有明显干扰。
