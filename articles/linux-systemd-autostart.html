Linux 服务开机自启与 systemd 管理

知知行笔记·约 20 分钟阅读
linuxsystemdjavaredisiotdbnacosautostart

使用 systemd 管理 Java、Redis、IoTDB 等长期运行服务，实现开机启动、失败重试和统一启停。示例中的目录 /opt/demo、服务名 demo-api、运行用户、内存和端口按实际安装情况调整；需要管理员权限的命令使用 sudo。

1. 先分清自启、启动和自动重试

操作或配置 含义
enable 建立开机启动关系，不立即启动进程
start 现在启动，不自动开启开机自启
disable 取消开机自启，不立即停止进程
stop 主动停止；不会因为 Restart=on-failure 自动拉起
daemon-reload 重新读取单元配置，不重启业务进程
Restart=on-failure 主进程失败退出后自动重试，正常退出不重试
RestartSec=60 失败后等待60秒重试，不是启动超时时间

nohup ... & 只是在当前系统运行期间启动后台进程，不提供开机自启和持续故障恢复。

2. 创建配置前检查现有进程

systemctl --version                       # 确认 systemd 版本
systemctl list-unit-files --type=service   # 查看已有服务，避免重复创建
ps -ww -eo pid,ppid,args                   # 查看完整进程参数
sudo ss -lntp                             # 核对监听端口和归属

示例：查找 Java 服务并确认 PID 为24680的进程使用的 Java 和工作目录。

pgrep -af 'demo-api.jar'
sudo readlink -f /proc/24680/exe
sudo readlink -f /proc/24680/cwd

如果输出分别为 /opt/jdk17/bin/java 和 /opt/demo，服务文件中就应沿用对应的 Java 与工作目录。PID 必须来自本次查询；进程重启后旧 PID 可能被其他程序复用。

原脚本中的 JVM 参数、Spring 环境、外部配置、日志目录都要核对。Redis 的 dir ./ 等相对目录还会影响数据文件位置。

3. Java 单服务配置

创建 /etc/systemd/system/demo-api.service：

[Unit]
Description=Demo API
Wants=network-online.target
After=network-online.target

[Service]
Type=simple
User=demo
WorkingDirectory=/opt/demo
ExecStart=/opt/jdk17/bin/java -Xms256m -Xmx512m -Duser.timezone=Asia/Shanghai -Dfile.encoding=UTF-8 -jar /opt/demo/demo-api.jar --spring.profiles.active=prod
Restart=on-failure
RestartSec=60
TimeoutStopSec=120
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=multi-user.target

示例：这会使用 demo 用户运行 /opt/demo/demo-api.jar，工作目录为 /opt/demo，控制台输出交给 journal。用户、JDK、JAR、目录必须已存在，用户须具备配置读取和日志写入权限。

Type=simple 应直接运行前台进程，不要在 ExecStart 里加 nohup、& 或 >>。它默认不通过 shell 执行；需要重定向时优先使用 systemd 的输出配置。多行命令用行尾 \ 续行，最后一行不加。

这里的堆大小只是示例。多个服务的堆、直接内存、线程和其他服务共同占用服务器资源，不能把每个服务都按整机内存配置。

4. 多个 Java 服务使用模板

创建 /etc/systemd/system/demo@.service，用 %i 代表实例名：

[Unit]
Description=Demo service %i
Wants=network-online.target
After=network-online.target

[Service]
Type=simple
User=demo
WorkingDirectory=/opt/demo
ExecStartPre=/usr/bin/mkdir -p /opt/demo/logs/%i
ExecStart=/opt/jdk17/bin/java \
  -Xms256m -Xmx512m \
  -XX:+HeapDumpOnOutOfMemoryError \
  -XX:HeapDumpPath=/opt/demo/logs/%i/heapdump.hprof \
  -XX:ErrorFile=/opt/demo/logs/%i/hs_err_pid%%p.log \
  -jar /opt/demo/%i.jar \
  --spring.profiles.active=prod
Restart=on-failure
RestartSec=60
TimeoutStopSec=120

[Install]
WantedBy=multi-user.target

示例：demo@auth.service 对应 /opt/demo/auth.jar；demo@gateway.service 对应 /opt/demo/gateway.jar。%%p 向 JVM 传入字面量 %p，避免被 systemd 当作自身占位符。示例目录须允许 demo 用户创建日志子目录。

模板适用于启动参数相同的服务。不同服务的内存、配置或依赖不同时，使用实例覆盖配置或独立服务，不强行共用。

5. 校验、加载、开启自启

sudo systemd-analyze verify /etc/systemd/system/demo-api.service # 校验文件
sudo systemctl daemon-reload                                   # 读取配置
sudo systemctl enable demo-api.service                         # 仅开启自启
systemctl is-enabled demo-api.service                          # 检查是否 enabled
systemctl cat demo-api.service --no-pager                       # 查看主文件与覆盖文件

示例：模板可校验并启用两个明确的实例：

sudo systemctl daemon-reload
sudo systemd-analyze verify demo@auth.service demo@gateway.service
sudo systemctl enable demo@auth.service demo@gateway.service
systemctl is-enabled demo@auth.service demo@gateway.service

预期得到两行 enabled。这不代表服务已经运行；用 is-active 和后面的业务检查确认运行情况。

6. 原手动进程如何切换

先在维护时间按原管理方式停止旧进程，确认退出及端口释放，再启动 systemd 服务。仅创建文件、enable 或 daemon-reload 不会把现有手动进程自动接管。

pgrep -af 'demo-api.jar'                          # 核对旧进程
sudo ss -lntp 'sport = :8080'                    # 核对端口
sudo systemctl start demo-api.service            # 旧实例停止后再启动
systemctl status demo-api.service --no-pager -l   # 检查管理状态

示例：旧进程已通过原脚本停止、8080端口也已释放时，执行 start。随后确认 MainPID 对应新的 Java 进程，再验证接口。不要直接为已有的手动进程再启动一份相同服务。

切换后统一使用 systemctl 启停，原来的开机脚本、cron @reboot 等重复入口应取消。直接用旧脚本杀进程可能触发 systemd 自动重试。

7. Redis 的自启重点

[Unit]
Description=Demo Redis
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=redis
WorkingDirectory=/opt/redis
ExecStart=/opt/redis/bin/redis-server /opt/redis/redis.conf --daemonize no --supervised no
Restart=on-failure
RestartSec=10
TimeoutStopSec=300

[Install]
WantedBy=multi-user.target

示例：保存为 redis-demo.service。若原配置为 dir ./，且原工作目录是 /opt/redis，此处保留它；不要因更换启动方式而换到空数据目录。运行用户应具备原数据目录和文件权限。

启用、切换方法与 Java 相同。验证时使用实际监听地址和认证方式：

redis-cli -h 127.0.0.1 -p 6379 --askpass PING  # 提示输入密码

示例：返回 PONG 表示本次连接、认证和 PING 成功。若 Redis 不需要密码，则省略 --askpass；ACL 用户还需指定 --user。

8. IoTDB、Nacos 与已有 MySQL 服务

服务 配置与检查重点
MySQL 已有系统服务时沿用，不另建第二套；保留原数据目录与配置
IoTDB ConfigNode 使用当前版本支持的前台启动方式，保留 Java、配置、安装目录
IoTDB DataNode 排在 ConfigNode 后启动；同时维护时先停 DataNode，再停 ConfigNode
Nacos 核对实际 Java、完整参数、插件目录、配置与日志参数，不能只复制启动命令前半段

IoTDB 1.3.2 的示例前台命令如下，脚本行为必须与安装版本一致，不加后台运行参数 -d：

/bin/bash /opt/iotdb/sbin/start-confignode.sh # 前台配置节点
/bin/bash /opt/iotdb/sbin/start-datanode.sh   # 前台数据节点，另一终端按需运行

示例：分别放入两个单元的 ExecStart，WorkingDirectory=/opt/iotdb，并配置实际 JAVA_HOME。不要将这两条作为检查命令在已有实例旁边再执行一遍。

IoTDB 单机部署也可能同时运行 ConfigNode 和 DataNode。在已登录的 IoTDB CLI 中检查：

SHOW CLUSTER;

示例：确认预期节点均为 Running；“cluster”是节点状态查询名称，不代表一定部署了多台服务器。

9. 覆盖已有服务与 systemd 版本差异

sudo systemctl edit nacos.service           # 编辑 drop-in 覆盖配置
sudo systemctl daemon-reload                # 保存后重新加载
systemctl cat nacos.service --no-pager       # 查看合并前的配置来源
systemctl show nacos.service -p Type -p ExecStart -p ExecStop -p Restart -p RestartUSec

示例：将 Nacos 从后台脚本切换为直接运行 Java 时，应核对整个启动命令。覆盖 ExecStart 先用空的 ExecStart= 清除旧值，再设置完整的新命令；若不再使用原停止脚本，也用 ExecStop= 清除它。

启动频率限制的写法取决于版本：

CentOS 7通常为systemd 219，先执行 systemctl --version 确认。启用和启动分两步写，便于分别核对；enable本身不启动服务：

sudo systemctl enable demo-api.service # 设置下次开机自启
sudo systemctl start demo-api.service  # 现在启动，已有运行实例时不会重复启动
systemctl is-enabled demo-api.service  # enabled表示已配置自启
systemctl is-active demo-api.service   # active表示当前运行，仍需验证业务接口
systemctl show demo-api.service -p ControlGroup -p MemoryLimit # 219常用内存限制属性

示例：219内存硬上限配置使用 [Service] 下的 MemoryLimit=512M，较新系统常用 MemoryMax=512M；按业务实测留足余量，不直接给已有服务加小限额。MemoryMax、StateDirectory、LogsDirectory等较新指令不能直接套到219；目录提前创建并赋给运行用户，未知指令应在校验和journal中处理。内存实际占用及OOM另查cgroup v1示例。

# CentOS 7 / systemd 219：放在 [Service] 下
[Service]
StartLimitInterval=0

示例：旧系统配置后，用 systemctl show nacos -p StartLimitInterval 确认实际值为 0，不能只看文件里有这一行。该设置关闭频率限制，持续故障时会一直按 RestartSec 重试。

# 较新 systemd：放在 [Unit] 下
[Unit]
StartLimitIntervalSec=0

示例：新系统使用 systemctl show nacos -p StartLimitIntervalUSec 核对。是否关闭频率限制按维护策略决定，不需要持续重试时可保留默认限制。

旧版配置见 systemd 219 服务手册，新版见 systemd.unit。

10. 启动顺序与依赖就绪

[Unit]
Wants=network-online.target redis-demo.service nacos.service
After=network-online.target redis-demo.service nacos.service

示例：放在 Java 单元中，会尝试拉起依赖并安排顺序。Redis 认证可用、Nacos 注册接口可用、远程数据库可连接，仍需应用重连或专门的就绪检查；After= 本身不执行这些检查。

应用表现 处理方式
因依赖失败而非零退出 systemd 按重试策略再次启动
进程存活且能自行重连 查看日志，等待依赖恢复并验证
进程存活但业务不可用 systemd 不会仅因业务异常而重启，需要业务监测与处理

network-online.target 的效果还依赖系统网络等待服务，不能保证远程数据库或互联网可访问。要求严格就绪时，可用 ExecStartPre 调用带超时的检查脚本，验证协议和认证，不只检测端口。

11. 日常管理和开机检查

以下为按需选择的操作，不要整段连续执行：

sudo systemctl start demo-api       # 启动
sudo systemctl stop demo-api        # 停止
sudo systemctl restart demo-api     # 重启，会中断服务
systemctl status demo-api --no-pager -l # 查看状态
systemctl is-active demo-api        # 查询当前是否活动
systemctl is-enabled demo-api       # 查询是否自启
sudo systemctl disable demo-api     # 仅取消开机自启

示例：只想查看状态时执行 status，只想取消下次开机启动时执行 disable。active 是单元活动状态，enabled 是开机配置状态，两个维度互不替代。

systemctl --failed --no-pager                    # 列出失败单元
systemctl show demo-api -p MainPID -p ExecMainStatus -p Restart -p RestartUSec -p NRestarts
sudo journalctl -u demo-api -b -n 100 --no-pager # 本次开机日志
sudo journalctl -u demo-api -f                   # 持续查看控制台输出
sudo ss -lntp 'sport = :8080'                   # 核对监听
curl -i --connect-timeout 3 --max-time 5 http://127.0.0.1:8080/health

示例：/health 假设为应用实际实现的只读接口，返回预期健康结果后，再检查登录、数据读取等关键业务。旧版 systemd 可能没有 NRestarts，可改看 journal 的启动退出记录。journalctl -f 按 Ctrl+C 只退出日志查看。

12. 控制台日志、业务日志与容量

日志 保存位置与作用
journal 收集进程整个运行期间的标准输出与错误，不只启动阶段
应用文件日志 继续由 Logback、Redis、IoTDB 等自身配置决定
JVM dump / 崩溃文件 由 HeapDumpPath、ErrorFile 等参数决定

systemd 不主动读取应用文件日志。保留相同工作目录、环境和应用配置，才能保持相对日志路径一致。

sudo journalctl --disk-usage                       # journal 总占用
sudo du -sh /var/log/journal /run/log/journal 2>/dev/null # 实际日志目录
sudo journalctl --list-boots                       # 目前保留的开机记录
sudo journalctl -u demo-api -b -1 -n 100 --no-pager # 上次开机，需日志仍保留

示例：只有 /run/log/journal 时，日志通常为临时存储，重启后丢失；/var/log/journal 用于持久存储。不能因为应用文件日志还在，就认为 journal 也跨重启保存。

目录检查里的 2>/dev/null 将标准错误丢弃，例如某个目录不存在的报错；正常的容量输出仍保留。它只隐藏提示，不代表目录都存在，排障时可以去掉后查看具体原因。

需要持久保存时，在 /etc/systemd/journald.conf 的 [Journal] 下按需配置：

[Journal]
Storage=persistent
SystemMaxUse=500M
RuntimeMaxUse=100M

示例：500MB和100MB分别约束持久和临时 journal 的容量，作用于整台服务器，不限制应用自己写的文件；轮转会有一定余量。仅设置容量不会单独开启持久化。不需要历史 journal 时，可保持现有存储策略。

sudo systemctl restart systemd-journald # 应用配置，可能短暂影响日志采集
sudo journalctl --flush                 # 有持久存储时刷新临时日志
sudo journalctl --disk-usage            # 复查占用

示例：上述操作针对日志服务，不是重启 Java；完成后再次检查实际日志目录。选项含义见 journald.conf。

13. 由 systemd 管理后如何发版

先上传新包到暂存位置；在维护时间停止服务，确认进程退出，备份并替换 JAR，再启动和验收。下面假设新包已经在 /opt/demo/releases/demo-api.jar.new：

sudo systemctl stop demo-api                          # 主动停止
systemctl status demo-api --no-pager -l                # 核对已停止
pgrep -af 'demo-api.jar'                              # 核对没有遗留实例
sudo cp -p /opt/demo/demo-api.jar /opt/demo/demo-api.jar.bak # 示例备份；已有备份时另取文件名
sudo install -o demo -g demo -m 0644 /opt/demo/releases/demo-api.jar.new /opt/demo/demo-api.jar
sudo systemctl start demo-api                         # 启动新版本
sudo journalctl -u demo-api --since '5 minutes ago' --no-pager

示例：启动后检查端口、健康接口和关键业务。备份应使用独立版本名避免覆盖；失败时停止新版本、恢复原包，再启动并验收。配置或数据库变更需要配套回滚方案，不能只恢复 JAR。

只替换 JAR 不需要 daemon-reload；修改 .service 或覆盖配置时才需要。参数详细说明见 systemd.service。

14. 常见问题

现象 优先检查
enabled 但没运行 enable 不等于 start；检查本次启动日志
开机端口占用 是否还有 cron、旧脚本或另一套单元启动同一实例
启动后很快 inactive 后台脚本与 Type 不匹配，或主进程已经退出
203/EXEC 可执行文件路径、权限、解释器、挂载选项与 SELinux
217/USER User/Group 是否存在、是否可用
200/CHDIR WorkingDirectory 是否存在、权限是否正确
start-limit-hit 先修根因，再按需 systemctl reset-failed demo-api 并启动
重启后数据像丢失了 首查配置和数据目录、运行用户，避免直接初始化数据
日志路径变了 首查 WorkingDirectory、环境变量、外部配置与配置环境
