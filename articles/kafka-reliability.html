Kafka 消息生产、消费与可靠性实践

知知行笔记·约 35 分钟阅读
kafkamqproducerconsumertransactionreliability

围绕发送失败、重复处理、顺序错乱、消费积压和事务可见性，配置客户端并验证消息的完整处理过程。Java 示例固定使用 kafka-clients 4.0.2，JDK 17+；命令在 Linux Bash 中执行。集群初始化和管理变量见 Kafka 部署、运维与故障排查。

1. 先确定业务要保证到哪一步

阶段 成功的含义 仍需解决的问题
应用调用 send 消息可能只进了客户端缓冲区 最终发送异常、进程退出、队列满
收到 Broker 确认 满足所配置 acks 的写入要求 副本策略、灾难故障、应用重复发送
consumer poll 返回 消息到达客户端 业务还没成功、异步任务仍在执行
数据库事务提交 业务副作用已落地 Kafka 位移提交前宕机会重新投递
位移提交成功 下一次从提交位置继续 提交之前的业务是否真的完成

示例：先提交位移，再执行扣库存，扣库存失败时就可能跳过消息；先扣库存再提交位移，提交失败后会重投。因此，“至少一次消费 + 业务幂等”是很常见的落地方式。

业务幂等使用稳定事件 ID，例如 event_id=order-1001-created-v1。在同一个数据库事务中插入带唯一约束的处理记录，再修改订单；重复事件命中唯一约束时确认其已经处理。去重记录与业务更新必须原子化，不能先写 Redis 标记再执行可能失败的数据库操作。

如果还需要“改数据库并发消息”，优先考虑事务 Outbox：业务更新与待发送事件写在同一数据库事务里，后台投递到 Kafka，消费者仍按事件 ID 去重。Kafka 事务不会自动把任意数据库、邮件或 HTTP 调用纳入一个原子事务。

2. 生产者参数如何配

参数 用途与起点 验证内容
acks=all 等待当前 ISR 所需的确认 与副本数、min ISR、错误率一起看
enable.idempotence=true 避免生产者内部重试造成重复写入 不与 acks、retries、in-flight 配置冲突
delivery.timeout.ms 限定一条消息发送的总交付时间 失败能被应用接收并处理
request.timeout.ms 单次请求等待时间 与总交付时间、linger 配合
max.block.ms 等元数据和缓冲区的阻塞上限 不把排队超时误认为消息一定未写入
linger.ms / batch.size 按分区积累批次 吞吐提升与尾延迟的取舍
compression.type 降低网络和存储开销 CPU、压缩比与实际消息大小

acks=all 不是等待所有配置副本，也不是等待业务消费者成功。三副本、min ISR=2 是一种常见配置组合；在允许的故障范围内维持写入可靠性，不能承诺任意断电或多副本损坏都不丢数据。

4.0.2 的 linger.ms 默认 5ms；幂等在无冲突配置时默认启用。示例仍显式设置幂等，避免被其他配置悄悄关闭。开启幂等时 acks=all、retries>0、max.in.flight.requests.per.connection<=5 需要兼容，详见 生产者参数。

幂等机制主要处理这个生产者会话内部的重试。应用重启后重新遍历数据库、用户重复点击、上游再次投递相同事件，都需要业务去重。

3. 一个能确认最终发送结果的 Java 示例

展开：准备依赖、编译与运行环境

  </dependencies>

先在工作目录创建 client.properties。本机实验内容如下；生产环境用管理员提供的 TLS/SASL 配置，其他示例也复用这个文件。

# 替换成客户端确实能访问的Broker地址
bootstrap.servers=127.0.0.1:9092
# 使用相同client.id前缀，方便在日志和监控中找到应用
client.id=orders-demo

保存为 OrderProducer.java：

import java.io.InputStream;
import java.nio.file.Files;
import java.nio.file.Path;
import java.time.Duration;
import java.util.Properties;
import java.util.concurrent.TimeUnit;
import org.apache.kafka.clients.producer.KafkaProducer;
import org.apache.kafka.clients.producer.ProducerRecord;
import org.apache.kafka.clients.producer.RecordMetadata;

public class OrderProducer {
    public static void main(String[] args) throws Exception {
        if (args.length != 4) {
            throw new IllegalArgumentException("用法: 配置文件 topic key value");
        }
        Properties p = new Properties();
        try (InputStream in = Files.newInputStream(Path.of(args[0]))) {
            p.load(in); // 保留连接、TLS和SASL配置
        }
        p.setProperty("key.serializer", "org.apache.kafka.common.serialization.StringSerializer");
        p.setProperty("value.serializer", "org.apache.kafka.common.serialization.StringSerializer");
        p.setProperty("acks", "all");
        p.setProperty("enable.idempotence", "true");
        p.setProperty("delivery.timeout.ms", "45000");
        p.setProperty("request.timeout.ms", "30000");
        p.setProperty("max.block.ms", "10000");
        KafkaProducer<String, String> producer = new KafkaProducer<>(p);
        try {
            // 示例逐条等待确认，失败直接返回非零退出码，不打印“发送成功”
            RecordMetadata m = producer.send(new ProducerRecord<>(args[1], args[2], args[3]))
                    .get(60, TimeUnit.SECONDS);
            System.out.printf("已确认 topic=%s partition=%d offset=%d%n",
                    m.topic(), m.partition(), m.offset());
        } finally {
            producer.close(Duration.ofSeconds(10)); // 有界关闭并释放连接
        }
    }
}

javac -cp 'lib/*' OrderProducer.java               # 编译完整生产者示例
java -cp '.:lib/*' OrderProducer client.properties orders order-1001 created # 发送并等待Broker确认

示例：成功会打印分区与 offset；失败会抛出异常。get() 检查结果是有效方式；高吞吐应用更常用回调批量异步发送，并把回调异常交给可靠的失败处理流程。不要在 Sender 回调里做慢 SQL、阻塞式 Redis 调用或等待同一个生产者的其他 Future。

超时意味着结果可能不确定：服务端可能写入成功，但响应没回来。不能直接判定“肯定没写”，再无条件重复业务。失败事件要保留稳定 ID，进入有界重试、补偿或待核查流程。共享一个线程安全的 Producer 通常比每条消息新建实例更合理。

4. 消费者：业务成功后再提交

下面示例把打印视为处理动作，便于验证提交时点；接数据库时用前面的幂等事务替换 handle。按分区顺序处理、每条成功后提交，逻辑简单但吞吐有限。maxMessages 用于实验结束，设置为 0 持续消费。

保存为 OrderConsumer.java：

import java.io.InputStream;
import java.nio.file.Files;
import java.nio.file.Path;
import java.time.Duration;
import java.util.List;
import java.util.Map;
import java.util.Properties;
import java.util.concurrent.atomic.AtomicBoolean;
import org.apache.kafka.clients.consumer.ConsumerRecord;
import org.apache.kafka.clients.consumer.ConsumerRecords;
import org.apache.kafka.clients.consumer.KafkaConsumer;
import org.apache.kafka.clients.consumer.OffsetAndMetadata;
import org.apache.kafka.common.TopicPartition;
import org.apache.kafka.common.errors.WakeupException;

public class OrderConsumer {
    private static void handle(ConsumerRecord<String, String> r) {
        // 演示动作；业务异常必须抛出，不能吞掉异常后继续提交
        System.out.printf("处理 topic=%s partition=%d offset=%d key=%s value=%s%n",
                r.topic(), r.partition(), r.offset(), r.key(), r.value());
    }

    public static void main(String[] args) throws Exception {
        if (args.length != 4) {
            throw new IllegalArgumentException("用法: 配置文件 topic group maxMessages(0为持续)");
        }
        int maxMessages = Integer.parseInt(args[3]);
        if (maxMessages < 0) throw new IllegalArgumentException("maxMessages不能为负数");
        Properties p = new Properties();
        try (InputStream in = Files.newInputStream(Path.of(args[0]))) { p.load(in); }
        p.setProperty("group.id", args[2]);
        p.setProperty("enable.auto.commit", "false");
        p.setProperty("auto.offset.reset", "earliest");
        p.setProperty("isolation.level", "read_committed");
        p.setProperty("max.poll.records", "100");
        p.setProperty("key.deserializer", "org.apache.kafka.common.serialization.StringDeserializer");
        p.setProperty("value.deserializer", "org.apache.kafka.common.serialization.StringDeserializer");
        AtomicBoolean stopping = new AtomicBoolean(false);
        KafkaConsumer<String, String> consumer = new KafkaConsumer<>(p);
        Thread hook = new Thread(() -> {
            stopping.set(true);
            consumer.wakeup(); // 唤醒poll；不在这个线程调用commit/poll/subscribe
        });
        Runtime.getRuntime().addShutdownHook(hook);
        try (consumer) {
            consumer.subscribe(List.of(args[1]));
            int handled = 0;
            while (!stopping.get() && (maxMessages == 0 || handled < maxMessages)) {
                ConsumerRecords<String, String> records = consumer.poll(Duration.ofSeconds(1));
                for (ConsumerRecord<String, String> r : records) {
                    if (stopping.get()) break;
                    handle(r); // 成功返回后，才提交这一条的下一位置
                    consumer.commitSync(Map.of(new TopicPartition(r.topic(), r.partition()),
                            new OffsetAndMetadata(r.offset() + 1)), Duration.ofSeconds(10));
                    handled++;
                    if (maxMessages > 0 && handled >= maxMessages) break;
                }
            }
        } catch (WakeupException e) {
            if (!stopping.get()) throw e; // 仅把主动关闭引发的wakeup视为正常退出
        } finally {
            try { Runtime.getRuntime().removeShutdownHook(hook); }
            catch (IllegalStateException ignored) { /* JVM已在关闭 */ }
        }
    }
}

javac -cp 'lib/*' OrderConsumer.java               # 编译完整消费者示例
java -cp '.:lib/*' OrderConsumer client.properties orders orders-demo-check 1 # 新实验组读取并处理一条
# 再次运行同一个组时从已提交位置继续；换一个新组可独立回放已有数据

示例：处理 offset=42 后提交 43，表示下次从 43 开始。若处理成功但提交前崩溃，42 可能重投；若 handle 抛异常，则不会提交这条或之后的记录。关闭 Consumer 不等于业务已成功，不能在 finally 中无条件提交整个 poll 的位置。

消费者 API 的线程安全边界、手动提交和位移含义可查 KafkaConsumer 4.0 API。

5. 批量、异步与重平衡时怎么提交

逐条提交开销大，可以按分区处理一批后提交该分区“连续成功”的下一位置。若 offset 100、102 已完成而 101 失败，不能提交 103；101 会被跳过。异步任务完成顺序与拉取顺序可能不同。

场景 建议做法 容易踩的坑
多消费者扩容 每个进程/线程独占一个 Consumer 多线程同时 poll 同一个实例
单分区要保序 对该分区串行处理 放进普通线程池后顺序完成不了
单次处理太慢 减少 max.poll.records、批量访问下游、缩短调用超时 只增大 session.timeout.ms
worker并发 主消费线程维护分区成功水位、pause/resume与背压 worker直接提交最新poll位置
分区被撤回 停止对应任务、处理可提交的连续水位、清理所有权 撤回后任务继续写入并提交
分区丢失 按已失去所有权处理，不假装还能成功提交 把 lost 与正常 revoke 同样处理
commitAsync失败 保留结果、避免过时提交覆盖新进度 盲目重试旧回调中的位移

异步提交回调失败后重试旧位移，可能把已提交的新进度写回旧值，从而增加重投。需要可证明的单调策略；不熟悉这种边界时，优先使用清晰的同步提交和分区级批处理。

pause 只是暂停取某些分区的数据，仍需及时 poll 维护组。限流时还应限制在途业务任务数量，不能把 Kafka 拉取速度当成下游可承受速度。

6. 顺序性与分区选择

Kafka 的顺序范围是分区，不是整个主题。相同业务 key 一般映射到同一分区，但要满足生产端分区策略一致、分区数稳定、消费者按序处理等条件。

例如订单创建、支付、取消要按 order_id 分区，而不是每条消息随机 key。不同订单可并行，同一订单串行。一个超级热点 key 不会因为增加消费者实例自动加速。

扩分区会改变后续 key 的映射，历史消息仍留在原分区。需要在业务层定义迁移屏障或顺序版本，不能扩完分区就继续承诺跨新旧分区严格顺序。

无 key 消息的默认分区策略随客户端版本演进，不把它固定描述成 round-robin。自定义分区器要处理空 key、分区不可用、负哈希与扩分区；仅为“平均一点”就重写分区器，往往会增加问题。

7. 消息太大、超时与重试怎么排查

现象/错误 先检查 处理与验证
RecordTooLargeException 序列化后大小、producer max.request.size、topic max.message.bytes、Broker message.max.bytes 优先对象存储+引用或拆包，再统一调整限额
Failed to allocate memory buffer等待、生产速率、Broker响应、Sender是否阻塞 先定位出口瓶颈，再评估缓冲区
TimeoutException 元数据、地址可达性、请求与交付上限、重试 保留事件ID，确认可能成功的模糊结果
NotEnoughReplicas ISR与min ISR 恢复副本健康，不先降低可靠性
CommitFailedException poll超时、rebalance、分区所有权 停止错误提交，处理重投与幂等
SerializationException 数据格式、schema、反序列化器与坏消息所在分区位移 留下证据，走明确的隔离流程

大消息还要考虑副本抓取和消费抓取预算，包括 replica.fetch.max.bytes、replica.fetch.response.max.bytes、max.partition.fetch.bytes、fetch.max.bytes。部分抓取限制允许首个大批次返回以保持进度，不能简单理解成超过就永远读不到。放大限额会增加内存、GC和网络压力，需压测与容量验证。

重试要有上限、退避与分类。认证失败、配置错误、确定的业务非法数据不能无限重试；瞬时超时与协调器切换通常需要客户端按协议重试。重试主题会打破原队列的直接顺序，须为同一实体定义处理策略。

坏消息隔离至少记录来源 topic/partition/offset、事件ID、错误原因与重试次数。只有确认隔离数据已可靠保存，才可按约定推进原位移；隔离投递失败就提交位移，会造成另一种丢失。

8. 从指定位置重新消费

先确认是临时读取，还是修改正式消费者组的进度。临时检查某分区的记录可以不加入业务组：

bin/kafka-console-consumer.sh --bootstrap-server "$BS" --topic "$TOPIC" --partition 0 --offset 42 --max-messages 5 --timeout-ms 10000 --property print.partition=true --property print.offset=true # 从分区0位移42起限量检查

示例：安全集群补 --consumer.config "$CLIENT_CONFIG"。若 42 已因留存被删除，检查结果受工具的重置策略影响，先查可用起止位移；该命令不应被用于证明业务组已回退。

修改正式组位移时，先停止该组全部消费者，记录业务补偿计划，确认幂等和所需消息还在。下面沿用运维篇的 BS/TOPIC/GROUP/ADMIN：

bin/kafka-consumer-groups.sh --bootstrap-server "$BS" "${ADMIN[@]}" --describe --group "$GROUP" --state # 必须确认组已无活跃成员
bin/kafka-consumer-groups.sh --bootstrap-server "$BS" "${ADMIN[@]}" --describe --group "$GROUP" > offsets-describe-before.txt # 记录已提交位置及原本为-的分区
bin/kafka-consumer-groups.sh --bootstrap-server "$BS" "${ADMIN[@]}" --group "$GROUP" --topic "$TOPIC" --reset-offsets --to-current --export --dry-run > offsets-before.csv # 保存当前位置方案，不执行修改
bin/kafka-consumer-groups.sh --bootstrap-server "$BS" "${ADMIN[@]}" --group "$GROUP" --topic "$TOPIC" --reset-offsets --to-earliest --dry-run # 只预览本次回放位置
bin/kafka-consumer-groups.sh --bootstrap-server "$BS" "${ADMIN[@]}" --group "$GROUP" --topic "$TOPIC" --reset-offsets --to-earliest --execute # 示例：明确要重放全部可用历史时才执行
bin/kafka-consumer-groups.sh --bootstrap-server "$BS" "${ADMIN[@]}" --describe --group "$GROUP" # 核对各分区新进度，再启动消费者

示例：只重放一个分区可将 topic 参数改成 orders:0；按时间可使用工具对应的 --to-datetime，需要先确认时区和目标 offset。auto.offset.reset=earliest 仅在没有可用提交位置或位置越界时生效，不会把已有组每次都强制拉回最早。

需要恢复原位移时，保持消费者停止，先预览再执行：

bin/kafka-consumer-groups.sh --bootstrap-server "$BS" "${ADMIN[@]}" --group "$GROUP" --reset-offsets --from-file offsets-before.csv --dry-run # 预览原位置
bin/kafka-consumer-groups.sh --bootstrap-server "$BS" "${ADMIN[@]}" --group "$GROUP" --reset-offsets --from-file offsets-before.csv --execute # 执行位移回退，业务副作用不会一起回退

示例：CSV 只保存消费位置，不能恢复数据库或已经过期的 Kafka 消息。--to-current 对原先没有提交位移的分区会按工具规则生成位置，因此导出前还要保存原始 --describe 输出，记录 CURRENT-OFFSET 为 - 的分区；不能把 CSV 当成完整状态备份。若原先 orders:2 没有提交位置，而本次重置创建了它，恢复 CSV 后还要在组停止时清除这个分区的提交：

bin/kafka-consumer-groups.sh --bootstrap-server "$BS" "${ADMIN[@]}" --group "$GROUP" --delete-offsets --topic orders:2 # 仅恢复事先记录的“原本无提交位置”分区，不对其他分区执行

再次 describe 核对恢复结果后才启动消费者。清除提交位置后，首次读取还受应用 auto.offset.reset 策略影响。

9. Kafka 到 Kafka 的事务示例

适用于“从源 Topic 读 → 处理 → 写目标 Topic → 提交源位移”需要一起提交的情况。输入、输出与位移必须在同一 Kafka 集群，消费者使用 read_committed。目标主题先创建，不从源写回源。

下面的完整程序只处理一次非空 poll后退出，便于观察事务。生产环境应围绕相同事务边界管理循环、停机和错误恢复。

保存为 KafkaTxCopy.java：

import java.io.InputStream;
import java.nio.file.Files;
import java.nio.file.Path;
import java.time.Duration;
import java.util.HashMap;
import java.util.List;
import java.util.Map;
import java.util.Properties;
import org.apache.kafka.clients.consumer.ConsumerRecord;
import org.apache.kafka.clients.consumer.ConsumerRecords;
import org.apache.kafka.clients.consumer.KafkaConsumer;
import org.apache.kafka.clients.consumer.OffsetAndMetadata;
import org.apache.kafka.clients.producer.KafkaProducer;
import org.apache.kafka.clients.producer.ProducerRecord;
import org.apache.kafka.common.TopicPartition;

public class KafkaTxCopy {
    public static void main(String[] args) throws Exception {
        if (args.length != 5 || args[1].equals(args[2])) {
            throw new IllegalArgumentException("用法: 配置文件 sourceTopic targetTopic group transactionalId；源和目标不能相同");
        }
        Properties base = new Properties();
        try (InputStream in = Files.newInputStream(Path.of(args[0]))) { base.load(in); }
        Properties cp = new Properties();
        cp.putAll(base);
        cp.setProperty("group.id", args[3]);
        cp.setProperty("enable.auto.commit", "false");
        cp.setProperty("auto.offset.reset", "earliest");
        cp.setProperty("isolation.level", "read_committed");
        cp.setProperty("max.poll.records", "100");
        cp.setProperty("key.deserializer", "org.apache.kafka.common.serialization.StringDeserializer");
        cp.setProperty("value.deserializer", "org.apache.kafka.common.serialization.StringDeserializer");
        Properties pp = new Properties();
        pp.putAll(base);
        pp.setProperty("transactional.id", args[4]); // 同一逻辑实例重启稳定，不同并发实例必须不同
        pp.setProperty("acks", "all");
        pp.setProperty("enable.idempotence", "true");
        pp.setProperty("key.serializer", "org.apache.kafka.common.serialization.StringSerializer");
        pp.setProperty("value.serializer", "org.apache.kafka.common.serialization.StringSerializer");
        try (KafkaConsumer<String, String> c = new KafkaConsumer<>(cp);
             KafkaProducer<String, String> p = new KafkaProducer<>(pp)) {
            p.initTransactions(); // 恢复相同transactional.id的旧会话状态
            c.subscribe(List.of(args[1]));
            long deadline = System.nanoTime() + Duration.ofSeconds(30).toNanos();
            while (System.nanoTime() < deadline) {
                ConsumerRecords<String, String> batch = c.poll(Duration.ofSeconds(1));
                if (batch.isEmpty()) continue;
                p.beginTransaction();
                Map<TopicPartition, OffsetAndMetadata> next = new HashMap<>();
                for (ConsumerRecord<String, String> r : batch) {
                    p.send(new ProducerRecord<>(args[2], r.key(), r.value())); // 同一事务写目标
                    next.put(new TopicPartition(r.topic(), r.partition()),
                            new OffsetAndMetadata(r.offset() + 1));
                }
                p.sendOffsetsToTransaction(next, c.groupMetadata()); // 提交源位移，不能再用commitSync
                p.commitTransaction(); // 等待发送结果，并原子提交目标消息和源位移
                System.out.printf("事务已提交，处理%d条%n", batch.count());
                return;
            }
            throw new IllegalStateException("30秒内没有读到可处理消息");
        }
        // 任意异常直接退出并关闭，不在不了解错误类别时继续复用会话
    }
}

# 先在实验集群创建orders-copy；生产主题按实际副本规划创建
bin/kafka-topics.sh --bootstrap-server "$BS" "${ADMIN[@]}" --create --topic orders-copy --partitions 3 --replication-factor 1
javac -cp 'lib/*' KafkaTxCopy.java                 # 工作目录中编译事务示例
java -cp '.:lib/*' KafkaTxCopy client.properties orders orders-copy orders-tx-demo orders-copy-instance-0 # 一个逻辑实例的稳定事务ID
bin/kafka-console-consumer.sh --bootstrap-server "$BS" --topic orders-copy --from-beginning --isolation-level read_committed --max-messages 1 --timeout-ms 10000 # 只查看已提交事务的输出

示例：源主题至少有一条消息，且新组尚未消费，才能完成这次验证。生产者、消费者与命令各补相应安全配置。

这个示例故意遇错退出。持续运行的服务需要区分可中止错误、致命 fencing/授权错误，以及提交结果不确定的超时：不能捕获所有异常后一律 abortTransaction() 并继续。特别是 commit 超时后，应按本版本 API 规定重试同一次提交或执行受控恢复，不在同一未决会话直接开始新事务。

异常关闭后未决事务可能暂时阻挡 read_committed；以稳定事务 ID 重新初始化会话可参与恢复，但并不替代错误分类与监控。事务 API 的约束见 KafkaProducer 4.0 API。

10. read_committed 读不到、Lag 却不大

read_committed 不返回未提交和已中止事务中的数据；遇到尚未结束的事务时，后面的消息即使已经写到日志，也可能暂时不可见。

排查顺序：确认目标主题确实有数据 → 确认消费者隔离级别 → 查生产者是否执行 commit/abort → 查事务超时、fencing 和协调器日志 → 再核对分区 HW 与 LSO。

不能因为普通控制台消费者看到了消息，就证明事务已提交；也不能看到 Lag=0 就认为业务已执行成功。用 read_committed 消费、检查目标业务结果和源组提交位置，共同验证事务链路。

11. 新消费者协议与频繁 Rebalance

4.0.2 默认仍是 group.protocol=classic；设为 consumer 才使用新消费者协议。新协议由服务端承担分配，客户端的 heartbeat.interval.ms、session.timeout.ms、partition.assignment.strategy 不能按 classic 的方式继续使用。

classic组常见触发点 先收集什么 处理方向
超过 max.poll.interval.ms 单次poll到下次poll间隔、慢业务调用 缩小批次、控制超时、处理背压
心跳长时间无法完成 GC停顿、CPU限流、网络、协调器错误 修资源与连接问题，再评估超时
滚动发布不断换成员 发布节奏、group.instance.id、撤回记录 规划静态成员唯一性与超时，评估协作式分配
订阅/分区变化 topic变更与分配日志 减少不必要变化，验证策略一致性
策略不兼容 INCONSISTENT_GROUP_PROTOCOL、各实例参数 按兼容路径统一分配策略与协议

静态成员减少短暂重启造成的重分配，但会影响故障接管等待时间；不同并发实例不能复用相同 group.instance.id。协作式重平衡和新消费者协议也不是同一件事。

协议升级前验证客户端、服务端、分配器和监控兼容性，按 消费者重平衡协议说明选择迁移方式，不能一次复制几项参数就认为已经无中断升级。

12. Connect 与 Streams 什么时候用

连接数据库、文件、对象存储等外部系统时，Connect 负责连接器任务与位移管理；对 Kafka 事件做过滤、聚合和关联时，Streams 提供嵌入应用的处理库。它们都有自己的故障面，不是“Broker收发正常就一定正常”。

Connect 出问题时先查任务状态，再看失败 trace 和连接器日志：

curl -fsS --max-time 5 http://127.0.0.1:8083/connectors # 在已有Connect管理环境列出连接器
curl -fsS --max-time 5 http://127.0.0.1:8083/connectors/orders-source/status # 查看连接器及各任务状态

示例：连接器 RUNNING 但某个 task FAILED，仍可能没有数据进入 Kafka。orders-source 换成真实名称；安全环境使用对应 HTTPS 和管理认证。先修复外部凭据、格式、权限或网络，再按维护流程重启失败任务，不仅循环重启整个 Connect。

Streams 的 application.id 同时关联消费者组、内部主题及状态恢复。相同应用的多个实例使用同一个 ID，不同逻辑应用使用不同 ID。扩实例也受分区/任务并行度限制。

问题 核对内容
聚合结果延迟出现 缓存/提交、事件时间、窗口与 grace，不把窗口大小当固定输出定时器
Join缺数据 key、分区数、分区策略、表是否就绪，leftJoin右侧可能为null
重启恢复很慢 本地状态目录、changelog大小、restore吞吐与磁盘
重复写外部系统 Streams事务只覆盖其支持的Kafka处理边界，外部副作用仍需幂等
重置应用 停全部实例，先理解输入位移、内部主题与本地状态的处理范围，不能只删本地目录

连接器源码和配置也要随目标版本核对。示例 FileStreamSourceConnector 适合演示，不直接承担多机器生产日志采集；尤其要检查插件路径、文件轮转和任务实际运行在哪个 Worker。
