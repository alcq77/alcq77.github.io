Nginx 配置、部署与日常运维

知知行笔记·约 50 分钟阅读
nginxlinuxproxyhttpswebsocketoperationstroubleshooting

配置 Nginx 静态网站、前后端代理和 HTTPS，并处理日志、权限及常见访问故障。示例域名 demo.example.com、服务器地址 192.0.2.10、目录 /srv/demo 按实际环境替换；普通用户执行管理命令需要相应sudo授权。

各配置按场景分别使用。“完整站点配置”放在已被 http 包含的站点文件中，“片段”放入指定层级，避免重复定义站点或 location。

查配置含义看第2项的“常用配置项速查”；修改后的备份、校验、加载、验证与回退统一看第18项。

1. 先找到实际运行的 Nginx

command -v nginx                        # 当前PATH是否能找到
ps -ww -eo pid,ppid,user,args | grep '[n]ginx' # 主进程、worker和参数
sudo ss -lntp 'sport = :80'             # 核对80端口归属
sudo ss -lntp 'sport = :443'            # 核对443端口归属
systemctl status nginx --no-pager -l     # 系统服务安装时查看
systemctl cat nginx --no-pager           # 核对单元中的程序、配置和启动方式

示例：command -v没输出，但进程显示 /opt/nginx/sbin/nginx，说明是自定义安装，应使用该路径，不是再装一个Nginx。| grep把进程列表的标准输出交给grep筛选，不修改进程。

nginx -v                 # 版本，通常输出到标准错误
nginx -V                 # 编译参数、模块和默认路径
sudo nginx -t            # 检查语法，并尝试打开引用的文件
sudo nginx -T            # 检查并输出磁盘上的主配置及include文件，不会加载到运行进程

示例：-V中的 --conf-path 可帮助找到默认主配置；-T还会输出实际include的内容，但不能证明运行进程已经应用这些内容。完整配置可能包含内网地址、认证信息或令牌，分享前脱敏。服务若指定了额外的 -p/-c/-g，检查命令也要保留相应参数。

命令参数见 Nginx官方说明。

尚未安装？展开查看安装与验证方法

先执行 cat /etc/os-release 确认系统。以下为发行版已批准仓库的新安装示例，按系统选择一套，不先卸载已有实例。

# Ubuntu / Debian
sudo apt-get update
sudo apt-get install nginx curl openssl

示例：包安装可能自动启动服务；先确认80端口和维护窗口。发行版包的版本号与官方包可能不同，安全补丁也可能由发行版回补。

# 使用dnf的RHEL / Rocky / AlmaLinux等，包须由现有源提供
sudo dnf install nginx curl openssl

CentOS 7：已有二进制安装先沿用原程序，不另装RPM实例。需要新包时先查现有批准仓库，不能假设基础源一定有Nginx：

rpm -q nginx                  # 查看是否已有RPM安装；查不到不代表没有手动安装
yum info nginx                # 查看候选版本与来源，没有候选则先处理软件源
sudo yum install nginx curl openssl # 仅在确认候选来源、版本和依赖后安装
sudo nginx -t                 # 使用实际安装的二进制校验配置，手动安装时改成绝对路径
sudo systemctl enable nginx   # 仅对已提供nginx.service的新安装实例设置自启
sudo systemctl start nginx    # 现在启动，先确认端口未被其他实例占用

示例：没有候选包时由管理员提供批准的CentOS 7包源或经过维护的构建，不直接添加Stream源或自动装EPEL。仓库失效处理见服务器常用命令。

若确实需要nginx.org官方包，按 官方Linux包说明 选择受支持的系统、stable/mainline源，核对签名和迁移方式；不混用两套包来源，不直接执行不明网站的一键安装脚本。

nginx -v
sudo nginx -t
sudo systemctl enable --now nginx # 仅对新安装、确认可启动的实例执行
systemctl status nginx --no-pager -l
curl -I --connect-timeout 3 --max-time 5 http://127.0.0.1/

示例：先校验再启动；enable --now同时设置自启和立即启动。已有手动进程运行时，先完成管理方式切换，不能再启动第二份。安装其他排障工具见 服务器常用命令。

2. 常用目录与配置结构

内容 系统包常见位置 自定义安装示例
程序 /usr/sbin/nginx /opt/nginx/sbin/nginx
主配置 /etc/nginx/nginx.conf /opt/nginx/conf/nginx.conf
站点文件 /etc/nginx/conf.d/*.conf，或sites-enabled 由主配置include决定
日志 /var/log/nginx/ /opt/nginx/logs/或自定义目录
PID文件 /run/nginx.pid等 以pid指令及prefix为准

这些是常见位置，实际以运行参数和配置为准。Debian/Ubuntu可能通过 sites-available 保存、sites-enabled链接启用站点；不要把同一配置在两个include入口里重复加载。

结构示意如下，不用于覆盖发行版原主配置：

# main：全局层级
worker_processes auto;

events {
    worker_connections 1024;
}

http {
    include /etc/nginx/mime.types;
    default_type application/octet-stream;

    # 站点文件展开后属于http层级
    include /etc/nginx/conf.d/*.conf;
}

示例：server通常在http内，location在server内，upstream/map/log_format放在http层级。每条普通指令以 ; 结束，块使用 {}；# 后是注释。省略MIME映射可能导致CSS/JS类型错误或被浏览器拒绝。

层级或指令 主要职责
main 最外层的全局配置，如worker数量、运行用户、PID文件
events 连接处理相关配置，如每个worker的连接上限
http HTTP功能的公共配置，可包含多个站点、MIME映射、上游组和日志格式
server 一个虚拟站点的监听地址、端口、域名、证书等
location 在选定站点内，按请求URI选择静态文件、代理、跳转等处理方式
include 在当前位置引入其他配置文件，本身不是独立运行层级

示例：两个域名可由同一http内的两个server处理，每个server再用不同location区分首页、接口和静态资源；URL查询参数通常不参与location路径匹配。

include是按位置展开配置，不会自动补全层级。nginx -t提示“directive is not allowed here”时，先查指令所在层级。

2.1 常用配置项速查：属性含义、位置和示例

Nginx配置中的“属性”通常称为指令。下面的值用于解释写法，不是建议统一套用的默认值；按本机版本、编译模块和业务需求选择。表内 http / server / location 表示指令允许放在这些层级，不需要每层重复写。

进程、连接和公共配置：

配置项与示例 放在哪 作用与注意点
user nginx; main worker运行身份；按实际账户设置，需要网页及父目录的读取/遍历权限
worker_processes auto; main 自动确定worker数量，不是最大并发请求数
pid /run/nginx.pid; main master PID文件；应与服务单元、实际目录和管理命令一致
worker_connections 1024; events 单个worker的连接上限，包含客户端和上游等连接；还受文件句柄限制影响
include /etc/nginx/conf.d/*.conf; 按被引入内容的层级 在当前位置展开匹配文件；放在http内时，站点文件通常直接写server块
default_type application/octet-stream; http / server / location 没有匹配到MIME类型时的默认响应类型，不能代替 mime.types 映射
sendfile on; http / server / location 静态文件发送方式，按文件系统和运行环境验证效果
keepalive_timeout 65s; http / server / location 客户端空闲长连接保留时间，不是后端响应总超时
server_tokens off; http / server / location 隐藏部分响应头及错误页中的版本号，不代替安全更新

站点、静态文件、日志和响应：

配置项与示例 放在哪 作用与注意点
listen 80; server 监听地址与端口；127.0.0.1:80仅本机可连，default_server决定该监听入口的默认站点
server_name demo.example.com; server 按请求域名选站点，不创建DNS记录，不开放端口
root /srv/demo/html; http / server / location 用根目录拼接URI定位文件，具体映射见第8节
alias /srv/files/; location 将匹配路径映射到另一目录，路径替换规则与root不同
index index.html; http / server / location 目录请求尝试的首页文件，不是所有404的回退页
try_files $uri $uri/ =404; server / location 顺序检查文件或目录，最后一项为回退URI、命名location或状态码
autoindex off; http / server / location 控制目录列表；关闭列表导致的403先查首页和访问需求
client_max_body_size 20m; http / server / location 限制请求体大小，超限常见413；还需核对上游与其他网关限制
access_log /var/log/nginx/demo.access.log; http / server / location等 请求访问日志，可另指定已定义的格式；通常在请求结束时记录
error_log /var/log/nginx/demo.error.log warn; main / http / server / location等 错误日志路径与最低级别；加载阶段错误还可能写到原全局error日志
add_header X-Content-Type-Options nosniff always; http / server / location等 添加响应头；always扩大适用状态码范围，继承行为见第15节
expires 1h; http / server / location等 生成客户端缓存相关响应头；修改后还需检查浏览器/CDN已有缓存
return 301 https://demo.example.com$request_uri; server / location等 返回状态码或跳转；固定目标域名，永久跳转可能被客户端缓存

反向代理与HTTPS：

配置项与示例 放在哪 作用与注意点
upstream demo_backend { server 127.0.0.1:8080; } http 定义后端组；这里的server是上游成员，不是虚拟站点块
proxy_pass http://demo_backend; location等 转发到后端；带不带URI及末尾斜杠会影响路径，见第6节
proxy_set_header Host $host; http / server / location 设置发给后端的请求头，按后端期望的Host及可信代理边界选择
proxy_http_version 1.1; http / server / location 明确Nginx到后端使用的HTTP版本，不改变浏览器到Nginx的协议版本
proxy_connect_timeout 3s; http / server / location 建立上游连接的超时，不是整个请求的总时限
proxy_send_timeout 60s; http / server / location 向上游连续两次写操作之间的超时，不是整个上传的总时间
proxy_read_timeout 60s; http / server / location 从上游连续两次读操作之间的超时，不是整个响应的总时间
proxy_buffering off; http / server / location 关闭上游响应缓冲，常见于SSE流式响应；不等于关闭请求体缓冲
proxy_request_buffering off; http / server / location 控制请求体先缓冲再转发还是边接收边转发；按上传和后端能力选择
ssl_certificate /etc/nginx/certs/demo.fullchain.pem; http / server 站点证书及中间证书链文件
ssl_certificate_key /etc/nginx/certs/demo.key; http / server 证书私钥路径；限制文件权限，不能放进网页目录
ssl_protocols TLSv1.2 TLSv1.3; http / server 允许的TLS版本；需Nginx及链接库支持，CentOS 7旧环境先核对能力

示例：接口出现413时先找实际生效位置的 client_max_body_size；接口连接不上查 proxy_pass 和连接超时；SSE一直积攒到最后才返回查 proxy_buffering，并核对应用flush及整条代理链。不要把所有timeout一律调大。

2.2 配置中的变量和继承怎么看

写法 含义与例子
$uri 当前规范化URI，不含查询参数，内部重写后可能变化，如 /api/orders
$request_uri 原始请求URI，包含参数，如 /api/orders?page=1；跳转保留参数常用它
$args 当前查询参数，如 page=1，rewrite等操作可能修改它
$host 根据请求行、Host头或匹配站点名等确定的主机名；不能把任意客户端输入当可信域名
$http_host 收到的Host请求头原值，可能含端口，也可能为空
$remote_addr Nginx看到的对端IP；经过其他代理时不一定是真实用户IP
$proxy_add_x_forwarded_for 在已有X-Forwarded-For后追加对端IP；已有部分可能由客户端伪造
$scheme 当前请求到达Nginx时的http或https；前置网关终止TLS时未必等于外部协议
$request_time 请求处理总耗时，单位秒，结合上游耗时字段判断慢在哪层

示例：try_files $uri $uri/ /index.html;里的变量由Nginx处理，不是Linux shell变量，不要把配置内容直接作为未加保护的shell命令执行。

较外层配置常可作为内层默认值，但继承规则由具体指令决定。root、请求体限制等按层级选择；add_header、proxy_set_header等成组指令在内层重新定义时，传统规则可能不再继承上层同类配置。不要只看http层就认定某个location一定使用同一个值。表格列出的层级为常用位置，细节及版本要求见核心进程指令、HTTP核心指令、代理指令、HTTPS指令。

3. 启动、停止、reload与自启

systemd管理的实例按需选择命令，不要整段连续执行：

sudo systemctl start nginx         # 启动
sudo systemctl stop nginx          # 停止，影响访问
sudo systemctl restart nginx       # 停后再启动，可能中断服务
sudo nginx -t                      # 修改后先校验
sudo systemctl reload nginx        # 校验通过再平滑加载配置
sudo systemctl enable nginx        # 开机自启，不立即启动
sudo systemctl disable nginx       # 关闭自启，不立即停止
systemctl is-enabled nginx         # 查询自启状态

示例：日常修改站点优先“检查 → reload”，不为改一个代理地址直接restart。reload会启动新worker并让旧worker处理已有连接；长连接可能让旧worker暂时保留。语法错误时旧配置通常继续服务，但仍须核对reload结果和日志。

自定义安装示例，始终保持相同prefix和配置文件：

sudo /opt/nginx/sbin/nginx -p /opt/nginx/ -c conf/nginx.conf -t # 校验
sudo /opt/nginx/sbin/nginx -p /opt/nginx/ -c conf/nginx.conf    # 确认未运行后启动
sudo /opt/nginx/sbin/nginx -p /opt/nginx/ -c conf/nginx.conf -s reload # 重载
sudo /opt/nginx/sbin/nginx -p /opt/nginx/ -c conf/nginx.conf -s quit   # 优雅停止

示例：-p指定prefix，-c指定配置；相对配置路径基于prefix。-s stop是快速停止，-s quit是优雅停止。通过错误的PID文件发信号可能操作失败或误操作其他实例，不能只凭目录名猜测。

自定义服务自启可复用已有服务单元；不要把默认后台运行的Nginx直接放进 Type=simple。若选择simple，应使用 daemon off; 保持前台运行；已有打包服务优先沿用原方式。管理原理见 systemd笔记。

4. 完整示例：静态网站

假设主配置已在http内include /etc/nginx/conf.d/*.conf，页面位于 /srv/demo/html/index.html。创建 /etc/nginx/conf.d/demo.conf：

server {
    listen 80;
    server_name demo.example.com;

    root /srv/demo/html;
    index index.html;

    access_log /var/log/nginx/demo.access.log;
    error_log /var/log/nginx/demo.error.log warn;

    location / {
        try_files $uri $uri/ =404;
    }
}

示例：访问 /guide.html 对应 /srv/demo/html/guide.html，不存在就404；目录请求按index和目录规则处理。网站目录和日志目录必须已存在且权限正确，不在生产开启autoindex来“修复”目录403。

先检查并reload，再指定Host在本机验证：

sudo nginx -t
sudo systemctl reload nginx
curl -i --connect-timeout 3 --max-time 5 -H 'Host: demo.example.com' http://127.0.0.1/

示例：预期返回首页和合适的 Content-Type。仅访问IP可能命中另一个默认站点；DNS还没生效时可用Host头测试HTTP，HTTPS使用后面的 --resolve。

server_name不创建DNS记录，也不开放防火墙。多个站点共享端口时，要同时核对listen地址、端口、Host；未匹配的Host会进入该地址端口的默认server，不由 server_name _ 的名字本身决定。

5. 完整示例：Vue / React前端与后端接口

此例用于根路径部署、使用history路由的SPA，后端位于本机8080，后端接口本身带 /api/ 前缀。用此server替换上一节的server，不重复添加相同域名站点：

server {
    listen 80;
    server_name demo.example.com;
    root /srv/demo/html;
    index index.html;

    location = /api {
        return 308 /api/;
    }

    location ^~ /api/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # 假设构建产物统一放在/assets/，不存在的资源直接404
    location ^~ /assets/ {
        try_files $uri =404;
    }

    location = /index.html {
        add_header Cache-Control "no-cache";
    }

    location / {
        try_files $uri $uri/ /index.html;
    }
}

示例：浏览器刷新 /users/42 时回退到index，由前端路由处理；/api/users转发为后端 /api/users。/assets/missing.js应404，不能返回index伪装成成功的JS；若构建目录是 /static/，相应调整资源location。

curl -I -H 'Host: demo.example.com' http://127.0.0.1/users/42
curl -I -H 'Host: demo.example.com' http://127.0.0.1/assets/missing.js
curl -i -H 'Host: demo.example.com' http://127.0.0.1/api/health

示例：前两个假设分别返回200和404，最后一个要与后端真实的只读接口相符。子路径部署如 /portal/ 还需同步前端base/router、资源路径和Nginx回退目标，不能只改server_name。

6. proxy_pass末尾斜杠：后端到底收到什么

以下假设普通前缀 location /api/，请求为 /api/users?id=1：

proxy_pass 后端收到的路径
http://127.0.0.1:8080 /api/users?id=1，不指定URI部分时保留路径
http://127.0.0.1:8080/ /users?id=1，匹配前缀替换成 /
http://127.0.0.1:8080/service/ /service/users?id=1，匹配前缀替换成 /service/

后端没有 /api 前缀时使用下面片段，替换前一例的对应location：

location ^~ /api/ {
    proxy_pass http://127.0.0.1:8080/;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}

示例：/api/health变为后端 /health。遇到后端404先核对路径，不直接加rewrite试错。正则location、命名location、变量proxy_pass及rewrite改变URI的情况有额外规则，不照搬上表。proxy_pass规则

Nginx到后端的 localhost/127.0.0.1 指Nginx所在的机器或容器；Nginx与应用分开部署时改用真实可达地址。前端HTTPS并不自动让Nginx到后端也变成HTTPS。

7. location匹配顺序

对同一server内的平级location，可按下面顺序理解：

  1. location = /health：精确命中则停止查找。
  2. 找出最长的前缀匹配；若该前缀带 ^~，跳过这一层的正则匹配。
  3. 否则按配置顺序检查正则，使用第一个命中的正则。
  4. 没有正则命中时使用之前找到的最长前缀。
# 以下片段放在server内
location = /health { return 200 "ok\n"; }
location ^~ /api/ { proxy_pass http://127.0.0.1:8080; }
location ~* \.(css|js|png)$ { try_files $uri =404; }
location / { try_files $uri $uri/ /index.html; }

示例：/health命中精确规则，/api/report.js仍走代理，/logo.PNG走不区分大小写的正则，其他路径走 /。普通前缀并不是按“谁写在前面”决定；~为区分大小写的正则，~*为不区分大小写。

嵌套location和内部重定向会影响后续匹配，初学配置优先保持平级和明确边界。/api/不会自动作为普通前缀匹配 /api 本身，所以示例单独处理裸路径。location规则

跳转与内部重写

# server内的两个独立示例
location = /old-guide {
    return 302 /guide;
}

location /legacy/ {
    rewrite ^/legacy/(.*)$ /api/$1 last;
}

示例：/old-guide向浏览器返回302，让客户端再次访问 /guide；/legacy/users在Nginx内部改为 /api/users，last让新URI重新选择location，浏览器地址本身不变。$1是正则中的第一组捕获内容，不能用作Shell变量解释。

break会停止当前rewrite指令处理、继续在当前location中处理请求，与 last 的重新匹配不同。长期迁移确认后可考虑永久跳转，但浏览器可能缓存；简单的路径前缀代理优先使用proxy_pass的明确URI映射，不为所有场景叠加rewrite。rewrite规则

8. root与alias：文件路径怎么拼

# 两种独立写法，选一种
location /files/ {
    root /srv/demo;
}

示例：/files/a.pdf对应 /srv/demo/files/a.pdf，root把完整URI拼到根目录后。

location /files/ {
    alias /srv/shared/;
}

示例：同样请求对应 /srv/shared/a.pdf，alias用目标目录替换匹配到的 /files/。目录location和alias都保持正确的尾部斜杠，避免边界不清或路径错误；正则location使用alias还涉及捕获组。

公开静态目录仅放可公开文件，不把配置、密钥、数据库备份放进root/alias目录；关闭目录列表也不能阻止已知路径访问。指向私有目录的符号链接也需要审查。alias与root说明

9. 完整示例：HTTPS与HTTP跳转

假设已持有 demo.example.com 的有效证书，完整证书链位于 /etc/nginx/certs/demo.fullchain.pem，私钥为同目录 demo.key。此例是独立站点配置：

server {
    listen 80;
    server_name demo.example.com;
    return 308 https://demo.example.com$request_uri;
}

server {
    listen 443 ssl;
    server_name demo.example.com;

    ssl_certificate /etc/nginx/certs/demo.fullchain.pem;
    ssl_certificate_key /etc/nginx/certs/demo.key;
    ssl_protocols TLSv1.2 TLSv1.3;

    root /srv/demo/html;
    index index.html;
    location / {
        try_files $uri $uri/ =404;
    }
}

示例：HTTP /guide?a=1跳至 https://demo.example.com/guide?a=1。固定目标域名避免把任意Host照搬进跳转地址；308保留请求方法与请求体，但业务仍应直接使用HTTPS入口，不在明文HTTP提交秘密数据。

证书文件通常包含站点证书和所需中间证书，顺序与内容应正确；私钥只允许必要管理身份读取，不能放进网站目录或公开仓库。TLSv1.3需要对应Nginx/OpenSSL能力，不支持的旧环境应升级并采用相容配置。

sudo nginx -t
sudo systemctl reload nginx
curl -I --resolve demo.example.com:443:192.0.2.10 https://demo.example.com/
openssl s_client -connect 192.0.2.10:443 -servername demo.example.com \
  -verify_hostname demo.example.com -verify_return_error < /dev/null

示例：--resolve临时把指定域名和端口指向测试IP，同时保持正确Host、SNI及证书校验，比只加HTTP Host头测试HTTPS更完整。< /dev/null让标准输入立即结束，不是把错误信息丢弃。不要用 curl -k 当作正式验收。

CentOS 7先用 nginx -V 查看编译参数及OpenSSL版本；系统 openssl version不一定等于Nginx实际链接版本。若 s_client没有 -verify_hostname，使用上面的curl验收；旧TLS库不能使用TLS 1.3时，先用已支持的TLS 1.2配置通过校验，再按维护计划升级，不能直接填写不受支持的协议。

检查本地证书有效期：

openssl x509 -in /etc/nginx/certs/demo.fullchain.pem -noout -subject -issuer -dates
openssl x509 -in /etc/nginx/certs/demo.fullchain.pem -noout -checkend 2592000

示例：第二条检查证书在未来30天（2592000秒）内是否会到期，成功退出表示在该时间范围后仍有效；它不替代完整链和域名验证。证书续期后要校验并reload，且检查对外实际提供的证书，不能只看磁盘文件已更新。

采用ACME工具时，按实际DNS/HTTP验证方式配置自动续期和成功后的reload钩子；本例80端口直接跳转，不包含专门的HTTP-01验证目录，需按证书工具要求补齐。HTTPS和证书链规则见 官方HTTPS说明。

10. 完整示例：WebSocket代理

将下列内容放在http包含的站点文件中，map与server并列。后端位于本机8081，WebSocket路径为 /ws/：

map $http_upgrade $connection_upgrade {
    default upgrade;
    '' close;
}

server {
    listen 80;
    server_name ws.example.com;

    location /ws/ {
        proxy_pass http://127.0.0.1:8081;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 300s;
    }
}

示例：客户端连接 ws://ws.example.com/ws/，后端仍收到 /ws/；成功握手应返回101，再验证真实消息和心跳。后端只支持其他路径时按前面斜杠规则调整。

Upgrade与Connection是逐跳头，需要明确传递。上面的300秒是两次读取上游数据之间的空闲超时，不是“连接只能活300秒”；后端心跳和客户端重连也要匹配。HTTPS页面应连接 wss://，否则可能被浏览器阻止；可将此location及map结合前节443站点使用。WebSocket官方说明

11. SSE与流式响应

SSE不是WebSocket，不需要Upgrade头。以下片段放在对应server内，后端提供 /events/ 流式接口：

location /events/ {
    proxy_pass http://127.0.0.1:8080;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 300s;
}

示例：响应缓冲关闭后，后端及时flush的事件可更及时送到客户端；应用仍须返回正确的 text/event-stream、持续输出有效事件和心跳。CDN、其他网关和压缩层也可能缓冲，需要逐层排查。

curl -N --max-time 20 -H 'Host: demo.example.com' http://127.0.0.1/events/

示例：-N关闭curl自身的输出缓冲，观察是否逐条收到事件；20秒后curl主动结束测试，不代表服务异常。不要为一个流式接口全局关闭所有站点的缓冲。proxy_request_buffering控制的是请求体缓冲，与响应缓冲不同。缓冲配置

12. 上传大小与超时

# server内的示例片段；替换既有/upload/对应规则，避免重复定义
location /upload/ {
    client_max_body_size 20m;
    proxy_pass http://127.0.0.1:8080;
    proxy_connect_timeout 3s;
    proxy_send_timeout 60s;
    proxy_read_timeout 60s;
}

示例：请求体超过20MB可能在Nginx层返回413；还要检查后端、其他代理的限制。client_max_body_size限制整个请求体，multipart文件外还有表单开销，因此“20MB文件”不保证能通过20m限制。

参数 主要含义
client_max_body_size 允许的请求体大小，0表示禁用该限制，不能为省事默认无限制
proxy_connect_timeout 建立到上游连接的等待时间
proxy_send_timeout 向上游两次写操作之间的超时
proxy_read_timeout 从上游两次读操作之间的超时，不是整个请求总时长
client_body_timeout 读取客户端请求体两次读操作之间的超时

长任务优先评估异步任务/查询状态等方案，不把所有超时全局调成很大。上传临时目录空间、写权限、磁盘I/O也会影响大文件；修改限制后用已授权的测试文件检查，不对生产接口随意发起上传。

13. 完整示例：多个后端负载均衡

以下upstream与server并列，放在http包含的站点文件中：

upstream demo_backend {
    least_conn;
    server 127.0.0.1:8080 max_fails=3 fail_timeout=30s;
    server 127.0.0.1:8081 max_fails=3 fail_timeout=30s;
    keepalive 16;
}

server {
    listen 80;
    server_name api.example.com;

    location / {
        proxy_pass http://demo_backend;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

示例：least_conn倾向活动连接少的后端，适合请求时长有差异的场景；删除该行则使用默认加权轮询。keepalive 16缓存空闲上游连接，并非限制后端总连接数为16。

配置 使用考虑
默认轮询、weight 一般分流或权重分配，实际请求分配不保证严格逐次交替
least_conn 按活动连接情况选择
ip_hash 可提供基于IP的黏性，但NAT、代理和客户端IP变化会影响分布
backup 主组不可用时的备用节点，需符合负载均衡方法限制

max_fails/fail_timeout属于被动失败判断，不是定时主动请求健康接口；何种响应计为失败还与代理重试配置相关。单后端有特殊处理，不能把多节点故障切换承诺套到单节点。部分主动健康检查能力依赖商业版或其他方案。upstream说明

不要随意对POST等非幂等操作增加重试，避免重复创建订单或写数据。后端已经共享数据库，也不等于登录会话、文件和任务状态天然适合多副本。

14. 转发头、真实IP与可信代理

常见片段，放在代理location内：

proxy_set_header Host $host;
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;

示例：后端可依据可信代理传递的协议生成链接，但不能把任意客户端提供的 X-Forwarded-* 当成事实。$proxy_add_x_forwarded_for会在现有链后追加地址，链中较早的值可能由客户端提供；后端应按可信代理链解析，不盲取第一个IP。

Nginx前面还有负载均衡时，$remote_addr默认可能是负载均衡地址。仅对已经确认的代理来源使用realip片段：

# http或server内；只信任真实代理地址，示例IP必须替换
set_real_ip_from 192.0.2.20/32;
real_ip_header X-Forwarded-For;
real_ip_recursive on;

示例：不设为信任全部互联网，且确认上游会清理/维护正确的头。该模块需编译支持，可在 nginx -V 中核对；HTTPS若终止于前置代理，$scheme仍可能是http，需按可信拓扑处理协议头，不能随意透传客户端值。realip说明

Nginx到上游也采用HTTPS时，应另外启用正确的SNI、上游名称及证书链验证；不要只写 proxy_pass https://... 就默认已验证上游身份。

15. 缓存、压缩与跨域

静态文件缓存片段，假设 /assets/ 文件名包含内容hash，改动后会生成新文件名：

location ^~ /assets/ {
    try_files $uri =404;
    expires 7d;
}

location = /index.html {
    add_header Cache-Control "no-cache";
}

示例：hash资源可缓存，index应允许重新验证，避免发布后入口仍指向旧资源。no-cache不是禁止保存，它要求使用前重新验证；含私密数据时应按需求使用 no-store 等策略。CDN缓存和代理缓存需分别排查。响应头与缓存说明

传统 add_header 继承规则容易踩坑：下层定义自己的add_header时，可能不再继承上层同类配置。新版本有相关扩展，跨版本配置不能直接假设追加继承；CORS和安全头实际以curl/浏览器响应为准。

# http/server内的按需压缩片段
gzip on;
gzip_vary on;
gzip_types text/plain text/css application/javascript application/json;

示例：用于适合压缩的文本，不对已经压缩的图片等一概重复压缩。流式和含敏感数据的响应要结合延迟、客户端及安全要求评估，不全局强套。

前端和API经同域不同路径代理时通常无需额外CORS；确需跨域时，明确允许的Origin、方法、请求头和凭证策略，OPTIONS也要匹配业务。不要直接复制 Access-Control-Allow-Origin: * 与凭证同时开启的错误组合，也不要让后端和Nginx同时输出重复CORS头。

16. access日志、error日志与耗时

在http内定义格式，再在server内引用：

# http层级
log_format demo_timing '$remote_addr [$time_local] "$request" '
                       '$status $body_bytes_sent rt=$request_time '
                       'upstream=$upstream_addr us=$upstream_status '
                       'uct=$upstream_connect_time uht=$upstream_header_time '
                       'urt=$upstream_response_time';

# 对应server内
# access_log /var/log/nginx/demo.access.log demo_timing;
# error_log /var/log/nginx/demo.error.log warn;

示例：实际使用时取消server内两条指令前的注释，并放进目标server。日志包含URI和查询参数，不把token或秘密放进URL；对外分享日志前脱敏。

字段 怎么看
status Nginx返回客户端的状态码
request_time 请求整体处理耗时，也可能受客户端上传/下载影响
upstream_addr / upstream_status 实际上游与状态，多个值可能对应多次尝试
upstream_connect_time 上游连接耗时
upstream_header_time 获取上游响应头耗时
upstream_response_time 上游响应耗时，需结合重试和传输情况看 
sudo tail -n 100 /var/log/nginx/demo.error.log # 最近日志
sudo tail -F /var/log/nginx/demo.access.log    # 持续跟踪，适应同名日志轮转
sudo journalctl -u nginx -b -n 100 --no-pager  # 服务管理与启动错误
sudo grep -nE 'upstream|timed out|Permission denied' /var/log/nginx/demo.error.log

示例：先按故障时间关联access/error及后端日志。tail -F按 Ctrl+C退出查看，不停止Nginx。access通常在请求结束时记录，长连接未结束时不一定立即出现最终记录。访问日志说明

日志轮转优先沿用系统包提供的logrotate配置。手工轮转后需要正确reopen；nginx -s reopen用于重新打开日志文件，不是reload配置。不要把正在写的日志直接删除后就认为空间一定释放，进程仍可能持有文件句柄。

17. 权限、SELinux与端口

ps -ww -eo user,pid,args | grep '[n]ginx' # 查worker实际用户
namei -l /srv/demo/html/index.html       # 各级目录的访问权限
ls -l /srv/demo/html/index.html          # 文件读权限

示例：主进程能读取配置不代表worker能读取网页；worker需要父目录的遍历权限和文件读权限。用户可能是nginx、www-data或其他值，按实际身份分配，只读静态站点不必给worker写权限。

SELinux拒绝读取网页或代理联网时，先查审计拒绝和合适的路径标签/布尔策略；由管理员按业务范围调整。不要用 chmod -R 777、关闭SELinux或让worker以root运行来掩盖问题。

# sudo dnf install policycoreutils-python-utils audit

18. 发布与回退：修改配置后的校验、加载和验证

执行顺序：确认实际实例与配置 → 备份 → 修改 → 校验成功后reload → 验证日志和业务 → 异常时回退。systemd管理与手动安装选择对应一套操作，不能混用默认路径与自定义实例。

18.1 备份并修改实际加载的文件

假设主配置已include /etc/nginx/conf.d/*.conf，本次只修改 /etc/nginx/conf.d/demo.conf。以下变量和命令在同一Bash终端逐步执行，备份或编辑失败时先处理错误，不继续加载：

NGINX_CONF=/etc/nginx/conf.d/demo.conf # 改为本次实际修改的文件；手动安装时也要改路径
NGINX_BACKUP="${NGINX_CONF}.bak-$(date +%Y%m%d-%H%M%S)" # 保存本次备份文件名，避免重复覆盖
sudo cp -p -- "$NGINX_CONF" "$NGINX_BACKUP" # 保留属性备份原配置，失败则停止
printf '%s\n' "$NGINX_BACKUP" # 记录备份位置，供本次回退使用
sudoedit "$NGINX_CONF" # 按授权编辑并保存，普通用户不必开启整个root会话

示例：备份名不以 .conf 结尾，避免被上述 *.conf 再次include；实际include若匹配所有文件，应备份到不被加载的目录。若同时改主配置、多个include、证书或前端文件，要保存整套对应版本；不是恢复一个站点文件就能回退全部变化。

18.2 校验并加载配置

保存配置文件不会自动生效。nginx -t只做检查，nginx -T再加上输出磁盘配置；两者都不会让正在运行的worker改用新配置。普通站点、代理和证书配置修改通常使用reload；它会让新worker承接新连接，旧worker处理已有连接后退出。不要用再次执行 nginx 代替reload，那是在尝试启动实例。

systemd管理：先完成上面的备份和修改，确认 systemctl cat nginx 中的程序、-p/-c/-g参数与校验命令一致。默认安装且没有额外参数时：

sudo nginx -t && sudo systemctl reload nginx # 校验成功才重载；失败则停在这里修复
systemctl status nginx --no-pager -l         # 查看服务状态与最近的管理日志
sudo journalctl -u nginx --since '5 minutes ago' --no-pager # 查看本次reload附近的服务日志
sudo tail -n 50 /var/log/nginx/error.log     # 核对原全局error_log路径，检查新worker或绑定失败
curl -i --connect-timeout 3 --max-time 5 -H 'Host: demo.example.com' http://127.0.0.1/ # 用新连接验证目标HTTP站点

示例：&&表示左侧退出码为0才执行右侧。校验通常会显示 syntax is ok 和 test is successful；有warning时也要检查，重复域名警告可能使某一站点配置被忽略。systemctl daemon-reload重新读取的是systemd单元文件，不会替Nginx加载nginx.conf；只有修改服务单元时才另行使用它。

手动安装：同样先备份、修改，始终使用原实例的二进制、prefix、配置和PID路径。下面只校验与重载，不启动第二份：

sudo /opt/nginx/sbin/nginx -p /opt/nginx/ -c conf/nginx.conf -t && sudo /opt/nginx/sbin/nginx -p /opt/nginx/ -c conf/nginx.conf -s reload # 两侧参数必须一致
sudo tail -n 50 /opt/nginx/logs/error.log    # 按原实例实际error_log路径检查加载错误
ps -ww -eo pid,ppid,user,args | grep '[n]ginx' # master通常不变，新worker出现，旧worker可能暂留
curl -i --connect-timeout 3 --max-time 5 -H 'Host: demo.example.com' http://127.0.0.1/ # 验证对应实例的实际监听入口

示例：-s reload返回成功主要说明信号发送成功，不能独自证明master完成新配置应用。master尝试打开新日志和监听socket等失败时，会继续使用旧配置；因此还要查原error日志，并验证本次修改的行为。只有绑定在其他地址/端口的实例，curl也要改为相应入口。重载过程说明

18.3 验证本次改动是否生效

改了什么 怎么验证 看到什么才算符合预期
静态目录、首页 带正确Host请求一个已知文件 正文是新文件，类型正确，不只是HTTP 200
域名、监听地址或端口 ss检查端口，再带Host/SNI请求 端口归属正确，命中目标站点
代理地址、路径 请求Nginx接口，对照后端直连与两端日志 后端收到预期URI，响应正文与业务状态正确
HTTPS证书 使用正确域名/SNI建立新连接 返回的是新证书，域名、证书链与有效期校验通过
响应头、缓存、压缩 curl -I查看实际目标资源，必要时显式发送Accept-Encoding 响应头符合配置，且浏览器/CDN缓存行为符合预期
上传限制、流式响应 在获准测试环境用边界大小文件或SSE/WebSocket客户端检查 上传结果、流式到达时间或101升级符合预期 
sudo ss -lntp 'sport = :80' # 改监听后检查实际端口及进程归属，端口按需替换
curl -I --connect-timeout 3 --max-time 5 --resolve demo.example.com:443:192.0.2.10 https://demo.example.com/ # 绕过DNS选IP，同时保留域名/SNI及证书验证

示例：nginx -T显示新配置但请求还是旧行为，按“实际实例与include → 本次reload日志 → 新连接 → Host/SNI及请求路径 → 上游 → 浏览器/CDN缓存”逐项核对。多台Nginx或负载均衡时逐台验证，不只改一台就检查公共入口。证书和长连接的详细验收见第9、10节；失败先保留日志，按下面的回退步骤恢复。

对代理接口，再把Nginx入口与后端直连分开验证；示例路径必须替换为实际存在的只读接口：

curl -i --connect-timeout 3 --max-time 5 -H 'Host: demo.example.com' http://127.0.0.1/api/health # 验证经过Nginx的接口路径与结果
curl -i --connect-timeout 3 --max-time 5 http://127.0.0.1:8080/api/health # 按proxy_pass映射改为后端实际路径，对照上游状态
sudo tail -n 50 /var/log/nginx/demo.access.log # 核对请求是否命中目标站点，按实际日志路径调整
sudo tail -n 50 /var/log/nginx/demo.error.log # 查看对应请求的上游、路径或权限错误

18.4 加载失败或业务异常时回退

若本次只改了前述站点文件，恢复同一终端中记录的备份；新开终端时先将两个变量设为实际路径，不能留空或使用另一轮备份：

printf '%s\n' "$NGINX_CONF" "$NGINX_BACKUP" # 先确认目标与备份路径属于本次变更
sudo cp -p -- "$NGINX_BACKUP" "$NGINX_CONF" # 确认路径后恢复文件；失败则停止，不继续加载
sudo nginx -t && sudo systemctl reload nginx # 仅适用默认配置的systemd实例，校验通过才加载回退配置

示例：手动安装改用18.2中相同二进制、prefix及配置参数的“校验成功再 -s reload”，不要套用系统服务命令。恢复后重新执行18.3的日志和业务检查；回退配置不恢复后端版本、DNS、证书或已缓存的响应，这些变化按各自备份恢复。

现象 优先检查
访问了另一网站 DNS、listen、Host/SNI、默认server、重复server_name
403 index是否存在、目录列表关闭、worker读取/遍历权限、访问规则、SELinux
静态文件404 root/alias映射、发布目录、资源base路径、文件是否真的存在

413 Nginx请求体限制、表单开销、其他代理与后端限制
499 客户端在响应前断开，结合耗时和代理链查原因，不直接算后端成功
502 上游拒绝/断连、协议错误、无法解析/无可用节点、权限，查error日志
504 等待上游超时；核对依赖和耗时，不直接无限延长timeout
WebSocket非101 请求路径、Upgrade/Connection、认证、源检查、上游支持
SSE积到最后才返回 应用flush、响应类型、Nginx/网关/CDN缓冲、压缩
JS报MIME或Unexpected token < 请求JS实际返回index或错误HTML，检查回退与资源路径
证书域名/链错误 SNI、server选择、SAN、证书链、磁盘与实际服务证书是否一致
redirect循环 TLS终止位置、可信协议头、应用base URL与跳转规则
地址已经占用 ss核对PID，是否另有Nginx、容器或重复启动入口
修改后不生效 是否改到实际include文件、是否reload成功、缓存/CDN、是否另一实例
