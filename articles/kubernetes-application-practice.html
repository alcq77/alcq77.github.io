Kubernetes 应用部署与配置实践

知知行笔记·约 18 分钟阅读
kubernetesdeploymentservicetroubleshooting

发布前确认环境

下列命令中的 demo 是示例命名空间，操作前替换为实际值。先检查当前集群和权限，避免把测试配置应用到生产集群。

# 显示当前 kubectl 上下文
kubectl config current-context
# 查看客户端和服务端版本
kubectl version
# 检查当前身份能否在目标命名空间创建 Deployment
kubectl auth can-i create deployments -n demo

镜像拉取失败

现象：Pod 显示 ErrImagePull 或 ImagePullBackOff。

执行顺序：查看 Pod → 读取事件中的具体错误 → 核对镜像名称、版本、仓库访问和凭据 → 修正声明文件 → 检查新 Pod。

# 查看命名空间内 Pod 及所在节点
kubectl get pods -n demo -o wide
# 查看目标 Pod 的镜像和最近事件；替换 Pod 名
kubectl describe pod demo-api-xxxxx -n demo
# 查看 Deployment 当前声明的镜像
kubectl get deployment demo-api -n demo -o jsonpath='{.spec.template.spec.containers[*].image}'

例如事件提示 manifest unknown，先核对仓库中是否存在该镜像标签；提示认证失败时，检查 Pod 使用的镜像拉取 Secret。不要把凭据粘贴到日志或工单中。

# 修正清单后，先检查本地文件与集群对象的差异
kubectl diff -f deployment.yaml -n demo
# 确认差异符合预期后应用清单
kubectl apply -f deployment.yaml -n demo
# 查看发布进度，等待新 Pod 就绪
kubectl rollout status deployment/demo-api -n demo --timeout=120s
# 复查 Pod 状态和重启次数
kubectl get pods -n demo -o wide

kubectl diff 发现差异时通常返回状态码 1，不一定是命令执行失败；权限或连接错误需单独检查。

Service 无法访问

执行顺序：确认 Pod 就绪 → 检查 Service 的 selector 和端口 → 查看 EndpointSlice → 在合适的网络位置分别测试 Pod 和 Service → 检查 DNS、网络策略和集群网络。

# 查看 Service、集群 IP 和端口
kubectl get service demo-api -n demo -o wide
# 检查选择器及 port、targetPort
kubectl describe service demo-api -n demo
# 查看 Service 对应的后端地址和端口
kubectl get endpointslice -n demo -l kubernetes.io/service-name=demo-api -o wide
# 查看匹配示例标签的 Pod，标签需改为 Service 实际 selector
kubectl get pods -n demo -l app=demo-api -o wide --show-labels

例如 EndpointSlice 为空，先核对 Service selector 是否与 Pod 标签一致，并检查就绪状态；后端端口错误时核对 targetPort 和应用实际监听端口。Service 无 selector 或使用自定义 EndpointSlice 时，应结合其实际配置判断。

滚动更新与健康检查

发布前检查 readiness、startup、liveness 的作用以及应用实际健康接口。readiness 决定 Pod 是否接收 Service 流量；startup 可给慢启动应用留出时间；liveness 持续失败可能触发容器重启，不能简单把依赖暂时不可用都当成需要重启。

# 查看 Deployment 的更新策略和 Pod 模板
kubectl get deployment demo-api -n demo -o yaml
# 查看更新进度
kubectl rollout status deployment/demo-api -n demo --timeout=120s
# 检查发布历史
kubectl rollout history deployment/demo-api -n demo
# 对照业务指标确认失败后，回退到上一版本
kubectl rollout undo deployment/demo-api -n demo
# 等待回滚完成
kubectl rollout status deployment/demo-api -n demo --timeout=120s

优雅退出需要应用处理终止信号、停止接收新请求并完成在途请求；还应结合终止宽限期、负载均衡和长连接实测，不能只配置 preStop 就断言无损。

运行一个完整的 Web 示例

前提：已有可用集群、kubectl 和创建命名空间的权限。保存下面内容为 demo-web.yaml。镜像版本仅作演示，部署前按仓库可用版本和安全要求调整。

# 创建独立的演示命名空间
apiVersion: v1
kind: Namespace
metadata:
  name: demo
---
# 通过配置文件提供静态首页
apiVersion: v1
kind: ConfigMap
metadata:
  name: demo-web-content
  namespace: demo
data:
  index.html: |
    <h1>Hello Kubernetes</h1>
---
# 由 Deployment 管理两个副本
apiVersion: apps/v1
kind: Deployment
metadata:
  name: demo-web
  namespace: demo
spec:
  replicas: 2
  selector:
    matchLabels:
      app: demo-web
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  template:
    metadata:
      labels:
        app: demo-web
    spec:
      terminationGracePeriodSeconds: 30
      containers:
        - name: web
          image: nginx:stable-alpine
          ports:
            - name: http
              containerPort: 80
          resources:
            requests:
              cpu: 100m
              memory: 64Mi
            limits:
              cpu: 500m
              memory: 128Mi
          startupProbe:
            httpGet:
              path: /
              port: http
            failureThreshold: 30
            periodSeconds: 2
          readinessProbe:
            httpGet:
              path: /
              port: http
            periodSeconds: 5
          livenessProbe:
            httpGet:
              path: /
              port: http
            periodSeconds: 10
          volumeMounts:
            - name: content
              mountPath: /usr/share/nginx/html
              readOnly: true
      volumes:
        - name: content
          configMap:
            name: demo-web-content
---
# 集群内部通过 Service 访问应用
apiVersion: v1
kind: Service
metadata:
  name: demo-web
  namespace: demo
spec:
  selector:
    app: demo-web
  ports:
    - name: http
      port: 80
      targetPort: http

执行顺序：校验 → 应用 → 等待就绪 → 检查端点 → 转发本地端口 → HTTP 验证。

# 仅解析和生成对象，不写入集群
kubectl apply --dry-run=client -f demo-web.yaml
# 创建命名空间、配置和应用；会修改当前集群
kubectl apply -f demo-web.yaml
# 等待 Deployment 完成发布，超时后查看事件而不是无限等待
kubectl rollout status deployment/demo-web -n demo --timeout=120s
# 检查副本和 Service
kubectl get deployment,pods,service -n demo
# 检查 Service 对应的后端
kubectl get endpointslice -n demo -l kubernetes.io/service-name=demo-web
# 仅绑定本机端口；保持该终端运行，Ctrl+C 结束
kubectl port-forward -n demo service/demo-web 8080:80

另开终端验证：

# 通过本机转发访问页面，预期包含 Hello Kubernetes
curl --fail --max-time 5 http://127.0.0.1:8080/

port-forward 只验证选中的后端与转发通路，不能代替 Service 集群内转发、Ingress 和所有副本的验收。

配置修改了，应用为什么没变化

环境变量从 ConfigMap 或 Secret 注入时，修改对象不会自动刷新已经运行的进程；使用挂载文件时，更新通常存在传播延迟，应用还需要重新读取文件。subPath 挂载也不能按普通目录挂载的更新行为判断。

# 查看当前 ConfigMap，配置含敏感信息时不要直接外传
kubectl get configmap demo-web-content -n demo -o yaml
# 从修改后的完整清单更新配置
kubectl apply -f demo-web.yaml
# 对依赖启动时读取配置的应用，安排一次滚动重启
kubectl rollout restart deployment/demo-web -n demo
# 等待重启完成
kubectl rollout status deployment/demo-web -n demo --timeout=120s

Secret 的 base64 表示不是加密。将业务密码通过受控的密钥管理流程注入，避免提交到公开仓库；读取 Secret 和创建 Secret 都应按需授予权限。

资源对象怎么选择

需求 对象与检查重点
常驻无状态服务 Deployment；副本、探针和更新策略
每节点运行采集器或代理 DaemonSet；节点选择、污点容忍和更新覆盖率
执行一次的任务 Job；完成条件、失败重试和任务幂等
周期任务 CronJob；时区、并发策略、错过调度和历史保留
固定身份和独立存储 StatefulSet；稳定网络身份、PVC 和有序更新

控制器保持副本数量，不保证业务绝不宕机。两个副本若落在同一故障域，仍可能同时不可用；生产应用应结合反亲和、拓扑分布和容量规划。

数据持久化与 StatefulSet

容器可写层不能作为可靠的数据存储。先确认存储类、访问模式、容量、拓扑和备份，再选择 PVC。ReadWriteOnce 不等于任意情况下只能被一个 Pod 使用，它主要约束单节点读写挂载；更严格的单 Pod 语义要检查存储插件是否支持对应模式。

# 查看可用存储类及默认项
kubectl get storageclass
# 检查业务卷与绑定状态
kubectl get pvc -n demo
# 查看 StatefulSet 副本、更新策略和卷声明
kubectl get statefulset -n demo -o yaml
# 检查某个 PVC 绑定、挂载相关事件
kubectl describe pvc demo-data -n demo

数据库副本、持久卷副本和备份解决不同问题。使用 Rook/Ceph、数据库 Operator 或 Vitess 前，应验证其版本兼容性、仲裁与故障恢复；不要因“已有三副本”就跳过备份恢复演练。

Ingress 与外部访问

创建 Ingress 对象之前必须确认有对应的控制器，并指定匹配的 IngressClass。流量顺序按外部 DNS → 入口地址 → 控制器 → Service → EndpointSlice → Pod 检查。配置了 Ingress 不表示公网地址和证书会自动准备好。

# 查看可用入口类
kubectl get ingressclass
# 查看业务入口地址、规则和事件
kubectl describe ingress demo-web -n demo
# 核对后端 Service 和端点
kubectl get service,endpointslice -n demo

HTTP 404 先确认 Host、路径和后端返回来源；502/503 结合控制器日志、端点就绪和后端监听排查。WebSocket、请求体大小和超时注解属于具体控制器能力，不能在不同产品之间直接照搬。

Helm 发布与回退

使用与当前集群兼容的 Helm 版本。旧教程中的 Tiller 和 Helm 2 初始化步骤不适用于常见的 Helm 3 工作流。Chart 来源、依赖、默认权限与持久卷行为都应在安装前检查。

# 查看本机 Helm 版本，前提是已安装
helm version
# 在本地 chart 目录执行基本检查
helm lint ./demo-chart
# 渲染资源清单，检查命名空间、镜像和权限；输出可能包含 Secret
helm template demo-web ./demo-chart -n demo -f values.yaml
# 确认后安装或更新；等待资源就绪，超时退出
helm upgrade --install demo-web ./demo-chart -n demo -f values.yaml --wait --timeout 5m
# 查看发布历史
helm history demo-web -n demo
# 确认回退目标后回滚到指定 revision
helm rollback demo-web 1 -n demo --wait --timeout 5m

应用回退不等于数据库结构和数据回退。发布前检查迁移脚本和向后兼容性，回退后仍需验证业务读写、错误率与数据完整性。

发布验收与清理

检查所有副本的就绪与重启次数、实际业务请求、错误率、日志、端点和外部访问。就绪成功是条件之一，不能替代业务验收。

# 只读检查应用副本与节点分布
kubectl get pods -n demo -l app=demo-web -o wide
# 查看各副本近期日志
kubectl logs -n demo -l app=demo-web --all-containers --prefix --tail=50
# 演示结束后只删除本例的 Deployment 和 Service
kubectl delete deployment/demo-web service/demo-web -n demo
# 删除本例的首页配置
kubectl delete configmap/demo-web-content -n demo

保留命名空间，清理前核对同名对象是否属于本次实验。

Helm 安装：Linux 二进制下载、校验与用户目录

在 Helm 发布页 选择与集群及 Chart 兼容的版本，并查看该版本的命令帮助。以下示例为 Linux amd64，其他架构替换包名。

# 输入选定版本号，包含 v 前缀
read -r -p 'Helm version: ' HELM_VERSION
# 下载指定版本的官方二进制包
curl --fail --location --output helm.tar.gz "https://get.helm.sh/helm-${HELM_VERSION}-linux-amd64.tar.gz"
# 下载对应校验文件
curl --fail --location --output helm.sha256sum "https://get.helm.sh/helm-${HELM_VERSION}-linux-amd64.tar.gz.sha256sum"
# 提取校验值并校验本地文件；成功后才继续
awk '{print $1 "  helm.tar.gz"}' helm.sha256sum | sha256sum --check
# 在独立临时目录解包，避免覆盖现有文件
helm_unpack=$(mktemp -d)
# 解开已校验的包
 tar -xzf helm.tar.gz -C "$helm_unpack"
# 创建用户可执行目录
mkdir -p "$HOME/.local/bin"
# 安装已校验的可执行文件
install -m 0755 "$helm_unpack/linux-amd64/helm" "$HOME/.local/bin/helm"
# 为当前终端添加 PATH
export PATH="$HOME/.local/bin:$PATH"
# 检查版本与帮助
helm version
helm upgrade --help

下载或校验失败应停止，不继续解包安装。安装不需要集群管理员权限，发布应用时仍受 kubeconfig 和 RBAC 限制。

定时任务重复执行或没有执行

CronJob 创建 Job，再由 Job 创建 Pod。检查时沿 CronJob → Job → Pod 逐层定位，区别没有调度、调度后失败和任务还在运行。业务任务要有幂等控制，不能把调度当成恰好执行一次的保证。

# 查看定时规则、暂停状态和上次调度时间
kubectl get cronjob -n demo
# 查看目标 CronJob 配置及事件
kubectl describe cronjob demo-report -n demo
# 查看已创建的任务及完成数量
kubectl get jobs -n demo
# 查看某个 Job 创建的 Pod，标签按实际 Job 名替换
kubectl get pods -n demo -l batch.kubernetes.io/job-name=demo-report-12345
# 查看该 Job 的日志；多 Pod 或容器时进一步指定
kubectl logs -n demo job/demo-report-12345 --tail=100

例如上一次任务运行超过调度周期，检查 concurrencyPolicy 是 Allow、Forbid 还是 Replace；没有执行则检查 suspend、时区、startingDeadlineSeconds 和控制器事件。需要人工补跑时先确认任务幂等及数据范围，再从 CronJob 创建独立 Job，不直接修改历史任务。

扩容之后吞吐没有提高

先区分副本未创建、Pod 未调度、Pod 未就绪、流量未分配和下游已饱和。增加副本不能解决数据库锁竞争、共享限流或单分区瓶颈。

# 查看 Deployment 的期望和可用副本
kubectl get deployment demo-web -n demo
# 查看各副本节点分布和状态
kubectl get pods -n demo -l app=demo-web -o wide
# 查看自动扩缩容状态及限制，依赖已配置 HPA
kubectl get hpa -n demo
# 检查资源用量，依赖 Metrics API
kubectl top pods -n demo --containers

CPU requests 影响调度和部分 HPA 利用率计算；CPU limit 可能导致节流，内存 limit 则可能引发 OOM。不要把 requests 当成实际用量，也不要只看宿主机空闲就判断容器没有资源瓶颈。
