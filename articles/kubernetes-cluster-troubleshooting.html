Kubernetes 集群搭建、维护与故障排查

知知行笔记·约 24 分钟阅读
kubernetesclustertroubleshooting

以下命令中的命名空间、节点与 Pod 均为示例，按实际环境替换。先确认当前集群和权限，再执行操作。

CentOS 7已有节点：先核对版本、内核、运行时与cgroup 
cat /etc/centos-release           # 确认发行版版本
uname -r                         # 记录节点实际运行内核
systemctl --version              # 查看systemd版本，CentOS 7常见219
kubelet --version                # 查看此节点kubelet版本，不通过安装新版来查询
kubectl get nodes -o wide        # 在有权限的管理机上对照各节点版本及运行时
findmnt -t cgroup,cgroup2         # 确认实际控制器挂载，CentOS 7常见v1
sudo systemctl cat kubelet       # 查看启动参数和配置路径，不修改配置

示例：kubelet、API Server、CRI运行时和CNI须按原集群版本分别核对。cgroup v1的内存/CPU路径见内核排查和性能排查，不能照搬 memory.events、cpu.max。较新版本可能要求不同内核及cgroup能力，按目标版本的kubeadm说明核对，不通过忽略预检查来强装。

下面的kind新建实验与kubeadm搭建步骤在符合目标版本要求的系统执行；CentOS 7已有节点以维护、迁移为主。不直接复制最新版软件源，不卸载原containerd/Docker，也不把cgroup模式在线切换当成修复。

先判断故障在哪一层

现象 第一组证据 后续方向
kubectl 连接失败 当前上下文、服务端地址、证书错误 API、控制面负载均衡、凭据
Pod Pending describe 的调度事件 requests、污点、亲和、PVC
CrashLoopBackOff 上一次退出原因和日志 启动参数、配置、依赖、探针
OOMKilled 容器限制与节点内存压力 工作集、堆外内存、并发
Pod 正常但请求不通 selector、EndpointSlice、实际监听端口 Service、DNS、策略和 CNI
部分节点才失败 Pod 分布、节点及网络插件日志 节点资源、路由、MTU、插件 
# 列出所有命名空间的 Pod，定位故障范围
kubectl get pods -A -o wide
# 按创建时间查看业务事件；事件有保留期限，不是完整审计日志
kubectl get events -n demo --sort-by=.metadata.creationTimestamp
# 查看当前容器日志
kubectl logs -n demo demo-api-xxxxx -c app --tail=100 --timestamps
# 容器重启后查看上一次实例的日志；未保留时可能无法获取
kubectl logs -n demo demo-api-xxxxx -c app --previous --tail=100 --timestamps

集群搭建前的版本核对

kubeadm、kubelet、kubectl 与容器运行时应按目标 Kubernetes 版本和操作系统选择兼容版本。不同 CNI 对网络和内核要求不同；先明确 Pod CIDR、Service CIDR、控制面入口和生产环境高可用方案。

# 查看系统与内核信息
cat /etc/os-release
uname -r
# 查看已有容器运行时服务状态
sudo systemctl status containerd --no-pager
# 查看已安装的 kubeadm 和 kubelet 版本
kubeadm version -o short
kubelet --version

较新的 Kubernetes 不再内置 dockershim；使用 Docker Engine 作为运行时时需要兼容的 CRI 适配器。不要照搬旧课程中的 dockershim socket、过期软件源或旧版 kubeadm 配置。安装、初始化和加入节点应使用匹配版本的官方说明，先在隔离环境验证。

本机实验：用 kind 创建集群

适用于练习清单、发布和故障排查；多节点容器共享同一宿主机，不能代表生产高可用。需要已安装并可使用 Docker 或 kind 支持的其他容器引擎。kubectl 安装见常用命令笔记中的折叠步骤。

安装 kind：下载、校验和普通用户目录

在 kind 官方发布页 选择版本，核对支持的节点镜像与系统架构。以下为 Linux amd64，arm64 需替换文件名与校验值。

# 输入发布页上选定的版本，例如 v开头的完整版本号
read -r -p 'kind version: ' KIND_VERSION
# 输入同一发布页提供的 linux-amd64 二进制 SHA256
read -r -p 'kind SHA256: ' KIND_SHA256
# 下载指定版本的二进制；失败时不执行后续安装
curl --fail --location --output kind "https://kind.sigs.k8s.io/dl/${KIND_VERSION}/kind-linux-amd64"
# 核对下载文件；仅校验通过后继续
printf '%s  kind\n' "$KIND_SHA256" | sha256sum --check
# 创建当前用户的可执行文件目录
mkdir -p "$HOME/.local/bin"
# 校验成功后安装，无需 root 权限
install -m 0755 kind "$HOME/.local/bin/kind"
# 临时将用户目录加到当前终端 PATH
export PATH="$HOME/.local/bin:$PATH"
# 检查安装结果
kind version

以上命令逐步执行，下载或校验失败应停止。永久 PATH 可加入当前 shell 的启动文件，重新登录后确认。

保存为 kind-demo.yaml：

# 使用当前 kind 支持的配置格式创建一控制面两工作节点
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
  - role: worker
  - role: worker

# 检查容器引擎是否可用
 docker info
# 创建实验集群并等待控制面就绪，kind 会更新 kubeconfig
kind create cluster --name demo-lab --config kind-demo.yaml --wait 120s
# 显式确认实验集群上下文，避免误操作其他集群
kubectl --context kind-demo-lab get nodes -o wide
# 创建失败时导出诊断日志
kind export logs --name demo-lab ./demo-lab-logs
# 实验完成且已保存所需数据后删除整个实验集群
kind delete cluster --name demo-lab

如需复现实验版本，按该 kind 发布说明选择兼容的 kindest/node 镜像并通过 --image 固定镜像及摘要。不要把旧教程镜像直接套到新 kind。

kubeadm 多节点搭建的执行顺序

kubeadm 不负责安装容器运行时和网络插件。先准备节点，再初始化控制面，安装一个匹配的 CNI，加入工作节点，最后验收。生产集群还需要控制面与 etcd 的高可用、备份及升级方案。

阶段 必须先确认的条件 验收
主机准备 唯一主机名、IP、时间同步、节点通信、CPU/内存、Swap 策略 节点间访问与资源满足要求
运行时 CRI 可用，kubelet 与运行时 cgroup 配置一致 crictl info 成功
软件包 使用目标版本对应的软件源，固定兼容版本 kubeadm/kubelet/kubectl 版本符合策略
控制面 API 入口、证书 SAN、CIDR 无冲突 API readyz 与静态 Pod 正常
CNI 按插件版本安装一个方案，CIDR/MTU 符合设计 网络 Pod 正常、CoreDNS 就绪
工作节点 使用初始化输出的 join 命令与正确 CA hash 节点 Ready、跨节点请求成功
kubeadm 初始化和加入：命令模板与凭据处理

以下只在已准备好的新实验节点执行。先将 kubeadm-config.yaml 按目标版本生成并修改，明确 API 入口和网络范围；不能原样用于既有集群。

# 生成本机 kubeadm 版本支持的默认初始化配置，输出到新文件
kubeadm config print init-defaults > kubeadm-config.yaml
# 手工编辑配置后，校验结构
kubeadm config validate --config kubeadm-config.yaml
# 查看当前配置所需的控制面镜像
kubeadm config images list --config kubeadm-config.yaml
# 在准备好的新控制面节点初始化；会修改系统并启动集群
sudo kubeadm init --config kubeadm-config.yaml
# 在控制面创建短时有效的工作节点加入命令；输出包含敏感 token
sudo kubeadm token create --ttl 30m --print-join-command

把最后输出的完整 join 命令交给目标工作节点的管理员执行，保留 token 和 CA hash，不通过公开聊天或仓库传播。控制面节点加入还需要额外的高可用配置，不能使用普通 worker join 命令替代。

初始化输出的 kubeconfig 配置步骤只交给被授权的管理员。不要覆盖已有 kubeconfig；保留备份或使用独立文件，通过 --kubeconfig 指定。

包安装按目标版本的 kubeadm 安装文档 选择软件源和版本；运行时配置 与 CNI 参数需按实际版本核对。

普通用户与 RBAC

Linux 的 sudo 权限和 Kubernetes 的 RBAC 是两套权限。不要通过 sudo kubectl 试图修复 RBAC，它可能切换到 root 的另一个 kubeconfig。

# 确认当前客户端上下文
kubectl config current-context
# 检查当前身份是否有读取权限
kubectl auth can-i get pods -n demo
# 检查当前身份是否可查看容器日志
kubectl auth can-i get pods --subresource=log -n demo
# 检查是否可进入容器
kubectl auth can-i create pods --subresource=exec -n demo

管理员应按命名空间绑定最小权限 Role；集群范围资源才考虑 ClusterRole。不要把 admin.conf 作为所有人的通用配置。kubeconfig 包含凭据与执行认证插件配置，只使用可信文件，限制读取权限。

containerd 和节点容器排查

ctr 默认命名空间与 Kubernetes 容器使用的命名空间不同；节点容器排查优先使用已配置正确 CRI endpoint 的 crictl。containerd 主版本不同，插件配置段也可能不同，不要用一条 sed 命令修改所有版本。

crictl 的安装与连接检查

优先使用发行版或 Kubernetes 匹配源提供的 cri-tools。先查询候选版本，确认仓库可信且版本适配，再安装。

# Debian / Ubuntu 查询候选包，前提是已配置匹配的软件源
apt-cache policy cri-tools
# 确认候选版本后安装，需要 sudo 权限
sudo apt-get install cri-tools
# RHEL 系查询可用版本
# dnf info cri-tools
# 确认后按系统包管理器安装
# sudo dnf install cri-tools
# CentOS 7已有节点：在原集群批准源中查询版本后，改用yum安装具体版本
# yum --showduplicates list cri-tools
# sudo yum install cri-tools-具体版本 # 替换版本后执行，不自动升级节点工具
# 查看 crictl 帮助及当前版本
crictl --version

containerd 的常见 endpoint 为 unix:///run/containerd/containerd.sock，先按本机服务配置确认路径。

# 明确指定已核对的 CRI endpoint，检查运行时
sudo crictl --runtime-endpoint unix:///run/containerd/containerd.sock info
# 查看包括退出实例在内的容器
sudo crictl --runtime-endpoint unix:///run/containerd/containerd.sock ps -a

# 查看运行时状态
sudo systemctl status containerd --no-pager
# 查看近期运行时错误
sudo journalctl -u containerd --since '30 minutes ago' --no-pager
# 检查节点内存及换页压力
free -h
vmstat 1 5

kubelet 与运行时的 cgroup 设置应一致。修改运行时配置可能影响所有节点容器，先计划维护并做好回退。不要直接重置集群来处理单个 Pod 的镜像错误。

API 或控制面异常

kube-apiserver 接收请求；etcd 保存集群状态；scheduler 选择节点；controller-manager 推进对象期望状态。仅 kubelet 正常并不足以说明控制面正常。托管集群的控制面通常需要通过云平台查询，不能直接套用自建节点路径。

# 查看 API 就绪检查，需要相应权限
kubectl get --raw='/readyz?verbose'
# 查看 kube-system 组件，注意控制面也可能以不同方式部署
kubectl get pods -n kube-system -o wide
# 自建 kubeadm 控制面检查证书到期信息
sudo kubeadm certs check-expiration
# 自建节点检查静态 Pod 清单文件名，不直接输出其中敏感参数
sudo ls -l /etc/kubernetes/manifests

API 超时要区分 TCP 不通、TLS 错误、认证拒绝和请求执行慢；Forbidden 通常先查授权。证书更新前保存配置和备份，按当前版本流程处理所有控制面节点，并核对客户端 kubeconfig，避免只更新一部分。

节点 NotReady

执行顺序：查看 Node 条件和事件 → 登录对应节点查看 kubelet 与运行时 → 检查资源及到控制面的连接 → 修复原因 → 持续观察恢复。

# 确认当前连接的集群
kubectl config current-context
# 查看节点状态和版本
kubectl get nodes -o wide
# 查看异常节点条件、污点和事件
kubectl describe node worker-01
# 在异常节点查看 kubelet 状态
sudo systemctl status kubelet --no-pager
# 在异常节点查看最近 30 分钟 kubelet 日志
sudo journalctl -u kubelet --since '30 minutes ago' --no-pager
# 查看节点可用磁盘空间和 inode
 df -hT
 df -i

例如 Node 的 Ready 条件为 Unknown 且 kubelet 日志显示无法连接 API，继续检查节点到 API 的实际地址、证书和网络；磁盘压力则查具体挂载空间与 inode。不要仅凭 NotReady 就重启所有组件。修复后重新执行 kubectl get nodes，并检查该节点上业务 Pod 是否恢复。

Pod Pending 与 CrashLoopBackOff

# 查等待调度或无法启动的具体原因
kubectl describe pod demo-api-xxxxx -n demo
# 读取上次退出实例日志，检查应用启动错误
kubectl logs demo-api-xxxxx -n demo -c app --previous --tail=100
# 查看各容器退出原因及退出码
kubectl get pod demo-api-xxxxx -n demo -o jsonpath='{range .status.containerStatuses[*]}{.name}{" "}{.lastState.terminated.reason}{" "}{.lastState.terminated.exitCode}{"\n"}{end}'

Pending 的事件若显示 Insufficient cpu，比较 Pod requests 与节点可分配余量；若是 untolerated taint，先确认工作负载是否应该到该节点，不能随意去掉控制面污点。亲和规则、拓扑约束和 PVC 也可能阻止调度。

CrashLoopBackOff 表示反复退出后的重试退避。查看退出前日志、启动命令、配置和探针事件；OOMKilled 结合容器限制与节点内存调查，退出码 137 本身不足以断言 OOM。修复后检查重启次数是否停止增长、探针与业务请求是否正常。

DNS 解析失败

执行顺序：确认服务名称及命名空间 → 检查 CoreDNS Pod 与 Service → 查看端点和日志 → 从受影响 Pod 所在环境对照查询 → 检查上游解析及网络策略。

# 查看 DNS 服务和 CoreDNS Pod
kubectl get service,pods -n kube-system -l k8s-app=kube-dns -o wide
# 查看 DNS Service 的后端端点
kubectl get endpointslice -n kube-system -l kubernetes.io/service-name=kube-dns -o wide
# 查看 DNS Pod 的近期日志，标签按实际集群调整
kubectl logs -n kube-system -l k8s-app=kube-dns --tail=100 --prefix
# 查看目标 Pod 的 DNS 配置；容器中需包含 cat
kubectl exec -n demo demo-api-xxxxx -- cat /etc/resolv.conf

如果同命名空间短名称可解析、跨命名空间不可解析，核对 服务名.命名空间.svc；仅外部域名失败时，检查 CoreDNS 转发配置和上游服务。日志与查询可能包含业务域名，分享前脱敏。

访问失败的分层对照

对照结果 优先检查
localhost 也失败 应用未启动、未监听、端口或协议错误
Pod IP 成功、Service IP 失败 Service 端口、后端选择、代理或替代数据路径
Service IP 成功、服务域名失败 DNS、搜索域、解析配置
同节点成功、跨节点失败 CNI、节点路由、封装、防火墙、MTU
集群内成功、外部失败 Ingress/LB、外部 DNS、证书、安全组与入口路由

测试必须在实际受影响的网络位置进行。port-forward 绕过了部分集群网络，成功并不能证明跨节点 CNI 正常；HTTP HEAD 与 GET 也可能走不同应用逻辑，按真实接口验证。

网络与存储插件的排查边界

Calico、Cilium 等提供的网络数据路径不同；部分配置还会替代 kube-proxy。先确认当前部署方案，避免把“没有 kube-proxy”误判成异常。按同节点 Pod、跨节点 Pod、Service IP、DNS 和外部访问分别测试，可以缩小故障层次。

# 查看系统 DaemonSet，确认网络和存储节点插件的期望/就绪数量
kubectl get daemonset -n kube-system -o wide
# 检查系统组件在哪些节点异常
kubectl get pods -n kube-system -o wide
# 列出命名空间内网络策略；还需核对插件自有策略
kubectl get networkpolicy -n demo
# 在故障节点只读查看路由和链路 MTU
ip route
ip -d link show

IPVS、iptables、nftables 或 eBPF 的排查工具按实际模式选择。不要通过清空防火墙、删除全部路由或全局关闭策略来试错。涉及跨节点大包失败时检查实际封装开销、MTU 和路径反馈，不统一照搬某个固定 MTU。

LoadBalancer 一直 Pending

# 查看外部入口分配及 Service 事件
kubectl describe service demo-gateway -n demo
# 查看该命名空间资源配额，配额也可能影响新资源和发布
kubectl get resourcequota,limitrange -n demo

LoadBalancer 类型需要云提供商或集群内负载均衡实现支持。在普通自建集群中，只创建 Service 不一定能分配外部 IP。先确认实现是否存在、地址池是否耗尽、云配额与权限是否满足，再检查安全组与路由。NodePort 也要按实际监听范围、流量策略和防火墙验证，不能以主机端口列表代替整个访问链路检查。

PVC 一直 Pending

执行顺序：检查 PVC 事件 → 查看 StorageClass、绑定模式和可用 PV → 按存储插件检查供应器 → 复查 Pod 调度与绑定。

# 查看业务命名空间的 PVC 状态
kubectl get pvc -n demo
# 查看目标 PVC 的存储类和事件
kubectl describe pvc demo-data -n demo
# 查看存储类及绑定模式
kubectl get storageclass -o wide
# 查看集群中的 PV 状态
kubectl get pv
# 查看使用 PVC 的 Pod 调度事件
kubectl describe pod demo-api-xxxxx -n demo

例如 StorageClass 的绑定模式为 WaitForFirstConsumer，在消费者 Pod 可调度前 PVC 处于 Pending 可能符合预期；若事件显示供应器不可用，再查对应 CSI 控制器与节点插件。不要直接删除 PVC 或 PV 来排障，先确认回收策略和数据备份。

NFS 挂载失败与快照恢复

Pod 事件出现 FailedMount 时，先看错误是客户端工具缺失、服务器不可达、导出权限、路径不存在还是挂载选项不兼容。NFS 客户端工具安装在实际执行挂载的节点上，不是只装在管理电脑上。

安装 NFS 客户端工具 
# Debian / Ubuntu 节点安装 NFS 客户端，需 sudo 权限
sudo apt-get install nfs-common
# RHEL 系节点改用对应包管理器安装
# sudo dnf install nfs-utils
# CentOS 7已有节点：按需选择这一条，使用现有批准仓库
# sudo yum install nfs-utils
# 检查挂载辅助程序路径
command -v mount.nfs

# 从事件确认失败发生在哪个节点及具体原因
kubectl describe pod demo-api-xxxxx -n demo
# 只读查看 PV 的服务端和挂载参数，先替换实际卷名
kubectl describe pv demo-pv
# 在失败节点检查到实际存储服务器的路由，替换示例地址
ip route get 192.0.2.20

不要通过放宽全部共享目录权限、取消根用户映射或强制拆盘来试错。恢复时先确认原工作负载停止写入，避免两个实例同时访问不支持并发写入的卷。

CSI 卷快照依赖驱动能力、快照 CRD 与控制器。先检查环境是否提供这些资源：

# 查看当前 API 是否包含快照资源
kubectl api-resources --api-group=snapshot.storage.k8s.io
# 已安装快照资源时查看可用快照类
kubectl get volumesnapshotclass
# 查看业务快照是否 readyToUse
kubectl get volumesnapshot -n demo

快照 readyToUse 只表示存储侧准备就绪，不保证数据库应用一致性；按数据库要求配合冻结、备份或日志恢复。恢复到新 PVC 并在隔离环境验证，保留原卷和恢复前证据。快照与源数据位于同一故障域时，也不能替代异地备份。

节点维护与恢复

先检查副本和容量、PDB、DaemonSet、本地卷及 emptyDir 数据。drain 受 PDB 和驱逐约束，失败时应理解原因，不直接加 force 跳过。

# 查看中断预算
kubectl get pdb -A
# 阻止新 Pod 调度到待维护节点
kubectl cordon worker-01
# 在已确认副本、数据和容量后驱逐普通工作负载；保留 DaemonSet
kubectl drain worker-01 --ignore-daemonsets --timeout=5m
# 完成维护后检查节点状态
kubectl describe node worker-01
# 确认恢复正常后允许调度
kubectl uncordon worker-01

drain 遇到 emptyDir 数据提示时，确认数据确实可丢弃后才考虑相应参数。维护后检查副本分布、业务请求和存储挂载，而不只看 Node Ready。

监控、备份与恢复验收

Metrics Server 主要提供资源指标，不能替代长期监控、日志和告警。监控至少包括节点资源、Pod 重启、请求错误率和延迟、API 与 etcd 状态、存储容量及备份结果。

# 查看节点当前资源，依赖集群提供 Metrics API
kubectl top nodes
# 查看业务 Pod 的容器资源
kubectl top pods -n demo --containers
# 检查 Metrics API 注册状态
kubectl get apiservice v1beta1.metrics.k8s.io

etcd 快照主要覆盖 Kubernetes 集群状态，不包含外部持久卷中的业务数据。备份计划应同时覆盖集群状态、应用清单、凭据保护、卷与数据库，并记录恢复所需版本、密钥、存储插件及网络配置。

不要在现有生产控制面直接练习快照恢复。先在隔离环境按备份工具与 etcd 对应版本恢复，再检验对象数量、权限、卷挂载、数据库一致性和真实请求；成功生成备份文件不等于已经能够恢复。
